Data agents in production: build, ground and evaluate over gold data

A data agent that answers "sales" with the wrong number is worse than no agent. Build one over a gold sales table, score it against eleven questions with known answers, fix the misses with instructions and example queries, then rerun the same test before every change goes live.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa AILakehouse

Short answer

A Fabric data agent turns a question into SQL, DAX or KQL, runs it as the person asking and answers in plain English. Getting one to answer is easy. Getting it to answer the way finance would is the work. Point it at a small gold table rather than everything, write down your definitions in the agent and data source instructions, add example queries for the patterns that matter, then measure it with the data agent evaluation SDK against questions whose answers you computed yourself. Run that test again every time anything changes. An agent without a test set is a demo.

The symptom

Harbour Goods, the fictional retailer used across this site, built a data agent over its sales lakehouse and shared it with store managers. Within a week three complaints came in:

  • "Sales for Q3" came back as 207,503.00. Finance reports 195,849.25.
  • The gross margin was quoted as 38.2 per cent. Finance says 34.5.
  • Asked why August was weak, the agent offered a confident paragraph about seasonality that nobody had evidence for.

The agent was not broken. It did what an agent does with no definitions: it summed quantity * unit_price, which is sales before discount, because nothing told it that "sales" at Harbour Goods means net of discount.

Measure it

Step 1: load the gold table

The sample data-agents-in-production.csv holds 72 orders from July to September 2026 across six stores and nine products: one row per order with quantity, unit price, discount, net_amount (after discount) and cost_amount. Upload it to the Files area of a lakehouse called lh_sales_gold, then run this in a notebook attached to it:

from pyspark.sql import functions as F

df = (spark.read.option("header", True).option("inferSchema", True)
      .csv("Files/data-agents-in-production.csv")
      .withColumn("order_date", F.to_date("order_date"))
      .withColumn("net_amount", F.col("net_amount").cast("decimal(12,2)"))
      .withColumn("cost_amount", F.col("cost_amount").cast("decimal(12,2)")))

df.write.mode("overwrite").format("delta").saveAsTable("gold_sales")
print(spark.table("gold_sales").count()) # expect 72

One clean table with descriptive column names does more for an agent than any instruction you will write later. net_amount is hard to misread. amt2 is not.

Step 2: build the agent with no help

In the workspace select + New item, search for Fabric data agent and name it da_sales_questions. In the OneLake catalog that opens, add lh_sales_gold, then tick only gold_sales in the Explorer. You need a paid F2 or larger capacity (or P1 with Fabric enabled). A capacity in India also needs the two tenant settings that let Azure OpenAI data be processed and stored outside the capacity's region. Select Publish so there is a stage to evaluate against.

Step 3: score it against known answers

The test set is data-agents-in-production-eval.csv: eleven questions with a question and an expected_answer column, the format the evaluation SDK expects. Every answer was computed from the CSV in Python, not taken from the agent. Upload it to the same Files area and run:

%pip install -U fabric-data-agent-sdk
import pandas as pd
from fabric.dataagent.evaluation import (
    evaluate_data_agent, get_evaluation_summary, get_evaluation_details)

df = pd.read_csv("/lakehouse/default/Files/data-agents-in-production-eval.csv")

run_id = evaluate_data_agent(
    df,
    "da_sales_questions",
    table_name="agent_eval",
    data_agent_stage="production",
)
display(get_evaluation_summary("agent_eval"))
display(get_evaluation_details(run_id, "agent_eval", get_all_rows=True))

The SDK asks each question, compares the agent's answer with yours using a judge prompt and writes two tables to the lakehouse: agent_eval with the verdicts and agent_eval_steps with the reasoning and the generated queries. Each row links to the evaluation thread, which only the person who ran it can open.

A first run on a bare agent typically scores around seven of eleven. The misses follow the pattern above:

  • Q3 sales at 207,503.00 instead of 195,849.25.
  • West named correctly as the top region but at 75,842.00 instead of 71,355.00.
  • Gross margin at 38.2 per cent, because it divided by sales before discount.
  • A speculative answer to the "why" question.

Your exact score will move between runs. The model is not deterministic, which is the whole reason you keep a test set.

Fix it

Step 4: agent instructions

Select Data agent instructions and write the definitions down. You have up to 15,000 characters; you will need about 800.

You answer questions about Harbour Goods store sales from gold_sales.

Definitions:
- "Sales" or "revenue" always means net sales: SUM(net_amount). Never use
  quantity * unit_price unless the user asks for sales before discount.
- Gross margin % = (SUM(net_amount) - SUM(cost_amount)) / SUM(net_amount).
- Quarters are calendar quarters. Q3 2026 is 1 July to 30 September 2026.
  If the user says "fiscal", ask which fiscal calendar they mean.
- One row is one order. Order counts are COUNT(DISTINCT order_id).

Rules:
- Show money with two decimals and say whether it is net or gross.
- For "why" questions, say the data records what happened, not why.
  Give the relevant figures and stop. Do not guess at causes.

The quarter rule earns its place. Many Indian businesses run an April to March financial year, where Q3 means October to December. Leave it undefined and the agent picks one.

Step 5: data source instructions

Select the lakehouse in the Explorer and open its instructions (the label may read Data source instructions). This is where table and column meaning goes:

gold_sales: one row per order, July to September 2026.
net_amount = quantity * unit_price * (1 - discount), in rupees.
cost_amount = quantity * unit cost, in rupees.
discount is a fraction: 0.15 means 15 per cent.
region values: North, South, East, West.

Step 6: example queries

Select Example queries and add question and SQL pairs for the patterns you care about. Up to 100 per data source; the agent retrieves the few most similar to each new question. Do not paste in your test questions. If the examples are the test, the test measures memory, not understanding.

-- Question: What were net sales in July 2026?
SELECT SUM(net_amount) AS net_sales
FROM gold_sales
WHERE order_date >= '2026-07-01' AND order_date < '2026-08-01';
-- Question: What was gross margin % by category last quarter?
SELECT category,
       CAST(100.0 * (SUM(net_amount) - SUM(cost_amount))
            / SUM(net_amount) AS DECIMAL(5,2)) AS gross_margin_pct
FROM gold_sales
WHERE order_date >= '2026-07-01' AND order_date < '2026-10-01'
GROUP BY category
ORDER BY gross_margin_pct DESC;

Add three or four more in the same style: orders by store, units by product, net sales for one region and month. Each example is validated against the schema; one that fails validation is silently ignored, so check every one shows as valid. The SDK can also test them in bulk with evaluate_few_shots.

Step 7: evaluate the draft before publishing

Your changes live in the draft. Rerun step 3 with data_agent_stage="sandbox" and a new table_name such as agent_eval_v2, so the before and after runs sit side by side. Publish only if the score went up and nothing that passed before now fails.

Treat 11 of 11 as the floor, not the finish. Eleven questions are a smoke test. A production agent wants fifty or more, written by the people who will use it, with new ones added every time a real user catches a wrong answer.

Where this breaks

  • The 25-row cap. Chat answers return at most 25 rows and 25 columns. "List all orders this quarter" comes back truncated and follow-up questions then reason over the truncated list. Agents are for answers, not extracts.
  • Region mismatch. The agent cannot query a source whose capacity sits in a different region from the agent's capacity. Keep them together.
  • Permissions are the asker's. Queries run under the user's identity, so row level security and workspace roles apply. A store manager sees their stores' numbers, which is right, but it means your evaluation run only proves the answers for your own permissions.
  • Semantic model sources work differently. Example queries are not supported for semantic models. Put the definitions in the model with Prep data for AI instead.
  • Leaving the compliance boundary. Once the agent is consumed from Copilot Studio, Microsoft Foundry or Microsoft 365 Copilot, its answers can leave Fabric's compliance boundary and region. Decide that on purpose, especially for regulated data.
  • Changing tables under the agent. Rename a column and the examples that use it stop validating. Rerun the evaluation after every schema change, not only after instruction changes.

On the brewhouse floor

Brewery A put an agent over its gold batch table so shift leads could ask for yesterday's numbers. The first question that went wrong was "what was brewhouse efficiency on batch 412?" The agent divided packaged volume by kettle volume, which is a real ratio, just not the one brewers mean. Brewhouse efficiency is the extract that reached the kettle as a share of what the malt could have given. One line in the instructions fixed it. One evaluation question with the head brewer's own figure keeps it fixed.
