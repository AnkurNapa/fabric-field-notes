Row and object security that holds under Direct Lake

Give each regional lead only their stores and hide product cost from them, with dynamic RLS and OLS on a Direct Lake model. Plus the part most guides skip: where the rules live, which identity reads the data and why Direct Lake on OneLake and on SQL behave differently.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa Power BIDirect LakeSecurity

Short answer

Define row-level security (RLS) and object-level security (OLS) as roles in the semantic model, then bind the Direct Lake model to a fixed identity cloud connection with single sign-on off. That combination keeps queries in memory and stops viewers going round the model to the lakehouse. Two rules catch almost everyone. First, model roles only apply to workspace Viewers; Admin, Member and Contributor bypass them, so test with a real Viewer. Second, RLS written on the lakehouse SQL analytics endpoint is not semantic model RLS. Direct Lake on SQL honours it by falling back to DirectQuery. Direct Lake on OneLake does not read it at all.

What you will build

Harbour Goods has four regional leads. Each should see sales for their own region's stores and nothing else. None of them should see product cost, because cost prices are negotiated centrally and the leads talk to suppliers.

On the sm_sales_kpis model you will add:

  • A dim_store table (store, city, region) and a region_access table that maps a user's sign-in name to the regions they can see.
  • One dynamic role, Region leads, that filters stores by the signed-in user.
  • OLS on the same role that hides fact_sales[cost_amount].
  • A fixed identity connection so viewers need no access to the lakehouse itself.

Before you start

  • The lh_sales_gold lakehouse and sm_sales_kpis Direct Lake on OneLake model from Your first Direct Lake model.
  • The store list: harbour-goods-stores.csv, six stores in four regions. Upload it to the lakehouse Files area.
  • Two accounts: yours (Admin or Member) and a test account added to the workspace as Viewer. Without the second account you cannot see RLS working.
  • Contributor or higher to create the cloud connection.

Step 1: add the store and access tables

Open a notebook on the lakehouse and run this. Replace the two sign-in names with real ones from your tenant: your own and your Viewer test account.

stores = (spark.read.option("header", True)
          .csv("Files/harbour-goods-stores.csv")
          .selectExpr("store_id", "city", "region", "to_date(opened) AS opened"))
stores.write.mode("overwrite").format("delta").saveAsTable("dim_store")

access = spark.createDataFrame(
    [("you@yourtenant.example", "West"),
     ("viewer.test@yourtenant.example", "West"),
     ("viewer.test@yourtenant.example", "South")],
    "user_upn string, region string")
access.write.mode("overwrite").format("delta").saveAsTable("region_access")

Store sign-in names in lower case. USERPRINCIPALNAME() returns the user principal name as the service resolves it. A capital letter typed into a mapping table is the most common reason a lead sees an empty report on day one.

In production this mapping comes from HR or an identity export, not a notebook. Keep it as a Delta table so the access list has history and an owner.

Step 2: add the tables to the model

  1. Open sm_sales_kpis from the workspace and switch to Editing.
  2. Select Edit tables, tick dim_store and region_access and confirm.
  3. Drag fact_sales[store_id] onto dim_store[store_id]: Many to one, cross filter Single.
  4. Leave region_access unrelated. Hide it from report view (right-click > Hide).

Single direction is deliberate. Bidirectional relationships are not supported in a Direct Lake model when the source relies on OneLake security RLS. They also make RLS filters harder to reason about.

Step 3: create the dynamic role

  1. On the ribbon select Manage roles, then New. Name the role Region leads.
  2. Under Select tables pick dim_store. Select Switch to DAX editor and enter:
dim_store[region]
    IN CALCULATETABLE (
        VALUES ( region_access[region] ),
        region_access[user_upn] = LOWER ( USERPRINCIPALNAME () )
    )
  1. Pick region_access and enter:
region_access[user_upn] = LOWER ( USERPRINCIPALNAME () )
  1. Select Save, then Assign and add the Viewer test account. Save again.

The second filter stops a lead with Build permission from querying the mapping table and learning who else sees what. The filter on dim_store flows to fact_sales through the relationship, so one rule covers every measure.

Step 4: hide cost with OLS

There is no OLS designer. Learn documents TMDL for it. TMDL view is available in the browser as a preview (some tenants label it TMDL View (Preview)) as well as in Desktop.

  1. Open TMDL view and drag the Region leads role from the Data pane into the editor. It scripts the role you just built as a createOrReplace block.
  2. Add the fact_sales permission at the bottom, keeping the indentation:
		tablePermission fact_sales
			columnPermission cost_amount
				metadataPermission: none
  1. Select Preview, check only the role changes, then Apply.

Scripting the role first matters. A createOrReplace that only contains the OLS lines replaces the whole role and silently drops the RLS filters you wrote in Step 3.

OLS hides the column and any measure that depends on it. For this role, Gross margin % and Average order margin % stop working and visuals that use them show a "can't be found" error. That is the intended behaviour, so give the leads a report page built on Net sales and quantities rather than reusing the margin page.

Keep RLS and OLS for the same audience in one role. Mixing an OLS role and a separate RLS role for one person is where tabular models start returning errors.

Step 5: bind a fixed identity

  1. In the workspace, open ... on sm_sales_kpis > Settings.
  2. Expand Gateway and cloud connections. Under Cloud connections, open Maps to and select Create a connection.
  3. Choose OAuth 2.0, Service Principal or Workspace Identity as the authentication method. Key and SAS options may appear but are not supported for Direct Lake.
  4. Leave single sign-on off. The option is described as Microsoft Entra ID SSO for DirectQuery and Direct Lake queries; the exact label may vary.
  5. Give the fixed identity Read and ReadAll on lh_sales_gold. Select Apply on the model settings.

Now the model reads the lake as one identity and applies your roles on top. Viewers need Read on the model and the report, nothing on the lakehouse. With SSO on, every viewer needs ReadAll on the lakehouse and can walk past the roles through a notebook or the SQL endpoint.

OneLake or SQL: where the rules actually run

Rule written inDirect Lake on OneLakeDirect Lake on SQL
Semantic model RLS and OLSApplied in memoryApplied in memory
SQL analytics endpoint RLSNot applied (see note)Applied, query falls back to DirectQuery
SQL analytics endpoint CLS or OLSNot evaluatedQuery errors on the secured column
OneLake security RLS and OLSApplied, then intersected with model rolesNot applicable

Learn is not consistent about the second row. The Direct Lake overview says queries on OneLake succeed and SQL endpoint RLS is not applied. The security integration page says such queries return an error. Either way the SQL rule does not protect a Direct Lake on OneLake report. Test it in your tenant before relying on either reading. Put the rule in the model or in OneLake security.

OneLake security is the choice when the same rows must be enforced in Spark, SQL and Power BI alike. Model roles only exist inside the model. A lead with ReadAll on the lakehouse can still read every row in a notebook.

Check it worked

  1. In the workspace, open ... on sm_sales_kpis > Security, then ... next to Region leads > Test as role. USERPRINCIPALNAME() returns your own identity here, so you see what your mapping row allows: West only.
  2. Sign in as the Viewer test account and open the report.

West is ST-011 Mumbai and ST-014 Pune. South adds ST-003 Bengaluru and ST-007 Chennai. If the Viewer sees 468,212.55, they are not a Viewer. If they see blank, compare their sign-in name with the region_access row character by character.

Where this breaks

  • Workspace roles beat model roles. Admin, Member and Contributor have Write on the model and RLS never applies to them. A lead given Contributor "so they can build their own reports" sees everything.
  • SSO hands out the lake. With SSO on, viewers need lakehouse access to query the model. Anyone with that access can bypass model roles through other engines.
  • Owner access for framing. The model owner must be able to read the source tables or refresh fails with an access denied message naming the tables.
  • Guest users. For B2B guests USERPRINCIPALNAME() may return an #EXT# form. Test with the real guest account; Test as role uses your identity.
  • Copilot and Q&A. Test as role cannot validate Copilot or Q&A output. Sign in as a Viewer to check what Copilot answers for a restricted user.
  • OneLake security limits. It does not support dynamic rules, so per-user mappings like this one stay in the model. After changing OneLake security roles, refresh Direct Lake on OneLake models that read the item.

On the brewhouse floor

A brewing group with three sites wants one production model where each head brewer sees only their own fermentation vessels and batches. The pattern is identical: a site table, a mapping of sign-in names to sites and one dynamic role. Brewery A's brewer opens the report and sees FV-01 to FV-08 and nothing from the other sites. The OLS line hides malt and hop cost per batch, which head office negotiates and site teams do not need. The model shows the brewer their tanks. It cannot stop someone with lakehouse access reading the other sites' gravity logs in a notebook, so the fixed identity is not optional.
