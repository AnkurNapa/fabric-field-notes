Fabric policies: control who creates what in production

Fabric policies (preview) replace on-or-off tenant switches with rules that check who, what and where. Build a capacity policy that lets only data engineers create notebooks, pipelines and lakehouses in production, without blocking everyone else on the capacity.

12 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa GovernanceSecurity

Short answer

Fabric policies arrived in preview in September 2026. Most tenant settings are a switch: on for a group, off for the rest. A policy is a set of rules. Each rule checks conditions such as the user's security group, the workspace and the item type. The policy lives as a Policy set item in a workspace. An admin activates it for the whole tenant or for one capacity.

The rule that catches people: once you add an Allow rule, the policy becomes an allow list. Anything no rule matches is blocked. Write a rule for everyone you still want to let through before you activate anything.

What you will build

Harbour Goods runs one F64 capacity. Two of its workspaces are production: hg-prod-sales and hg-prod-supply. Last quarter someone built a Dataflow Gen2 straight into hg-prod-sales and it ran every 15 minutes for six weeks. The team wants three things:

  • Only data engineers create notebooks, pipelines and lakehouses in production.
  • Only BI authors create semantic models and reports in production.
  • Every other workspace on the capacity carries on as before.

You will build one capacity-scoped policy set with three rules:

RuleSecurity groupsWorkspacesItem types
1. Engineers build in prodIs any of: sg-hg-data-engineersIs any of: both prod workspacesIs any of: Notebook, Pipeline, Lakehouse
2. BI authors publish in prodIs any of: sg-hg-bi-authorsIs any of: both prod workspacesIs any of: Semantic model, Report
3. Everything else as before(none)Is none of: both prod workspaces(none)

Conditions inside one rule must all be true. Separate rules are alternatives: one match is enough. A condition you leave out matches everything. Rule 3 has no group or item type condition, so it allows anyone to create anything outside production.

Before you start

  • The Policies (preview) tenant setting enabled. Turning it on needs a Fabric administrator.
  • A capacity administrator for the capacity you want to govern. Only they can activate a capacity-scoped policy.
  • An admin workspace on a Fabric capacity where you hold Contributor or higher. Call it hg-governance. Keep it locked down, because anyone who can edit the policy item can edit its rules.
  • The two Microsoft Entra ID security groups, plus one test user in each and one test user in neither.
  • A region check. In the preview, policies aren't supported on capacities in West Europe, North Europe or West US.

Step 1: turn on the Policies setting

  1. In the Fabric portal, open the OneLake catalog and select the Govern tab.
  2. Select Configurations and filter by Policies.
  3. Expand Policies and set the toggle to Enabled.
  4. Under Apply to, select a security group of platform admins, not the entire organisation. This setting decides who can create policy sets. It doesn't decide who the policies apply to.
  5. Select Apply.

Step 2: create the policy set

  1. Open hg-governance and select New item.
  2. Search for Policy set. If nothing shows, select All items and search again.
  3. Name it hg-cap-f64-prod-creation. Spaces aren't allowed.
  4. Under Policy set scope, select A capacity.
  5. Select Create.

You can't change the scope later. If you pick Fabric tenant by mistake, delete the item and start again.

The new policy set is inactive. Each policy shows its system default. Allow item creation starts at Allowed, which means every item type is allowed by workspace permissions as usual.

Step 3: add the three rules

  1. Open the policy set and find Allow item creation.
  2. Select Advanced (Set by user). This turns on the rule builder.
  3. Select Add rule. Name it engineers-build-in-prod and add a description that says who, what and where.
  4. Add three conditions:
    • Security groups, Is any of, sg-hg-data-engineers.
    • Workspaces, Is any of, hg-prod-sales and hg-prod-supply.
    • Item type, Is any of, Notebook, Pipeline and Lakehouse.
  5. Select Apply.
  6. Repeat for bi-authors-publish-in-prod with sg-hg-bi-authors, the same two workspaces and the item types Semantic model and Report.
  7. Add everything-else-as-before with one condition only: Workspaces, Is none of, hg-prod-sales and hg-prod-supply.

If you manage policies through the REST API or Git, the same rule 1 looks like this. The API takes object IDs and API item-type names such as DataPipeline, not display names such as Pipeline.

{
  "displayName": "engineers-build-in-prod",
  "description": "Data engineers create notebooks, pipelines and lakehouses in the two prod workspaces.",
  "policy": "ItemCreation",
  "conditions": [
    {
      "type": "Dynamic",
      "targetProperty": "principal.groups.id",
      "predicate": { "operator": "AnyOf", "values": ["<sg-hg-data-engineers object ID>"] }
    },
    {
      "type": "Dynamic",
      "targetProperty": "workspace.id",
      "predicate": { "operator": "AnyOf", "values": ["<hg-prod-sales ID>", "<hg-prod-supply ID>"] }
    },
    {
      "type": "Dynamic",
      "targetProperty": "item.type",
      "predicate": { "operator": "AnyOf", "values": ["Notebook", "DataPipeline", "Lakehouse"] }
    }
  ]
}

workspace.name isn't accepted. The API rejects it with UnsupportedPropertyValue.

Step 4: activate it

  1. In the policy set, open the status menu and select Active.
  2. Pick the F64 capacity and read the confirmation.
  3. If another policy set is already active on that capacity, Fabric asks you to replace it. Only one can be active per capacity.

Wait 15 minutes before testing. That's how long changes can take to apply. You can't activate a policy through Git. Activation is always an admin action in the portal or through the REST API.

Check it worked

Sign in as each test user and try to create the item shown. The expected result follows from the three rules.

BI authorhg-prod-supplyDataflow Gen2BlockedNone
Neither grouphg-prod-salesDataflow Gen2BlockedNone

Engineerhg-dev-salesReportAllowed3

Two blocked outcomes surprise people. An engineer can't create a report in production. A BI author can't create a Dataflow Gen2 there either. That's what an allow list means. If you want either, add it to a rule.

Then open the Fabric audit logs and find the policy decisions for your test users. Every allow and every block is recorded. That record is what you show an auditor.

Where this breaks

  • Preview. The labels and the policy list will change. Read the Learn page again before you roll this out to another capacity.
  • Forgetting rule 3. Without it, nobody can create anything in any non-prod workspace on the capacity. The first ticket arrives within the hour.
  • The tenant scope is stricter. Allow external data sharing is a tenant policy whose default is Block all. Any rule you add there is an allow list for the whole organisation. Test it with real recipient domains before you activate it.
  • One active set per scope. You can't stack a second capacity policy for another team. Merge their rules into the one set. Capacity policies hold up to 50 rules, tenant policies up to 100, with up to 50 values per condition.
  • No domain or workspace scope yet. Domain admins and workspace admins can't run their own policies. Plan for a capacity admin to own the rules.
  • Existing items aren't touched. The policy checks creation. The Dataflow Gen2 already in production keeps running until someone deletes it.
  • Security groups only. Conditions take Entra security groups, not individual users. Keep group membership tidy, because it's now part of your enforcement.

Policies are included in your Fabric licence and don't consume capacity units.

On the brewhouse floor

A brewery's quality lab keeps its gravity, pH and dissolved oxygen results in one production workspace. These numbers decide whether a batch is released. At Brewery A, a well-meaning shift lead built a second lakehouse there with hand-typed readings for FV-03. For a week, two sets of dissolved oxygen figures disagreed. One rule fixes it: only the QA group creates lakehouses and notebooks in the lab workspace. The policy blocks the second copy before it exists.
