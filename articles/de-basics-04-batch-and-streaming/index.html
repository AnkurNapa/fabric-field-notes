Data engineering basics, lesson 4 of 8

Batch and streaming

Lesson 4 of Data engineering basics. Batch moves data in scheduled lumps; streaming moves each event as it happens. See why an hourly average can hide a twenty-minute cold-store breach that a stream would catch.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa Real-timeKQL

Short answer

Batch processing collects data and moves it in lumps on a timetable: every night, every hour, every fifteen minutes. Streaming processes each event within seconds of it happening. Most business data is batch and that is fine. Streaming earns its cost only when someone will act differently because they saw something in seconds rather than hours. In Fabric, pipelines and notebooks handle batch; Eventstream, Eventhouse and Activator handle streaming.

Why it matters for your career

"We need real time" is one of the most common requests a data engineer hears and one of the most expensive to get wrong. Asking the right question and building the cheaper answer when it is enough marks you out quickly.

The idea

Two Harbour Goods examples show the difference.

Orders are batch. Finance looks at revenue each morning. If the orders file arrives at 05:30 and loads at 06:00, nobody is worse off. Running it every ten seconds would cost more and change nothing.

Cold-store temperatures are streaming. Harbour Goods keeps chilled stock between 2 and 8 °C in two cold-store warehouses. Each sensor sends a reading every few minutes as an event: one small record saying what happened and when. If a dock door is propped open, a sensor can climb past 8 °C in fifteen minutes. A report loaded at 06:00 the next day tells you the stock spoiled. A stream tells the shift lead while there is still time to shut the door.

The question to ask any "real time" request: what will someone do differently if they see it in ten seconds rather than ten minutes? If the honest answer is nothing, a faster batch schedule is the right build.

Try it in Fabric

You will query a short burst of cold-store readings with KQL in an Eventhouse, Fabric's store for event data. No stream is needed for this exercise; the readings are typed into the query itself, so it costs very little.

  1. In the harbour-dev workspace select + New item, search for Eventhouse and select it. Name it eh_harbour and select Create. A KQL database with the same name is created inside it.
  2. In the Explorer select the KQL database eh_harbour, then select Query with code on the database ribbon. You can also open the attached queryset, named like eh_harbour_queryset.
  3. Paste this and select Run:
let readings = datatable(warehouse_id:string, sensor_id:string, reading_time:datetime, temperature_c:real)
[
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:00), 4.1,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:05), 4.3,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:10), 4.2,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:15), 5.0,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:20), 6.4,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:25), 7.6,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:30), 8.4,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:35), 9.1,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:40), 9.3,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:45), 8.7,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:50), 7.2,
    "WH-02", "WH-02-C1", datetime(2026-10-05 14:55), 5.8
];
readings
| summarize hourly_avg_c = round(avg(temperature_c), 1) by bin(reading_time, 1h);
readings
| where temperature_c > 8
| summarize first_breach = min(reading_time), readings_over_8 = count(), peak_c = max(temperature_c) by sensor_id

You get two results. The first is the batch view: one hourly average of 6.7 °C, comfortably inside the 2 to 8 °C range. The second is the event view: the first breach at 14:30, 4 readings over 8 °C and a peak of 9.3 °C. Same twelve readings, two very different stories. A daily report built on hourly averages would never have flagged that afternoon.

In a real build, an Eventstream would bring the readings in as they happen, the Eventhouse would store them and an Activator rule such as "above 8 °C for five minutes" would message the shift lead. The roadmap step linked below tours those pieces.

If you are on a paid capacity, delete eh_harbour afterwards so it does not keep using capacity.

Common beginner mistakes

  • Calling a faster refresh "real time". A report that refreshes every fifteen minutes is still batch, done more often.
  • Averaging away the event. Aggregates hide short spikes. Keep the raw events and alert on them, as the second query does.
  • Streaming everything because you can. A stream runs all day and uses capacity all day. Stream the few signals that need action.
  • Forgetting time zones. Sensors usually send UTC. 14:30 UTC is 20:00 in India. Say which one a dashboard shows.

On the brewhouse floor

In Brewery A the cellar team takes a gravity sample from each fermenter once a day. That is batch. A daily load is all it needs. The temperature probe on fermenter FV-03 reports every minute. That is a stream worth watching: lager yeast working at 10 °C that drifts to 14 °C for a few hours can leave buttery and fruity off-flavours the brewer cannot remove later. Same tank, two kinds of data, two different builds.
