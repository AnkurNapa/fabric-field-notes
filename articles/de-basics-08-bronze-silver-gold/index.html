Data engineering basics, lesson 8 of 8

Bronze, silver and gold, simply

Lesson 8 of Data engineering basics. Bronze keeps data as it arrived, silver makes it correct and gold makes it ready to report. Build all three for Harbour Goods orders in one short notebook and add it to the daily pipeline.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa LakehouseSpark

Short answer

The medallion pattern stores data in three layers. Bronze is the raw copy, exactly as it arrived. Silver is cleaned and checked: right types, no duplicates, bad rows set aside. Gold is shaped for a specific use, usually totals that a report reads directly. Each layer is built only from the one before it, so when something looks wrong in gold you can walk back to the row in bronze that caused it.

Why it matters for your career

Bronze, silver and gold is the most common layout in lakehouse projects, on Fabric and elsewhere. If you can explain what belongs in each layer and why, you can find your way around almost any team's lakehouse on your first day.

The idea

You have already built bronze: bronze_orders from lesson 5, 60 text rows with five known problems. Here is what each layer does with them:

LayerHarbour Goods tableRuleRows
Bronzebronze_ordersKeep everything as text, exactly as sent60
Silversilver_ordersReal types, duplicates removed, only rows that pass every check55
Quarantinequarantine_ordersFailed rows with a reason, kept for follow-up4
Goldgold_sales_by_region_monthOrders, units and net revenue by region and month12

The numbers add up: 55 clean rows plus 4 quarantined rows plus 1 removed duplicate is 60. Being able to say that sentence is the point of the pattern. Nothing disappears without a reason.

Gold is not "the best data". It is data shaped for one audience. Finance wants revenue by region and month; a stock planner would want a different gold table built from the same silver.

Try it in Fabric

  1. Open lh_harbour and select Open notebook > New notebook. Rename it nb_bronze_to_gold.
  2. Check the Spark runtime under Workspace settings > Spark. Runtime 2.0 became the default in October 2026 and some Learn pages still mention 1.3. Runtime 2.0 is strict about conversions, which is why this code uses try_cast.
  3. Paste each block into its own cell and run them in order. Each starts with %%sql, which tells the notebook the cell is Spark SQL.

The store list, typed in so the lesson needs no extra file:

%%sql
CREATE OR REPLACE TEMPORARY VIEW stores AS
SELECT * FROM VALUES
    ('ST-003', 'Bengaluru', 'South'), ('ST-007', 'Chennai', 'South'),
    ('ST-011', 'Mumbai', 'West'),     ('ST-014', 'Pune', 'West'),
    ('ST-019', 'Delhi', 'North'),     ('ST-022', 'Kolkata', 'East')
AS s(store_id, city, region);

Typed and de-duplicated bronze. DISTINCT removes the repeated HG-40017:

%%sql
CREATE OR REPLACE TEMPORARY VIEW typed_orders AS
SELECT DISTINCT
    order_id,
    try_cast(order_date AS date)          AS order_date,
    store_id,
    product_id,
    try_cast(quantity AS int)             AS quantity,
    try_cast(unit_price AS decimal(10,2)) AS unit_price,
    try_cast(discount AS decimal(4,2))    AS discount
FROM dbo.bronze_orders;

Silver, the rows that pass every check:

%%sql
CREATE OR REPLACE TABLE dbo.silver_orders AS
SELECT t.*,
       CAST(t.quantity * t.unit_price * (1 - t.discount) AS decimal(12,2)) AS net_amount
FROM typed_orders t
WHERE t.order_date IS NOT NULL
  AND t.quantity > 0
  AND t.store_id IN (SELECT store_id FROM stores);

Quarantine, the rows that do not, with a reason:

%%sql
CREATE OR REPLACE TABLE dbo.quarantine_orders AS
SELECT t.*,
       CASE WHEN t.order_date IS NULL THEN 'impossible order date'
            WHEN t.quantity IS NULL   THEN 'missing quantity'
            WHEN t.quantity <= 0      THEN 'quantity zero or below'
            ELSE 'unknown store' END AS reason
FROM typed_orders t
WHERE t.order_date IS NULL
   OR t.quantity IS NULL
   OR t.quantity <= 0
   OR t.store_id NOT IN (SELECT store_id FROM stores);

Gold, revenue by region and month:

%%sql
CREATE OR REPLACE TABLE dbo.gold_sales_by_region_month AS
SELECT s.region,
       date_format(o.order_date, 'yyyy-MM') AS month,
       COUNT(*)                             AS orders,
       SUM(o.quantity)                      AS units,
       SUM(o.net_amount)                    AS net_revenue_inr
FROM dbo.silver_orders o
JOIN stores s ON o.store_id = s.store_id
GROUP BY s.region, date_format(o.order_date, 'yyyy-MM');

Check it worked

%%sql
SELECT region, SUM(orders) AS orders, SUM(net_revenue_inr) AS net_revenue_inr
FROM dbo.gold_sales_by_region_month
GROUP BY region
ORDER BY net_revenue_inr DESC;

Compare that with the 156269.85 the raw view in lesson 3 showed: the 3204.05 difference is exactly the duplicate, the -2 return and the two orders with an unknown store or impossible date. gold_sales_by_region_month should hold 12 rows and quarantine_orders 4.

Finally, make it part of the daily run. Open pl_orders_daily, add a second Notebook activity set to nb_bronze_to_gold and connect it to nb_check_orders with On success. Save. From tomorrow at 06:00 the pipeline copies, checks and then publishes gold.

Common beginner mistakes

  • Cleaning in bronze. Once bronze is edited you have nothing to compare against. Keep it raw.
  • Building gold from bronze. It skips the checks. Gold reads silver only.
  • One gold table for everyone. Gold is per use. Make small, named tables rather than one huge one.
  • Dropping failed rows. Quarantine them. The four rows here are four phone calls, not four deletions.
  • Three lakehouses on day one. For a small project, one lakehouse with clear table names is enough. Split later if access rules need it.

On the brewhouse floor

Brewery A logs a gravity reading for every fermenter each morning. Bronze holds the readings exactly as typed, including the one where FV-03 shows 1012 because someone left out the decimal point. Silver turns them into real numbers, keeps only readings between 0.990 and 1.120 and sends the 1012 to quarantine with a note. Gold gives the head brewer one row per batch: original gravity, latest gravity and the alcohol so far, worked out as (OG minus current gravity) times 131.25. For a batch that started at 1.050 and reads 1.012 today, that is 4.99% ABV. The brewer can trace that figure back to the exact morning reading behind it.
