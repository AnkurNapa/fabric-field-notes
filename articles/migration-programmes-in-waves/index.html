Migration programmes: Synapse, ADF, SSIS and Databricks in waves

A design guide for running a Fabric migration as a programme of waves rather than one big cutover. Which tool moves which workload, what each one leaves behind and the acceptance test that decides when a wave is actually done.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa LakehouseWarehouseSparkGovernance

Short answer

Do not migrate a platform. Migrate workloads, one wave at a time, each with its own tool and its own exit test. Synapse is really three migrations: Spark goes through the Spark Migration Assistant, dedicated SQL pools go through the Fabric Migration Assistant for Data Warehouse and pipelines follow the Data Factory upgrade path. ADF pipelines get assessed and upgraded where they are marked Ready, while the rest keep running in ADF. SSIS packages can run as they are through the Invoke SSIS Package activity, then get rewritten when they earn it. Databricks usually stays where it is and gets mirrored. Move data access first so Fabric can read existing data on day one, then ingestion, then transformation, then models and reports. A wave is finished when consumers have moved and the old thing is switched off, not when objects exist in Fabric.

The decision

Most migration arguments are really one question asked badly: lift and shift or rebuild? The honest answer depends on three things the client already knows: how hard the deadline is, how clean the code is and how much the numbers matter to an auditor.

ApproachPick it whenWhat it costs youWhat it buys you
Lift and shiftHard deadline (a licence or a data centre exit), code is reasonably cleanYou carry today's design debt into FabricSpeed and a short parallel run
Phased modernisationLots of technical debt, no fixed exit dateLonger programme, two platforms billing at onceEach wave lands in a better shape than it left
Parallel runFinancial, regulatory or contractual numbersDouble compute for the run period, a reconciliation process to buildEvidence that the new numbers match the old ones
Coexist and do not migrateThe source works and the team is strong in itTwo platforms to govern for yearsNo migration risk at all for that workload

Reference design

A wave plan for Harbour Goods, the fictional retailer used across this site. Today it runs a Synapse workspace with a dedicated pool holding orders and deliveries, an ADF factory with 140 pipelines, 60 SSIS packages on an old SQL Server for store and product loads and a Databricks workspace the data science team likes.

Wave 0  Foundations          capacity, workspaces, identities, connections,
                             gateways, Git and deployment pipelines
Wave 1  Read before you move shortcuts to the Synapse ADLS account,
                             mirrored Databricks catalog
                             -> Power BI can use Direct Lake on day one
Wave 2  Pilot, end to end    one subject area (deliveries): pipeline, table,
                             model, report, all in Fabric, old path still live
Wave 3  Ingestion            ADF Ready pipelines upgraded; SSIS packages run
                             through Invoke SSIS Package
Wave 4  Warehouse            dedicated pool schema via Migration Assistant,
                             facts via CETAS + COPY INTO, dimensions via copy
Wave 5  Transformation       Synapse notebooks via Spark Migration Assistant,
                             mssparkutils -> notebookutils
Wave 6  Consumers + exit     rebind reports, reroute extracts, parallel run
                             on finance tables, then switch off the source

Two ordering rules drive that shape. First, data access before compute: shortcuts and mirroring let Fabric read the existing lake without moving anything, so reporting can start while the heavy engineering waits. Second, the pilot is a whole vertical slice, not a horizontal layer. A wave that moves every pipeline but no reports proves nothing to the business.

For the big fact tables in the dedicated pool the fastest documented path is to extract in parallel with CETAS to ADLS Gen2, then load with COPY INTO in the Warehouse. The plain copy assistant is fine for dimensions like stores and products, which are small enough that elegance does not matter.

Questions to ask the client

  1. What date forces this? A licence renewal, a data centre lease or nothing? The answer picks the approach in the first table.
  2. Which numbers would an auditor or a board member notice if they moved by one per cent? Those tables get a parallel run.
  3. How many SSIS packages use custom or third-party components, or read from sources inside a private network? Those cannot use the SSIS activity in preview.
  4. Do any ADF pipelines use tumbling window triggers? They need redesign as schedules plus watermark logic.
  5. Is the Synapse workspace inside a managed virtual network? The Spark Migration Assistant cannot migrate those.
  6. Who owns each downstream consumer: reports, extracts, APIs, spreadsheets with live connections? Nobody can decommission what nobody has listed.
  7. Is the Databricks team happy? If yes, mirror and leave them alone.
  8. What does Synapse workspace RBAC look like today? Warehouse grants and masking mostly migrate, but workspace access collapses to four Fabric roles, so that layer is a redesign, not a copy.

Review checklist

  • The Fabric Assessment Tool has been run against the Synapse workspace and the blockers list is in the plan.
  • Capacity Metrics app baseline taken on the target capacity before Wave 2.
  • Every wave has a named acceptance test covering data, security, operations and downstream consumption.
  • Upgraded ADF triggers are noted as arriving disabled, with a named person to re-enable them.
  • SSIS packages saved with DontSaveSensitive have credentials supplied through connection manager overrides.
  • Reconciliation queries exist for every table in a parallel run, with an agreed tolerance.
  • The data sync for the parallel run period is designed before the run starts.
  • A decommission date is in the calendar for each source, triggered by the date, not by someone remembering.

Anti-patterns

  • Big bang cutover. One weekend, everything moves, nothing is reversible. Waves exist so that one bad surprise costs a week, not the programme.
  • Done means created. Objects exist in Fabric, so the wave is marked green. Then a finance extract still points at the dedicated pool for six months. Done means the source is off.
  • Migrating the debt. Lifting a 2,000-line stored procedure into the Warehouse because the assistant converted it. If nobody can explain it, that is a rewrite candidate, not a migration win.
  • Rebuilding the Databricks silver layer in Fabric. Two teams transforming the same data means two compute bills and two answers. Mirror the gold.
  • Security as an afterthought. Synapse roles do not map one to one. Design the workspace and OneLake security model in Wave 0.
  • Decommissioning on a feeling. Switching off the source before every consumer is rerouted is how a store manager finds out first.

On the brewhouse floor

A brewery that bought another brewery inherits its spreadsheets, its SQL Server and its SSIS jobs, the way it inherits the other site's yeast. Brewery A ran its brew logs and packaging counts through packages nobody had opened since the person who wrote them left. The wave approach works there too: run those packages untouched through the SSIS activity first, so the daily brew report keeps arriving, then rewrite the one that calculates excise volume, because that is the number a tax inspector reads. Packaging yield gets a parallel run. The cleaning schedule export does not.
