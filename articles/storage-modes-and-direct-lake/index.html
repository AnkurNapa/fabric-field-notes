Import, DirectQuery, composite and Direct Lake: the four storage modes

A semantic model can copy data in, ask the source every time, mix the two or read Delta tables in OneLake straight into memory. Here is what each mode does, when it fits and the one difference between the two Direct Lake flavours that decides whether a broken table errors or quietly slows down.

Ankur Napa 11 Oct 2026, 5 min read

Short answer

Storage mode is a property of each table in a semantic model. It decides where a visual's data comes from when someone opens a report.

  • Import copies the data into the model. Fast to query, as fresh as the last refresh.
  • DirectQuery copies nothing. Every visual sends a query to the source. Fresh, but only as fast as the source.
  • Composite is a model that mixes modes, for example a large DirectQuery fact table with small Import dimensions.
  • Direct Lake reads Delta tables in OneLake into memory on demand. Import speed without copying the data on a schedule. It needs a Fabric capacity and comes in two flavours: on OneLake and on SQL.

For a new model over Fabric Delta tables, Microsoft recommends Direct Lake on OneLake. Import is still right for non-Fabric sources, Pro-only workspaces and incremental refresh. DirectQuery is right when the source must be live and can carry the load.

Read the "how it stays fresh" row against a real morning. Harbour Goods runs its Import sales model at 06:00. The overnight orders from the late shift at store ST-014 finish loading into the lakehouse at 06:20. The regional manager opens the report at 08:00 and ST-014 looks like it had a terrible night. It did not; the model is two hours behind the lake. With Direct Lake the model reframes when the Delta table changes, so the 08:00 view shows the 06:20 load. Nobody scheduled anything.

A ten-minute tour

You need a workspace on a Fabric capacity or a trial, with at least one semantic model. Building one from a lakehouse takes two minutes if you have none: in the lakehouse ribbon select New semantic model, pick a table or two and confirm (the button may read Confirm or Create).

  1. Find the mode of each table. Open the semantic model and switch to the model view. Select a table and look in the Properties pane for Storage mode (in Power BI Desktop it sits under Advanced). A model built from the lakehouse ribbon shows Direct Lake.
  2. Tell the two Direct Lake flavours apart. In Power BI Desktop or the TMDL view, look at the model's data source expression. A Direct Lake on SQL model points at a SQL analytics endpoint (by GUID). Direct Lake on OneLake points at the Fabric item itself. If you cannot tell, ask whoever built it before the first incident, not after.
  3. Open the refresh settings. In the workspace select the model's ... > Settings and expand the refresh section. A Direct Lake model shows Keep your Direct Lake data up to date, on by default. An Import model shows a refresh schedule with time slots.
  4. Compare with an Import model. If you have one, open its refresh history. Note how long a refresh takes. A Direct Lake framing usually finishes in seconds because it copies metadata, not rows.
  5. Check the capacity size. Direct Lake has per-SKU guardrails. On F2 to F32 a table can hold 300 million rows; on F64 it is 1,500 million. Your workspace settings show which capacity you are on.

What people get wrong

  • "Direct Lake always falls back to DirectQuery." Only Direct Lake on SQL does. Direct Lake on OneLake has no fallback: when a table exceeds a guardrail or a source view is not a Delta table, queries return an error. That is often the better behaviour, because a silent fallback turns a two-second visual into a twenty-second one and nobody knows why.
  • "Direct Lake means no refresh." It means no data copy. Framing still happens, automatically by default. If an automatic update hits a non-recoverable error, Power BI suspends automatic updates until an on-demand refresh succeeds.
  • "Import is legacy." Import is still the right mode for sources outside Fabric, for Pro-only workspaces and for features Direct Lake does not have, such as incremental refresh, hybrid tables and user-defined aggregations.
  • "DirectQuery is the real-time option." It is the live option. Whether it feels real time depends on how fast the source answers a burst of report queries. A busy transactional database rarely enjoys it.
  • "Deployment rules will rebind it." Deployment pipeline rules can rebind a Direct Lake on SQL model to another endpoint. They do not work for Direct Lake on OneLake.

On the brewhouse floor

A brewery's packaging line finishes a run at 06:20 and the counts land in the lakehouse. The production manager opens the yield report at 08:00. With an Import model refreshed at 06:00, that run is missing and the day looks short by a whole batch of kegs. With Direct Lake the model picks up the new rows on its own and the report matches what the line actually packed. Same problem as the late store orders, same fix.
