A star schema that behaves: modelling retail sales

Split one flat sales extract into an orders fact, two dimensions and a proper date table in Power BI Desktop, wire them one-to-many with single-direction filters, then prove the model with numbers you can check by hand.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 1 Ankur Napa Power BI

Short answer

Put the numbers you add up in one table (the fact) and the words you slice by in small tables around it (the dimensions). Join each dimension to the fact on a key that is unique on the dimension side. Set every relationship to many-to-one with a single cross filter direction, add one date table and mark it as the date table. That shape is called a star schema and it is what the Power BI engine is built for. Most "the total is wrong" tickets come from skipping one of those steps, usually the unique key.

What you will build

Harbour Goods is a fictional mid-size retailer with eight stores across India. Its order system exports one flat file with everything on every row: order, store, city, product, category and price. You will turn it into this:

TableRoleRowsOne row perJoins to orders on
ordersFact110Order line, January 2025 to September 2026
productsDimension9Product: name, category, unit costproduct_id
storesDimension8Store: city, region, opening datestore_id
DateDimension731Day in 2025 and 2026order_date

Picture orders in the middle with the other three around it, each joined by one line. That is the star.

Then three measures and a page that proves the filters flow the way you think.

Before you start

  • Power BI Desktop, recent build. Everything here also works in a Fabric workspace later, but Desktop is the cleanest place to learn modelling.
  • The sample file: star-schema-that-behaves.csv. It is synthetic, 110 rows. Prices are in INR.
  • Ten minutes of patience for Power Query. The modelling itself is quick.

Step 1: load the flat file

  1. In Power BI Desktop select Get data > Text/CSV and pick the file.
  2. In the preview select Transform Data, not Load. You want Power Query open.
  3. Rename the query to orders_raw.
  4. Check the column types in the header icons: order_date as Date, opened as Date, quantity as Whole Number, unit_price, unit_cost and discount as Decimal Number. Fix any that came in as text.

Step 2: turn off Auto date/time

Before anything else, go to File > Options and settings > Options > Current File > Data Load and clear Auto date/time under Time intelligence. Left on, Desktop builds a hidden date table for every date column in the model. That bloats the file and those hidden tables cannot be shared across facts. You will build one real date table instead.

Step 3: split out the dimensions

Each dimension is a reference to the raw query, cut down to its own columns, with duplicates removed.

  1. Right-click orders_raw in the Queries pane and select Reference. Rename the new query products.
  2. Select Home > Choose Columns and keep product_id, name, category and unit_cost.
  3. Select Home > Remove Rows > Remove Duplicates.
  4. Repeat for stores: reference orders_raw, keep store_id, city, region and opened, then remove duplicates.
  5. Reference orders_raw once more and name it orders. Keep order_id, order_date, store_id, product_id, quantity, unit_price and discount.
  6. Right-click orders_raw and clear Enable load. It feeds the other three but should not land in the model itself.
  7. Select Close & Apply.

Notice where unit_price went. It stays on the fact because the price is part of the sale and could change from one order to the next. unit_cost belongs to the product. Deciding which side a column lives on is most of the modelling job.

Step 4: build and mark the date table

Select Modeling > New table and paste:

Date =
ADDCOLUMNS (
    CALENDAR ( DATE ( 2025, 1, 1 ), DATE ( 2026, 12, 31 ) ),
    "Year", YEAR ( [Date] ),
    "Year month", YEAR ( [Date] ) * 100 + MONTH ( [Date] ),
    "Month", FORMAT ( [Date], "mmm yyyy" )
)

Then:

  1. Select the Month column. Under Column tools, set Sort by column to Year month. Without this, April sorts before January.
  2. Select the Date table, then Table tools > Mark as date table and choose the Date column.

The table covers whole calendar years, even though the data stops in September 2026. Time intelligence functions expect full years with no gaps.

Step 5: relationships

Open Model view. Desktop may already have guessed two relationships from matching column names. Check them anyway in Modeling > Manage relationships.

You want exactly three:

From (many)To (one)CardinalityCross filter direction
orders[product_id]products[product_id]Many to oneSingle
orders[store_id]stores[store_id]Many to oneSingle
orders[order_date]Date[Date]Many to oneSingle

To add a missing one, drag the fact column onto the dimension column in Model view, or use Manage relationships > New. If Desktop offers Both for cross filter direction, change it to Single. Both feels helpful because slicers start filtering each other. It also creates more than one path between tables and the engine then picks a path you did not choose. If one measure truly needs the other direction, turn it on inside that measure with CROSSFILTER, not on the relationship.

Finally, hide the key columns on the fact (product_id, store_id, order_date) so report authors slice by the dimension columns instead. Right-click each and select Hide in report view.

Step 6: three measures

Select the orders table, then New measure for each.

Net sales =
SUMX ( orders, orders[quantity] * orders[unit_price] * ( 1 - orders[discount] ) )
Units = SUM ( orders[quantity] )
Products sold = DISTINCTCOUNT ( orders[product_id] )

The fact stores quantity, price and discount, the additive base values. The line amount is computed in the measure. A stored percentage or margin would not add up across rows.

Step 7: a proof page

Build one report page:

  • Three cards: Net sales, Units, Products sold.
  • A table with stores[region], Net sales and Products sold.
  • A clustered column chart of Net sales by Date[Month].

Check it worked

In Table view the row counts should read 110 for orders, 9 for products, 8 for stores and 731 for Date. If products shows more than 9 rows, the same product came through with two spellings or two costs. Fix that before you trust a single total.

The cards:

  • Net sales: 995,654.70
  • Units: 741
  • Products sold: 9

The region table:

RegionNet salesProducts sold
East84,098.106
North164,567.359
South451,352.809
West295,636.459

By category, Outdoor leads at 452,275.80, then Home at 284,444.30 and Kitchen at 258,934.60.

Now the test that shows you understand the filter direction. Add a quick measure Product count = COUNTROWS ( products ) and drop it into the region table. It shows 9 on every row, East included. The region filter flows from stores to orders, but it never flows out of orders into products, because that relationship is single direction. Products sold counts over the fact, so it does answer "how many products did East actually sell": six. Count over the fact when the question is about activity. Count over the dimension when the question is about the catalogue.

Where this breaks

  • A duplicate key on the one side. If a product arrives twice with different costs, Remove Duplicates keeps both rows because they are not identical. Desktop then either refuses the relationship ("One of the columns must have unique values") or quietly suggests many-to-many. Fix the source, or pick one row per key in Power Query.
  • Bidirectional relationships to make a slicer behave. It works on day one and causes ambiguous paths on day ninety when a second fact arrives.
  • Joining on text. City names are not keys. "Bengaluru" and "Bangalore" are the same store and two different rows.
  • Mixed grain. If the source adds a delivery charge per order, do not put it on every order line or it will be counted once per line. Allocate it down to the lines or keep it in its own fact.
  • Auto date/time left on. You get a date hierarchy that looks fine and a model twice the size it should be.

On the brewhouse floor

A brewery's sales export looks like this file: every invoice line repeats the beer name, the style, the pub and the town. Split it the same way. Invoice lines become the fact with litres sold and price, beers become one dimension with style and strength, outlets become another with town and channel. The date table is identical. The first time someone asks how many beers a pub actually stocked last quarter, you count over the fact, not the beer list, for exactly the reason East showed six products and not nine.
