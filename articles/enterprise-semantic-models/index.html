Enterprise semantic models: XMLA, TMDL and incremental refresh

A nightly Import refresh that reloads 40 months of orders to change three. Measure what each refresh reads, move the fact table to an incremental refresh policy, manage it through the XMLA endpoint and put the model under source control as TMDL.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa Power BICI/CDCapacity

Short answer

An Import model that reloads its whole fact table every night is paying for history that has not changed. Give the fact table an incremental refresh policy so only the most recent months reload. Switch the model to the large semantic model storage format and turn the capacity's XMLA endpoint to read-write so you can see and refresh partitions. Then save the model as a Power BI Project in TMDL so every change is a readable diff in Git. On the sample data below the nightly refresh reads 88.8 per cent fewer rows. The catch is the edits that land after the window has moved on. Plan for those before you celebrate.

The symptom

Harbour Goods, the fictional retailer used across this site, has an Import semantic model called sm_harbour_sales. Its orders fact table pulls from an ERP read replica and holds every order line since June 2023. The model does three things badly:

  • The nightly refresh takes 62 minutes and has started to collide with the morning store reports.
  • Twice last quarter it timed out when the replica was slow.
  • The model lives as a .pbix on one analyst's laptop. Nobody can review a change to a measure before it ships, because a .pbix diff is a binary blob.

None of this is a capacity problem yet. It is a model that does the same work every night whether or not anything changed.

Measure it

The sample file enterprise-semantic-models.csv holds 40 rows: order lines per month from June 2023 to September 2026, plus a count of rows edited more than 90 days after their month. It is synthetic and stands in for what you would pull from the source with a GROUP BY on order month.

1. What a refresh reads today. Sum order_rows: 2,478,090 rows, every night. Open the model's Refresh history in the workspace (from the model's settings or the ... menu). This model shows 62 minutes, so the source delivers roughly 40,000 rows a minute. Write that rate down. It is the number that turns rows into minutes later.

2. What actually changed. The three most recent months hold 276,480 rows: 95,180 in July, 96,190 in August and 85,110 in September 2026. Everything older is closed. The rows_edited_after_90_days column adds up to 1,679 rows across the first 37 months. Those are returns, credit notes and corrected discounts keyed against old orders. Keep that figure; it comes back in "Where this breaks".

3. How the model is partitioned now. You need the XMLA endpoint for this. Copy the workspace connection string from Workspace settings (the label may read License info or Premium, then Workspace connection). It looks like powerbi://api.powerbi.com/v1.0/myorg/Harbour%20Sales. Connect from SQL Server Management Studio, or open DAX query view on the model and run:

EVALUATE
SELECTCOLUMNS (
    INFO.PARTITIONS (),
    "Partition", [Name],
    "Mode", [Mode],
    "Refreshed", [RefreshedTime]
)

Today the orders table has one partition. One partition means one way to refresh it: all of it.

Fix it

Step 1: turn on XMLA read-write and large format

A capacity admin goes to OneLake catalog > Govern > Capacities, selects the capacity, expands Workloads (some tenants still show Power BI Workloads) and sets XMLA Endpoint to Read Write. It applies to every workspace on that capacity, which is why you do it on the dev and test capacity freely and lock production writes to your deployment identity. The tenant setting Allow XMLA endpoints and Analyze in Excel with on-premises semantic models must also be on.

Then, in the semantic model settings, turn on Large semantic model storage format. Without it the model is capped at 10 GB and the XMLA writes you are about to do are slower.

Step 2: add the incremental refresh policy

In Power BI Desktop, open Power Query and create two parameters named exactly RangeStart and RangeEnd, both of type Date/Time. Filter the source query on them, with an equals sign on one boundary only:

let
    Source = Sql.Database("erp-replica.harbourgoods.example", "sales"),
    Orders = Source{[Schema = "dbo", Item = "orders"]}[Data],
    InRange = Table.SelectRows(
        Orders,
        each [order_ts] >= RangeStart and [order_ts] < RangeEnd
    )
in
    InRange

>= on one side and < on the other is not style. If both sides carry the equals sign, an order stamped exactly on a boundary lands in two partitions and your totals double count it.

Right-click orders in the Data pane, select Incremental refresh and set:

  • Archive data starting 4 years before refresh date, so all 40 months stay in the model.
  • Incrementally refresh data starting 3 months before refresh date.
  • Only refresh complete days on, because the replica lags by a few hours.

Before you publish, confirm the filter folds. Right-click the last step and choose View Native Query. If it is greyed out, the filter runs in the mashup engine after the whole table has been pulled. Incremental refresh then saves you nothing.

Step 3: publish once, then stop using Desktop to publish

Publish and run the first refresh. That refresh is a full load: it builds the partitions and fills them. Expect it to take as long as the old one. Run INFO.PARTITIONS() again and you will see a mix of year, quarter and month partitions for orders instead of one.

From here on, do not republish the model from Desktop. Once the service owns the partitions, a model changed through XMLA cannot be downloaded back as a .pbix. Pushing a fresh copy from Desktop throws the policy's partitions away. Schema changes go through a metadata-only deployment instead: Tabular Editor or the ALM Toolkit over XMLA, or Git integration.

Step 4: put the model under source control as TMDL

In Desktop, choose File > Save as and pick Power BI Project (.pbip). With the TMDL format enabled, Desktop writes a sm_harbour_sales.SemanticModel folder with a definition folder inside, one .tmdl file per table plus a .gitignore that excludes cache.abf and localSettings.json. Commit that folder to Azure DevOps or GitHub. Now a measure change reads like this in a pull request:

	measure 'Net sales' = SUM ( orders[net_amount] )
		formatString: #,##0.00
		displayFolder: Sales

Deploy from the repository with Fabric Git integration or fabric-cicd. Both ship metadata only, so trigger a refresh after a deployment that adds a column.

Prove it

Run the scheduled refresh the next night, then compare.

BeforeAfter
Rows read by the nightly refresh2,478,090276,480
Partitions on orders1Year, quarter and month partitions
Refresh duration at about 40,000 rows a minute62 minutesAbout 7 minutes
Refreshes a day through XMLA or the enhanced refresh APICapped at 48 from the service scheduleNot capped
Reviewing a measure changeOpen two .pbix files side by sideRead a TMDL diff

The 7 minutes is 276,480 rows at the rate you measured in step 1, so treat it as the target rather than a promise. If the real figure is far above it, the filter is not folding.

Where this breaks

  • Late edits outside the window. The 1,679 rows edited more than 90 days after their month sit in partitions the nightly refresh no longer touches. The model quietly disagrees with the ERP. Schedule a monthly TMSL refresh of the older partitions through XMLA, or widen the window if the source can bear it. Detect data changes helps only if the source has a reliable last-modified column. It never sees hard deletes.
  • A filter that does not fold. A native SQL query, a merge with a local file or a type change Power Query cannot translate breaks folding. Each partition then pulls the whole table and filters it locally. The refresh gets slower than before, not faster.
  • The Desktop republish. One analyst publishing the old .pbix over the model resets the partitions and forces another full load. Remove publish rights in production and deploy only from the repository.
  • Direct Lake does not use this. Direct Lake tables have no model partitions. A refresh there is framing, a metadata pass over the Delta table. If your fact table already lands in OneLake as Delta, partition the Delta table instead and skip incremental refresh entirely.
  • Refresh near half the capacity memory. A full refresh holds the old and new copies in memory at once. On a large model, refresh by table or partition through the enhanced refresh API rather than the whole model.

On the brewhouse floor

Brewery A keeps five years of fermentation readings in an Import model: gravity and temperature for every tank, every few hours. The nightly refresh reloaded all of it to add yesterday. An incremental policy on the readings table refreshes the last three months and leaves closed batches alone. The late edit there is the lab result keyed in after a batch of lager was already released from FV-03, so the monthly back refresh is not optional. It is how the quality record stays honest.
