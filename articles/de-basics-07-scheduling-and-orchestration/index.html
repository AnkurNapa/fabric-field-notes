Data engineering basics, lesson 7 of 8

Scheduling and orchestration

Lesson 7 of Data engineering basics. Scheduling decides when work runs; orchestration decides what runs in what order and what happens on failure. Add a quality gate, a retry and a 06:00 schedule to the Harbour Goods pipeline.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa LakehouseSpark

Short answer

Scheduling answers "when": run this pipeline at 06:00 every day. Orchestration answers "in what order and what if": copy first, check quality only if the copy worked, retry a flaky step, tell someone when it fails. In Fabric both live in the pipeline. You connect activities with On success, On failure, On completion and On skip paths, set retries on each activity and add one or more schedules from the Home tab.

Why it matters for your career

Anyone can run a job by hand once. The engineer who builds the job that runs itself at 06:00, stops safely when the data is bad and wakes the right person is the one teams keep. Most production incidents are orchestration problems, not code problems.

The idea

IdeaPlain meaningHarbour Goods example
ScheduleA timetable that starts a runDaily at 06:00 India time
DependencyStep B waits for step ACheck quality only after the copy succeeds
RetryTry a failed step again before giving upCopy retries twice, a minute apart
GateA step that fails on purpose when data is badStop if more than 10% of rows are bad
AlertTell a person when a run failsEmail the data team

The coloured lines on the pipeline canvas are dependencies. Green is On success, red is On failure, blue is On completion (run whatever happened) and grey is On skip.

A gate is the bridge between lesson 6 and a real pipeline. Fabric also has a Fail activity for this, used with an If Condition; a notebook that raises an error is the simpler start. The checks you wrote become a step that raises an error when the data is too bad to publish. The pipeline then stops before bad numbers reach a report.

Try it in Fabric

You will extend pl_orders_daily from lesson 5 to: copy, then gate, on a schedule.

1. Build the gate notebook

  1. Open lh_harbour. On the ribbon select Open notebook > New notebook. The notebook opens with lh_harbour attached as its default lakehouse. Rename it nb_check_orders.
  2. Paste this into the first cell and select Run:
# Quality gate for the daily Harbour Goods orders run
MAX_BAD_SHARE = 0.10  # stop the pipeline if more than 10% of rows are bad

row = spark.sql("""
    SELECT
        COUNT(*) AS total_rows,
        SUM(CASE WHEN try_cast(quantity AS int) IS NULL
                   OR try_cast(quantity AS int) <= 0
                   OR try_cast(order_date AS date) IS NULL
                 THEN 1 ELSE 0 END) AS bad_rows
    FROM dbo.bronze_orders
""").first()

total, bad = row["total_rows"], row["bad_rows"]
print(f"{bad} of {total} rows failed the checks")

if total == 0 or bad / total > MAX_BAD_SHARE:
    raise ValueError(f"Quality gate failed: {bad} of {total} rows are bad")

Expected output: 3 of 60 rows failed the checks. The three are the blank quantity, the quantity of -2 and the impossible date. That is 5%, under the 10% threshold, so the cell finishes without an error. In Spark, try_cast turns a blank or impossible value into NULL instead of failing, which matters because Fabric's newer Spark runtime is strict about bad conversions.

2. Chain it after the copy

  1. Open pl_orders_daily. On the Activities tab select Notebook. A Notebook activity appears on the canvas.
  2. With it selected, open the Settings tab and pick nb_check_orders in the Notebook list.
  3. Hover over the Copy activity, drag from its On success handle (the green tick) and drop it on the Notebook activity.
  4. Select the Copy activity, open the General tab, tick Enable retries, set Retry to 2 and Retry interval (sec) to 60.
  5. Select Save, then Run. In the Output tab both activities should show Succeeded.

3. Schedule it

  1. On the Home tab select Schedule > Add schedule.
  2. Choose a daily repeat at 06:00 and pick the India time zone, shown as UTC+05:30.
  3. Set a start date of today. An end date is required, so set one far ahead, such as 1 January 2099.
  4. Under Failure notifications add yourself.
  5. Select Save. The next run time appears in the schedule pane.

4. Prove the gate works

Change MAX_BAD_SHARE to 0.01 in the notebook, save and run the pipeline again. The copy succeeds, the notebook raises the error and the pipeline shows Failed. Select the failed activity in Output to read the message. Set the threshold back to 0.10 and save. Failure emails go out only for scheduled runs, not runs you start by hand.

Common beginner mistakes

  • Scheduling every activity separately. Two schedules at 06:00 and 06:05 work until the copy takes six minutes. Chain them in one pipeline.
  • Retrying everything forever. Retries help with a network blip. They do not fix a wrong password; that fails three times more slowly.
  • Nobody on the failure list. A schedule with no notification fails silently. You find out from an angry email.
  • Forgetting whose identity runs it. A notebook in a scheduled pipeline runs with the permissions of the person who last changed the pipeline or schedule. If they leave, the run can start failing.
  • Mixing up time zones. The schedule's time zone is the one you pick, not the one on your laptop.

On the brewhouse floor

At harvest, Winery A's weighbridge writes a file for every truck of grapes: grower, block, tonnes and sugar level in degrees Brix. During vintage those files pile up through the night. A pipeline scheduled for 05:00 can copy them, then gate on a simple rule such as "Brix between 15 and 30" before the morning crush plan is built. A reading of 2.4 is almost certainly 24 with a missing digit. The winemaker would rather get an email at 05:05 than plan the day's pressing around it.
