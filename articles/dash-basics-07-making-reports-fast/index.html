Making reports fast: Performance Analyzer and Direct Lake basics

A slow page is usually too many visuals, a heavy measure or a model that is not doing what you think. Use Performance Analyzer in the browser to see which. Then learn what Direct Lake does on the first and second view of a page.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa Power BIDirect Lake

Short answer

Measure before you change anything. Performance Analyzer records how long each visual on a page takes and splits the time into the query and the drawing. It runs in the Fabric service: open the report, select Edit, then View > Performance Analyzer. Most slow pages are fixed by fewer visuals, tables limited to the top rows people actually read and simpler measures. On a Direct Lake model, the first view after new data lands is slower than the second, because the columns it needs are loaded into memory on demand.

Why it matters for your career

People forgive an ugly report sooner than a slow one. Being able to say "this visual takes four seconds and here is why" instead of "Power BI is slow" is the difference between a report builder and someone teams call when things break.

The idea

Every visual on a page sends its own query to the semantic model when the page opens and again when you click a slicer. Performance Analyzer shows each one:

Line in the paneWhat it measuresIf it is big
DAX queryTime for the model to answer the visual's querySimplify the measure or the model
Direct queryTime for an external source to answer (DirectQuery only)You are not getting Direct Lake or Import speed
Visual displayTime to draw on screenToo many points, heavy custom visual, maps
OtherWaiting for other visuals, preparing queriesToo many visuals on the page

Direct Lake in two sentences. Your model reads the Delta tables in the lakehouse directly; there is no copy into the model and no import refresh to schedule. When new data lands, the model takes a quick metadata step called framing, then loads only the columns a query needs into memory the first time someone asks for them.

So with Direct Lake, "cold" (first view after new data) and "warm" (second view) timings differ. Both are normal. A model built from the lakehouse ribbon, as in lesson 1, is Direct Lake on OneLake. It has no DirectQuery fallback: a table that breaks a Direct Lake rule makes queries error rather than run slowly. A Direct Lake on SQL model falls back to DirectQuery instead. Seeing a Direct query line in Performance Analyzer on a Direct Lake model is a sign it has fallen back.

Fixes in order of effort:

FixWhy it works
Fewer visuals per pageEach visual is a query; Microsoft recommends only what is needed
One multi-value card instead of five cardsOne query instead of five
Top N on big tablesNobody reads 100,000 rows; set the visual to the top 1,000
Detail on drillthrough and tooltip pagesDetail loads only when asked for
Simpler measuresHeavy row-by-row logic shows in DAX query time

Try it in Fabric

Open rpt_harbour_sales from the workspace.

  1. Select Edit, then on the View menu select Performance Analyzer. The pane opens to the right of the canvas.
  2. Select Start recording, then Refresh visuals in the pane.
  3. Expand each visual's entry and note its DAX query, Visual display and Other times. Write down the total for the slowest one.
  4. Select Refresh visuals again and compare. The second run is usually faster, partly because data is already in memory.
  5. Select 2026-09 in the month slicer. A new section appears, labelled as a slicer change, with a fresh set of timings.
  6. On the matrix entry select Copy query. That is the DAX query the visual sent. You can paste it into DAX query view (Open data model, then DAX query view) to run it on its own.
  7. Select Stop. Export saves the timings as a JSON file if you want to compare later.

Check it worked: with 96 orders every visual should finish in well under a second and none should show a Direct query line. Exact milliseconds vary by capacity and time of day, so record your own as the baseline. Then add five more card visuals and refresh: Other time climbs as visuals queue for their turn, even on a tiny model.

Common beginner mistakes

  • Guessing. Changing the measure, the model and the visuals at once means you never learn which one mattered.
  • Testing only warm. Users opening the report first thing after the overnight load see the cold time. Measure both.
  • Blaming the capacity first. Check the page and the measure before asking for a bigger capacity. If the whole capacity is busy, the Capacity Metrics app shows it.
  • Huge default tables. An unfiltered table visual over millions of rows is the classic slow page. Microsoft's optimisation guide calls this out by name.
  • Desktop timings as truth. Your laptop is not the service. Measure where users actually open the report.

On the brewhouse floor

Brewery A put every temperature reading from FV-01 to FV-08, one every minute for a year, on a single line chart on the cellar page. It took twelve seconds to open. The cellar team stopped using it. Performance Analyzer showed nearly all of it was visual display: four million points nobody could see. Showing the last 72 hours per tank, with the history on a drillthrough page, brought it under two seconds. The brewers wanted to know whether FV-03 was holding at 12 °C now, not what it did last March.
