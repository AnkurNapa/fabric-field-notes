Your first notebook: clean messy order data with PySpark

Read a messy orders export from a lakehouse table, fix the types, drop duplicate lines, work out revenue and margin, then write a clean silver Delta table and check it with Spark SQL.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 1 Ankur Napa SparkLakehouse

Short answer

Open a notebook from the lakehouse and read the raw table with spark.read.table. Cast every column on purpose with try_cast so a bad value becomes a null instead of a crash. Drop duplicates on the natural key, derive revenue and margin with column expressions and write the result with saveAsTable into a silver schema. Then prove it with three Spark SQL checks: row count, no duplicate keys and the totals per store. On Runtime 2.0, the default since 6 October 2026, try_cast matters more than it used to.

What you will build

A notebook called nb_clean_orders that turns dbo.orders_raw into silver.orders: one row per order, typed, deduplicated, with revenue, cost, margin and margin percentage worked out from the quantity, price, discount and unit cost.

The sample is two weeks of synthetic orders from the six Harbour Goods stores, 1 to 14 September 2026, exported from the till system with the unit cost at the time of sale. It has the faults a real export has. Six orders were sent twice. Two quantity cells say n/a. One price arrived as INR 1299.00 instead of a number. One discount is blank and one store code has stray spaces round it. Download it here: first-notebook-clean-orders-pyspark.csv.

The duplicates are the detail I care about. A till does not know whether its last upload landed, so on a morning when the store's connection drops it sends the batch again. The data is not wrong. It is honest about a flaky network. The silver layer is where you deal with that once instead of in every report.

Which tool for this job

Roadmap step eng-1-2 asks you to choose an ingestion tool. The short version for this case: the file is already in OneLake, so no shortcut, mirroring or copy job is needed to land it. Load to tables gets it into Delta. The cleaning has rules a finance team can name (what counts as a duplicate, what a blank discount means, how margin is worked out), which is code, so a notebook. A Dataflow Gen2 would work for the casting, but the rules read better as code and live happily in Git.

Before you start

  • A workspace on a Fabric capacity or trial, with Contributor or higher. Notebooks are Fabric items, so Users can create Fabric items must be on in the tenant.
  • The lakehouse lh_sales from the first lakehouse walkthrough, with Lakehouse schemas on.
  • Check the runtime: Workspace settings > Data Engineering/Science > Spark settings > Environment > Runtime version. This walkthrough assumes 2.0 (Spark 4.1, Delta 4.2). The code also runs on 1.3.

Steps

1. Land the raw file as a table

  1. In lh_sales, select Get data > Upload files and upload the CSV.
  2. In Files, select ... next to it > Load to tables > New table.
  3. Schema dbo, New table name orders_raw, Column header ticked. Select Load.

Load to tables infers types. Because of the n/a cells and the INR prefix, quantity and unit_price will most likely come through as text. That is the point of the next steps.

2. Create the notebook

  1. In the lakehouse ribbon select Open notebook > New notebook. The notebook opens with lh_sales attached and pinned as the default lakehouse.
  2. Rename it nb_clean_orders from the name at the top left.
  3. Leave the language as PySpark (Python).

The first cell takes a little while because the Spark session starts on first run.

3. Read the raw table

from pyspark.sql import functions as F

raw = spark.read.table("dbo.orders_raw")
print(raw.count())   # expect 70
raw.printSchema()

4. Fix the types

Cast every column on purpose. try_cast returns null where plain CAST would throw under ANSI mode.

def as_text(c):
    return F.trim(F.col(c).cast("string"))

def as_number(c, sql_type):
    # keep digits, the decimal point and a minus sign; 'INR 1299.00' becomes '1299.00'
    return F.expr(
        f"try_cast(regexp_replace(cast({c} AS STRING), '[^0-9.-]', '') AS {sql_type})"
    )

typed = raw.select(
    as_text("order_id").alias("order_id"),
    F.expr("try_cast(trim(cast(order_date AS STRING)) AS DATE)").alias("order_date"),
    as_text("store_id").alias("store_id"),
    as_text("product_id").alias("product_id"),
    as_number("quantity", "INT").alias("quantity"),
    as_number("unit_price", "DECIMAL(10,2)").alias("unit_price"),
    F.coalesce(as_number("discount", "DECIMAL(4,2)"), F.lit(0).cast("decimal(4,2)")).alias("discount"),
    as_number("unit_cost", "DECIMAL(10,2)").alias("unit_cost"),
)

Casting through a string covers both cases: Load to tables leaving a column as text or inferring it as a number already. The blank discount becomes zero on purpose. That is a business rule, so write it down where the team can see it: a missing discount at this retailer means no discount, not an unknown one.

5. Drop bad rows and duplicates

clean = (
    typed
    .where("order_id IS NOT NULL AND order_date IS NOT NULL")
    .where("quantity IS NOT NULL AND quantity > 0")          # the n/a lines
    .where("unit_price > 0 AND discount >= 0 AND discount < 1")
    .dropDuplicates(["order_id"])
)
print(clean.count())   # expect 62

The key is the order id, not the whole row. Two uploads of the same order are one order, even if the second copy arrived with different spacing. The trim in step 4 already fixed the padded store code, so that row survives.

6. Derive revenue and margin

Revenue is quantity times unit price times one minus the discount. Cost is quantity times unit cost. Margin is revenue minus cost. Margin percentage is margin over revenue.

revenue = F.col("quantity") * F.col("unit_price") * (F.lit(1) - F.col("discount"))
cost = F.col("quantity") * F.col("unit_cost")

silver = clean.select(
    "order_id", "order_date", "store_id", "product_id",
    "quantity", "unit_price", "discount", "unit_cost",
    F.round(revenue, 2).alias("revenue"),
    F.round(cost, 2).alias("cost"),
    F.round(revenue - cost, 2).alias("margin"),
    F.round((revenue - cost) / revenue * 100, 1).alias("margin_pct"),
    F.current_timestamp().alias("processed_at"),
)

Money stays in DECIMAL, not DOUBLE. A double cannot hold 0.1 exactly and a finance team will notice the paisa that goes missing over a year of rows.

7. Write the silver table

spark.sql("CREATE SCHEMA IF NOT EXISTS silver")

(silver.write
    .mode("overwrite")
    .option("overwriteSchema", "true")
    .saveAsTable("silver.orders"))

Refresh the lakehouse Explorer and orders appears under Tables > silver. Overwrite keeps this first version simple and safe to rerun. Incremental loads come later on the roadmap.

8. Check it with Spark SQL

Add a cell and start it with the %%sql magic:

%%sql
SELECT store_id,
       COUNT(*)                                   AS orders,
       SUM(revenue)                               AS revenue,
       SUM(margin)                                AS margin,
       ROUND(SUM(margin) / SUM(revenue) * 100, 1) AS margin_pct
FROM silver.orders
GROUP BY store_id
ORDER BY store_id;

Check it worked

First the guard rails, in Python so the cell fails loudly if anything drifts:

n = spark.table("silver.orders").count()
dupes = spark.sql("""
    SELECT COUNT(*) - COUNT(DISTINCT order_id)
    FROM silver.orders
""").first()[0]
assert n == 62 and dupes == 0, (n, dupes)
print("silver.orders OK:", n, "rows")

Then the step 8 query should return six rows, one per store, matching this:

Across all stores that is 62 orders, revenue of 259,655.40 rupees and a margin of 103,495.40, or 39.9 per cent. ST-007 sitting near 36 per cent while ST-003 makes 42 is what you would expect from a store selling more pressure cookers and speakers, which carry thin margins. If a store showed 20 per cent, that is a conversation with the store manager about discounts, not a data problem.

Where this breaks

  • ANSI mode on Spark 4. Runtime 2.0 runs Spark 4.1, where upstream Spark turns ANSI mode on by default. CAST('n/a' AS INT) then fails the whole job instead of returning null. Use try_cast and the other try_ functions. Setting spark.sql.ansi.enabled to false works as a stopgap but hides bad data.
  • The runtime changed under you. Runtime 2.0 became the default on 6 October 2026 for workspaces that never pinned one. If a notebook that ran last week fails today, check Spark settings before the code. Pin the runtime in the workspace or an Environment item.
  • Spark SQL reads the default lakehouse. Two-part names such as silver.orders resolve against the pinned default lakehouse. Attach a second lakehouse and forget to move the pin and your %%sql cell reads the wrong place.
  • Schema drift on overwrite. Without overwriteSchema a rerun that changes a column type fails. With it, the rerun quietly replaces the schema, so check downstream reports after any type change.
  • The SQL analytics endpoint lags. The table exists in Spark the moment the write commits. The endpoint picks it up a little later through metadata sync, so a pipeline step reading through T-SQL straight after this notebook can see old data. Refresh the endpoint metadata before that step.
  • toPandas() on a real export. Fine for 62 rows, an out-of-memory error on the driver for a year of till data from every store. Keep work in Spark DataFrames until the result is small.

On the brewhouse floor

A brewery's fermentation log has the same faults. A tablet logger on fermenter FV-07 sends the morning gravity reading twice when the Wi-Fi drops. A reading of n/a means nobody pulled a sample that day. The same notebook fixes both: drop duplicates on batch plus reading time, try_cast the gravity so n/a becomes a null. The derived column is alcohol by volume instead of margin, worked out from the starting and current gravity of the beer. The cellar team gets one clean reading per batch per morning without anyone retyping the log.
