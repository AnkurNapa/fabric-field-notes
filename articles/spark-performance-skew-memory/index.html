Spark performance: find the slow task before you buy a bigger node

A notebook that ran in minutes now runs for an hour, then dies on the driver. Read the Spark UI for skew, shuffle, small files and memory, fix the code instead of the node size and prove it with counts that cannot lie.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa SparkLakehouse

Short answer

Most slow Spark notebooks in Fabric are not short of compute. One task is doing most of the work, or the driver is being asked to hold the whole table. Open the run from the Monitoring hub, go to the Spark UI and compare the median task with the max task in the slowest stage. A big gap is skew. A driver crash with no tasks running is almost always toPandas() or collect(). Fix the shape of the work (aggregate before you window, partition by a finer key, write instead of collect) and the same pool finishes. Scaling up a skewed job only buys a bigger machine to wait on one task.

The symptom

Harbour Goods runs a notebook every morning that builds quarter-to-date net sales per store for a chart. It was fine for a year. Then ST-014 in Pune started fulfilling online orders and its volume went to 60 per cent of the company. The notebook now runs for most of an hour, the progress bar sits at 199 of 200 tasks for twenty minutes and some mornings it fails with OutOfMemoryError on the driver. Someone has already asked for a bigger node size.

To reproduce it, generate a synthetic quarter of orders with that shape. This writes 24 million rows, 14.4 million of them for ST-014.

from pyspark.sql import functions as F

others = F.array(*[F.lit(s) for s in ["ST-003", "ST-007", "ST-011", "ST-019", "ST-022"]])

orders = (spark.range(24_000_000)
    .withColumn("order_id", F.format_string("HG-%09d", F.col("id")))
    .withColumn("store_id", F.when(F.col("id") % 100 < 60, F.lit("ST-014"))
                             .otherwise(F.element_at(others, (F.col("id") % 5 + 1).cast("int"))))
    .withColumn("order_date", F.expr("date_add(DATE'2026-07-01', CAST(id % 92 AS INT))"))
    .withColumn("quantity", (F.col("id") % 4 + 1).cast("int"))
    .withColumn("unit_price", (F.lit(299) + (F.col("id") % 7) * 100).cast("decimal(10,2)"))
    .withColumn("net_amount", (F.col("quantity") * F.col("unit_price")).cast("decimal(14,2)"))
    .drop("id"))

orders.write.mode("overwrite").format("delta").saveAsTable("perf_orders")

And this is the notebook as it was written:

from pyspark.sql import Window

w = (Window.partitionBy("store_id")
           .orderBy("order_date", "order_id")
           .rowsBetween(Window.unboundedPreceding, Window.currentRow))

running = spark.table("perf_orders").withColumn("qtd_sales", F.sum("net_amount").over(w))

pdf = running.toPandas()                                   # for the chart
daily = pdf.groupby(["store_id", "order_date"]).last()     # one point per store per day

Measure it

Before you touch anything, check which runtime you are on. Runtime 2.0 (Spark 4.1, Delta 4.2) became the default for new workspaces on 6 October 2026, but some Learn pages still say 1.3. Look in Workspace settings > Data Engineering/Science > Spark settings > Environment. Timings and defaults differ between the two, so write the version next to every number you record.

  1. Find the run. Select Monitor in the left navigation, filter Item type to Notebook and open the run. The detail page has a Jobs tab; select a job's Description to open the Spark UI in a new tab. From inside the notebook, the cell's context menu has the same route.
  2. Read the Spark Advisor first. In the notebook, advice icons appear under the cell; on the run detail page the same advice sits in the Diagnostics panel. The advisor detects skew on its own and often names the stage for you.
  3. Stages tab, slowest stage. Open it and read Summary Metrics for Completed Tasks. Compare median, 75th percentile and max for Duration and Shuffle Read Records. Learn's rule of thumb is that a few tasks with ten to a hundred times the input of the rest is skew.
  4. Executors tab. Exit code 137 means a container ran out of memory. Exit code 143 with dynamic allocation is usually Fabric scaling down an idle executor and is harmless if the job finishes.
  5. Driver logs. A driver OutOfMemoryError while no tasks are running points at code that pulls data to the driver.
  6. The plan. running.explain() shows Exchange hashpartitioning(store_id, 200) feeding the Window. Six stores means six keys, so at most six of those 200 partitions hold any data at all.

What you should find. The numbers are exact because the data is generated:

  • The window stage has one task reading 14,400,000 records (ST-014) and at most five others reading 1,920,000 each. Everything else is empty. Max to typical is 7.5 to 1 on rows and worse on time, because sorting 14.4 million rows spills.
  • toPandas() asks the driver for all 24,000,000 rows.

That is two problems, skew and memory. Neither gets better with a bigger node. Learn says it bluntly: adding resources to a skewed workload does not help, because the oversized partition still lands on one executor.

Two more checks belong in every investigation, even when they turn out clean:

  • Shuffle size. spark.sql.shuffle.partitions defaults to 200 and Adaptive Query Execution is on by default in every Fabric runtime, so small shuffles get coalesced for you. The lever that matters is how many rows reach the shuffle at all.
  • Small files. Run DESCRIBE DETAIL perf_orders and divide sizeInBytes by numFiles. Microsoft's target is 128 MB to 1 GB per file. A table of thousands of tiny files spends its time opening files, not reading them. The fix is compaction, covered in Delta maintenance.

Fix it

1. Aggregate before you window. The chart needs one value per store per day. The running total at the last order of a day equals the sum of every day up to and including it. So sum first, then run the window over 552 rows instead of 24 million.

daily = (spark.table("perf_orders")
         .groupBy("store_id", "order_date")
         .agg(F.sum("net_amount").alias("day_sales")))

w = (Window.partitionBy("store_id")
           .orderBy("order_date")
           .rowsBetween(Window.unboundedPreceding, Window.currentRow))

qtd = daily.withColumn("qtd_sales", F.sum("day_sales").over(w))
qtd.write.mode("overwrite").format("delta").saveAsTable("store_qtd_sales")

The groupBy runs a partial aggregation on every input task before the shuffle, so ST-014's 14.4 million rows become at most 92 per task long before they meet the hot key.

2. Bring only the answer to the driver.

pdf = spark.table("store_qtd_sales").toPandas()   # 552 rows

Learn's pattern table puts it simply: write to storage instead of collect() and filter or aggregate before toPandas().

3. When you genuinely need every row in a window, partition by a finer key that the business logic allows. Numbering orders within a store and day instead of within a store cuts the largest window partition from 14,400,000 rows to 156,524. If no finer key exists, salt the key and recombine, which Learn shows in the memory troubleshooting guide.

4. Leave the config alone until the code is right. If a Python UDF or a native library still runs out of memory after the fix, raise spark.executor.memoryOverhead. Fabric sets it to a fixed 384 MB regardless of node size, which is often too small. Executor and driver settings cannot be changed with spark.conf.set() mid-session; put them in a %%configure cell as the very first cell, or in an environment.

%%configure -f
{"conf": {"spark.executor.memoryOverhead": "4g"}}

Do not reach for spark.sql.adaptive.skewJoin.enabled here. AQE splits skewed partitions in joins. A window has no join to split.

Prove it

Run both versions on the same pool and fill in the timings for your capacity. The counts below do not depend on hardware; if yours differ, the data or the code differs.

Then check the answer did not change. ST-014's final quarter-to-date value is 21,563,998,900.00 in both versions and the six stores total 35,939,998,000.00. In the Monitoring hub, open Historical runs > Monitor run series for the notebook and select both runs in Compare runs. The window stage's duration should collapse; if it does not, the fix did not deploy.

Where this breaks

  • The fix moves the skew. If a later step joins store_qtd_sales back to row-level orders on store_id, the hot key returns. Broadcast the small side.
  • Native Execution Engine memory. The engine reserves off-heap memory and can squeeze the JVM heap. If exit code 137 appears on a job that ran fine before, test with the engine off. Learn's memory page names the setting spark.fabric.nativeExecution.enabled while the runtime page uses spark.native.enabled; check which one your runtime honours.
  • Runtime 2.0 is stricter. Spark 4 runs in ANSI mode. A cast that returned null on 1.3 raises an error on 2.0, which can look like a performance regression when it is a data problem. Use try_cast on messy columns.
  • Starter pools are best effort. If a session takes minutes to start, that is pool start-up, not your code. Custom pools start in about three minutes; libraries in an environment add more.
  • Run series only compares like with like. It compares runs of the same notebook, not two different notebooks.

On the brewhouse floor

A brewery's fermentation log has the same hot key. Brewery A logs most tanks once a minute, but FV-03 carries a new pressure probe that reports every second, so one tank produces sixty times the rows of its neighbours. A notebook that ranks readings per tank sends all of FV-03 to one task. Average per tank per minute first, then window. The job then treats FV-03 like every other vessel. The brewer only ever looked at the minute anyway.
