Labels, endorsement and lineage: mark it, trust it, trace it

Label a sales lakehouse and model as confidential and watch the label flow to the reports, promote and certify the model so people find the right one, then use lineage and impact analysis before changing anything shared. Includes what deployment pipelines do and do not carry across.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa GovernanceSecurity

Short answer

Three separate tools answer three questions. A sensitivity label says how sensitive an item is and travels with it, to downstream items and to exported files. An endorsement (Promoted, Certified or Master data) says how much to trust it. Lineage and impact analysis say what depends on it. Apply labels at the source and let downstream inheritance carry them. Promote anything reusable; certify only what has passed a documented check. Run impact analysis before you change anything another team reads. None of the three changes who can open an item on its own. Access is still workspace roles, item permissions and data security.

What you will build

The Harbour Goods sales work from earlier walkthroughs lives in one workspace: the lh_sales_gold lakehouse, the sm_sales_kpis Direct Lake model and two reports, rpt_sales_kpis and rpt_sales_explorer. Product cost sits in that lakehouse. Somebody will export a table to Excel one day. That file should say Confidential in its header when it lands in an inbox.

You will:

  • Read the workspace lineage view.
  • Label the lakehouse and the model Confidential and confirm both reports inherit it.
  • Promote the model and make it discoverable, then request certification.
  • Run impact analysis on the lakehouse and draft a change notice.

Before you start

  • The items above. If you only did Your first Direct Lake model, you have one report, which is enough.
  • Sensitivity labels published to you from Microsoft Purview Information Protection by your organisation. Label names are set per tenant; this walkthrough says Confidential for whatever your tenant calls its middle tier.
  • Edit permission on the items (Contributor or higher) and a Power BI Pro or Premium Per User licence to apply labels.
  • For certification, membership of a security group your Fabric administrator has named in the certification tenant setting.

Step 1: read the lineage view

  1. Open the workspace. On the toolbar switch from list view to Lineage view.
  2. Find the lh_sales_gold card. Select the arrow at the bottom right of the card to highlight its lineage. Everything unrelated dims.

The view shows every item in the workspace and how they connect, plus external sources one level upstream. It does not show downstream items in other workspaces. Users with the Viewer role see the items but not the data sources.

Spend a minute here before changing anything. Most surprises in a shared workspace are a report someone built on the wrong model three months ago.

Step 2: label the lakehouse and the model

  1. Open lh_sales_gold. Select the sensitivity indicator in the item header to open the flyout and choose Confidential. You can also do this in the item's settings under the sensitivity section.
  2. Open the settings for sm_sales_kpis. In Sensitivity label choose Confidential. Leave the box that applies the label to downstream items ticked if your tenant shows it. Select Apply.

What happens next depends on a tenant setting. In the default mode, downstream inheritance runs with user consent: that tick box is the consent. The label lands on each downstream report you have edit rights on. In fully automated mode there is no box and it happens anyway.

The rules that decide whether a downstream item changes:

  • A more restrictive label wins. A less restrictive one never replaces it.
  • A manually applied label is never overwritten by inheritance.
  • If more than 80 items sit downstream, no downstream inheritance happens at all. Only the item you labelled changes.
  • A new report built on a labelled model inherits the label on creation, even with downstream inheritance switched off.

Step 3: promote, make discoverable, request certification

  1. Open the settings for sm_sales_kpis and expand Endorsement.
  2. Select Promoted. Tick Make discoverable so people without access can find the model in the OneLake catalog and request access instead of rebuilding it from a CSV.
  3. Select Apply.

If you are an authorised certifier, select Certified instead. If you are not, the Certified option is greyed out and a link reads along the lines of How do I get content certified. It points to your organisation's process, if your administrator has published one.

Before certifying anything, write down the checks it passed. A minimum for a sales model:

CheckEvidence
Measures reconcileNet sales for Q3 2026 = 468,212.55, matching the finance extract
One ownerA named person and a backup, not a shared mailbox
Security testedRLS tested as a Viewer, see Row and object security
Change controlChanges go through Git and a deployment pipeline

Certified items rank first in the OneLake catalog. That is the point and the risk: a badge on a model nobody owns is worse than no badge.

Step 4: impact analysis before a change

Say you plan to rename fact_sales[cost_amount] to unit_cost_total in the lakehouse.

  1. In lineage view, select the impact analysis button on the lh_sales_gold card. You can also open it from the item's details page under Lineage > Impact analysis.
  2. Switch between Child items and All downstream items. Use Browse by item type and Browse by workspace to group them.
  3. Select Notify contacts, describe the change and the date, then Send. The message goes to the contact lists of every affected workspace, including ones you cannot open.

You need write permission on the item to run impact analysis. Items you cannot access show as Limited access rather than by name.

Check it worked

  • Labels. Open each item and check the sensitivity indicator in its header. Four items should read Confidential: the lakehouse, the model and both reports. If a report kept a lower label, someone set it by hand; inheritance will not overwrite it.
  • Export. Open rpt_sales_kpis, export the table visual to Excel and open the file. It should carry the Confidential label; Learn supports label transfer on export for Power BI items in supported export paths.
  • Endorsement. Open the OneLake catalog and search for sm_sales_kpis. It shows the Promoted badge. A colleague without workspace access can find it.
  • Impact. All downstream items for lh_sales_gold should list at least the model and both reports, all in one workspace. The exact chain (lakehouse, then SQL analytics endpoint or model) depends on how the model connects; a Direct Lake on SQL model sits behind the endpoint.

Where this breaks

  • Deployment pipelines drop endorsement. Endorsement settings are not copied between stages. Certify in production, not in development.
  • Labels in pipelines are conditional. A label is copied only when the item is new in the target stage or when the source label has protection and the target has none. An existing test item keeps its own label after a deployment.
  • Labels are not access control. A Contributor still reads a Confidential lakehouse. To restrict access by label, your administrator needs Purview protection policies.
  • Inheritance from data sources is narrow. Picking up a label from an upstream data source works for Power BI semantic models only. A notebook connected to a labelled source does not inherit through that route, although connecting it to a more restrictive Fabric item in the UI does trigger reevaluation.
  • Lineage stops at the workspace edge. Lineage view does not draw downstream items in other workspaces. Use impact analysis for those, or Microsoft Purview for one tenant-wide picture.
  • Parent labels. If your tenant adds sublabels under Confidential, items carrying the parent label stop inheriting cleanly and exports fail. Move them to the right sublabel.

On the brewhouse floor

A winery buys grapes from forty growers on contracts priced per tonne by block and variety. Those prices sit in the same lakehouse as the cellar data. The vintage cost model reads both. Label the grower contracts table's lakehouse Confidential and the cost model and its reports inherit it, so the export the winemaker sends to a consultant carries the label too. Certify the cost model only after the tonnes received reconcile with the weighbridge tickets. Run impact analysis before anyone renames the block code, because the vineyard map, the harvest report and the bottling schedule all join on it.
