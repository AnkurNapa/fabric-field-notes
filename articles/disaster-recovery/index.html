Disaster recovery in Fabric: what fails over and what you must back up

Fabric copes with a failed datacentre on its own. A lost region is different: OneLake data is replicated only if you switch it on. Most code and configuration is not replicated at all. Here is the item-by-item map, a tiered design and the backups people forget.

Ankur Napa 11 Oct 2026, 9 min read

Short answer

Fabric spreads itself across availability zones without any set-up, so a failed datacentre usually costs you a retried Spark job or a rerun query. A lost region is your problem as much as Microsoft's.

  • Data in OneLake (lakehouse and warehouse) is copied to the Azure paired region only if a capacity admin turns on the capacity's disaster recovery switch. The copy is asynchronous, so whatever had not replicated when the region went down is gone.
  • Power BI semantic models, reports and dashboards have disaster recovery by default and stay readable after failover. Refreshes and publishing stop.
  • Almost everything else is not replicated: notebook code, pipelines, Dataflow Gen2, Eventstream and Activator definitions, KQL databases, SQL database in Fabric, mirrored database settings, ML experiments and Fabric Apps. You rebuild those from Git, exported files or a second copy you kept running elsewhere.

After a failover the portal is read only. Lakehouses and warehouses cannot be opened, though their files are readable through the OneLake APIs. Recovery means a new capacity in a working region, new workspaces with the same item names, a copy of the data and a redeploy from source control.

And disaster recovery is not backup. A bad overnight load replicates perfectly. Accidental deletes and bad loads need soft delete, Delta time travel and warehouse restore points instead.

Three facts change the conversation with a client. Microsoft declares the failover, not you. It typically completes in under an hour. Replication works only where the home region and capacity region have an Azure pair that runs Fabric. And if the tenant home region itself is down, recovery waits for Microsoft to restore it first.

Reference design

Harbour Goods tiers its estate by how painful each data product is to lose.

  sc-coldstore-prod (Eventhouse)            second Eventhouse in another region,
                                            Eventstream writes to both
  claims app (Fabric App + SQL database)    nightly .bacpac to storage in
                                            another region

Tier 2: rebuild from source in a day
  sales-reporting-prod, fin-margin-prod     capacity PROD-2, DR switch OFF
                                            models and reports as PBIP in Git

All tiers
  every prod workspace connected to Git
  connections, gateways and secrets listed in the runbook

The recovery runbook, in Learn's order:

  1. Create a new capacity in a working region. Learn suggests a region outside the primary geography, because demand spikes during a regional event.
  2. Create workspaces on it, with the same names if scripts depend on them.
  3. Create items with the same names as the originals. The lakehouse copy scripts assume this.
  4. Copy lakehouse tables one table at a time and files in one pass, from the old OneLake paths to the new lakehouse.
  5. Reload warehouses from an interim lakehouse with INSERT INTO, SELECT INTO or CREATE TABLE AS SELECT.
  6. Connect the new workspaces to Git and sync notebooks, pipelines, Activator rules and models.
  7. Import the latest .bacpac, recreate mirrors, redeploy apps and rebind connections.

Disaster recovery covers a lost region. The everyday losses need different tools:

What went wrongToolWindow
Someone deleted files in OneLakeOneLake soft delete7 days
Someone deleted an itemItem recovery, on by default3 days by default, up to 90
Someone deleted a workspaceWorkspace retention7 days by default, up to 90
A bad load overwrote a lakehouse tableDelta time travel and RESTORE TABLEUntil VACUUM removes the old files
A bad release broke a warehouseRestore point, restored in placeSystem point every 8 hours; 30-day default retention, 1 to 120 days

Questions to ask the client

  • For each data product, how long can it be down and how much recent data can it lose? Get two numbers, not "as little as possible".
  • Which data can be reloaded from the source system? Does the source still hold the full history?
  • What is the tenant home region? Does it have an Azure pair that runs Fabric?
  • Are any KQL databases, SQL databases or mirrored databases in production? None of them is covered by the switch.
  • Is every production workspace connected to Git today? If not, which ones hold the only copy of their code?
  • Which gateways, connections and secrets would have to be recreated? Who knows the credentials?
  • Who holds the capacity admin role? Are they reachable at 3 in the morning?
  • When was recovery last rehearsed?

Review checklist

  • Each production capacity has a recorded decision on the DR switch, with the reason.
  • Every production workspace is in Git, including notebooks, pipelines, Activator rules and semantic models.
  • Data outside OneLake (KQL, SQL database, shortcut targets in your own storage) has its own protection.
  • SQL database exports run on a schedule and land in a different region.
  • A user restore point is created before every warehouse release.
  • Soft delete, item recovery and workspace retention periods are set on purpose, not left at defaults by accident.
  • The runbook names the recovery region and lists every connection to recreate.
  • BCDR storage and operations are visible in the Capacity Metrics app and in the budget.
  • Recovery has been rehearsed into a test capacity at least once.

Anti-patterns

  • Treating the DR switch as a backup. It copies your mistakes too. Corrupt data in the primary becomes corrupt data in the secondary as soon as it replicates.
  • Code that only exists in the workspace. Notebook code is not saved after a regional disaster. If Git is not connected, the notebook is gone.
  • Assuming streaming data is covered. KQL database data lives outside OneLake. The switch does nothing for it.
  • Flipping the switch on and off to save money. Each change locks it for 30 days. The first replication can take a long time in busy regions.
  • Forgetting the app. Fabric Apps are not replicated. Without the source code in a repository, there is nothing to redeploy.
  • A runbook nobody has run. Item names, connection strings and gateway credentials all surface as surprises on the day.

On the brewhouse floor

A winery takes in grapes for a few weeks a year. Every truck crossing the weighbridge becomes a record: grower, block, tonnes and sugar level. Those intake records decide what each grower is paid and which tank the fruit went into. The vintage happens once. If they sit in a lakehouse, the DR switch protects them. If the weighbridge feed lands in a KQL database for live dashboards, the switch does not, so the same events should also land in a lakehouse or a second Eventhouse elsewhere. You can re-run a report next week. You cannot re-run a harvest.
