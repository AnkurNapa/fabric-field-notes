A Fabric app in an afternoon: a store issue tracker on Rayfin

Scaffold a Fabric app with the Rayfin CLI, model stores and delivery or stock issues as decorated TypeScript classes, lock rows to claims.sub, deploy with rayfin up and know exactly where the preview runs out of road.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa Rayfin

Short answer

Rayfin turns decorated TypeScript classes into a SQL database in Fabric, a GraphQL API, Entra sign-in and static hosting, all deployed with npx rayfin up. A store issue tracker fits it well: stores, issues and a rule that each store manager sees only their own issues while the regional lead sees everyone's. Key every row on claims.sub, because that is the only identity you can trust. There are two roles, claims.role is always "Authenticated", policies compare with eq and ne only, password sign-in stops working once you deploy and secrets never reach the browser. Build inside those lines and the afternoon holds.

What you will build

An issue tracker for Harbour Goods stores. A regional lead registers the stores in their region. Store managers log what went wrong with a delivery or with stock: a late or short delivery, damaged goods, a line out of stock or the wrong item sent. Each manager sees only the issues they logged. The lead sees every issue for their stores and marks them resolved.

Speed is the whole reason the app exists. A short delivery logged at the back door, while the driver is still in the yard and the delivery note is still on the clipboard, gets a credit note. The same shortage raised in Friday's email gets an argument. So the form has to be quick and the permissions have to be right first time, which means the database enforces them, not the UI.

Three entities:

  • Store: code, city, region, opening date and owner_id, the regional lead's claims.sub.
  • StoreIssue: one issue at one store, with reporter_id and a copied lead_id.
  • Membership: who is a manager and who is a lead, for the UI only. More on why below.

Before you start

  • Capacity. The target workspace needs Fabric capacity assigned. Fabric apps consume capacity units.
  • Tenant setting. A Fabric admin enables Fabric apps (preview) under Tenant settings in the admin portal, for the whole organisation or a security group. Fabric apps are not in every region yet, so check region availability if item creation fails.
  • Workspace role. Contributor, Member or Admin on the workspace. Anyone redeploying later needs at least Edit on the app item.
  • Node.js 20 or later. Docker Desktop too, if you want the fully local stack.
  • SDK version. Everything here was checked against Rayfin SDK and CLI 1.36.2. It is a preview that ships often, so run npx rayfin --version and compare.

Step 1: scaffold

npm create @microsoft/rayfin@latest -- store-issues --template todoapp --workspace "Retail Dev"
cd store-issues

The todoapp template already wires Fabric sign-in, a typed client and per-user row security, which is most of what a tracker needs. Delete rayfin/data/Todo.ts once your own entities are in.

Step 2: model the entities

rayfin/data/Store.ts:

import { entity, role, uuid, text, set, date, many } from '@microsoft/rayfin-core';
import { StoreIssue } from './StoreIssue.js';

@entity()
@role('authenticated', 'read')
@role('authenticated', ['create', 'update', 'delete'], {
  policy: (claims, item) => claims.sub.eq(item.owner_id),
})
export class Store {
  @uuid() id!: string;
  @text({ max: 10 }) code!: string; // e.g. ST-014
  @text({ max: 40 }) city!: string;
  @set('North', 'South', 'East', 'West')
  region!: 'North' | 'South' | 'East' | 'West';
  @date() opened!: Date;
  @text({ max: 128 }) owner_id!: string; // claims.sub of the regional lead
  @many(() => StoreIssue) issues?: StoreIssue[];
}

rayfin/data/StoreIssue.ts:

import { entity, role, uuid, text, int, set, date, one } from '@microsoft/rayfin-core';
import { Store } from './Store.js';

type IssueKind = 'late delivery' | 'short delivery' | 'damaged' | 'out of stock' | 'wrong item';

@entity()
@role('authenticated', 'read', {
  policy: (claims, item) =>
    claims.sub.eq(item.reporter_id).or(claims.sub.eq(item.lead_id)),
})
@role('authenticated', 'create', {
  policy: (claims, item) => claims.sub.eq(item.reporter_id),
})
@role('authenticated', 'update', {
  policy: (claims, item) =>
    claims.sub.eq(item.reporter_id).or(claims.sub.eq(item.lead_id)),
})
export class StoreIssue {
  @uuid() id!: string;
  @one(() => Store) store?: Store;
  @uuid() store_id!: string;
  @text({ max: 128 }) reporter_id!: string;
  @text({ max: 128 }) lead_id!: string; // copied from Store.owner_id
  @date() reportedOn!: Date;
  @set('late delivery', 'short delivery', 'damaged', 'out of stock', 'wrong item')
  kind!: IssueKind;
  @int({ min: 1, max: 5 }) severity!: number;
  @text({ max: 20, optional: true }) order_id?: string;
  @set('open', 'resolved') status!: 'open' | 'resolved';
  @text({ max: 500, optional: true }) notes?: string;
}

rayfin/data/Membership.ts:

import { entity, role, uuid, text, set } from '@microsoft/rayfin-core';

@entity()
@role('authenticated', 'read', {
  policy: (claims, item) => claims.sub.eq(item.user_id),
})
@role('authenticated', 'create', {
  policy: (claims, item) =>
    claims.sub.eq(item.user_id).and(item.storeRole.eq('manager')),
})
export class Membership {
  @uuid() id!: string;
  @text({ max: 128, unique: true }) user_id!: string;
  @text({ max: 80 }) displayName!: string;
  @set('manager', 'lead') storeRole!: 'manager' | 'lead';
}

Why lead_id sits on every issue: a policy compares a claim with a field on the same row. It cannot join to Store or look up Membership. So the lead's identity travels with the row and the read rule becomes a plain or. There is no delete on StoreIssue, so a logged issue stands. It can only be resolved.

Register all three in rayfin/data/schema.ts. Import the classes as values, not with import type, or the lazy () => Store callbacks resolve to undefined:

import { Membership } from './Membership.js';
import { Store } from './Store.js';
import { StoreIssue } from './StoreIssue.js';

export type IssuesSchema = {
  Store: Store;
  StoreIssue: StoreIssue;
  Membership: Membership;
};

export const schema = [Store, StoreIssue, Membership];

Step 3: configure rayfin.yml

id: store-issues
name: store-issues
version: 1.0.0
services:
  auth:
    enabled: true # rayfin up fails without auth
    fabric:
      enabled: true # Entra SSO, the only sign-in after deploy
    password:
      enabled: true # local development only
    allowedRedirectUris:
      - http://localhost:5173
  data:
    enabled: true
    dialect: mssql
  staticHosting:
    enabled: true
    folder: dist
    buildCommand: npm run build:fabric
    indexDocument: index.html

Step 4: wire the client

Rename the template's TodoAppSchema import in src/services/rayfinClient.ts to IssuesSchema, then add src/services/issues.ts:

import { getRayfinClient } from './rayfinClient';

type NewIssue = {
  kind: 'late delivery' | 'short delivery' | 'damaged' | 'out of stock' | 'wrong item';
  severity: number;
  order_id?: string;
  notes?: string;
};

export async function logIssue(store: { id: string; owner_id: string }, issue: NewIssue) {
  const client = getRayfinClient();
  const session = client.auth.getSession();
  if (!session.isAuthenticated || !session.user) throw new Error('Sign in first.');
  return client.data.StoreIssue.create({
    ...issue,
    store_id: store.id,
    reporter_id: session.user.id, // must equal claims.sub or the policy rejects it
    lead_id: store.owner_id,
    reportedOn: new Date(),
    status: 'open',
  });
}

export async function issuesFor(storeId: string) {
  // A manager gets their own rows back; the lead gets every row for the store.
  return getRayfinClient().data.StoreIssue
    .select(['id', 'kind', 'severity', 'order_id', 'status', 'reporter_id'])
    .where({ store_id: { eq: storeId } })
    .execute();
}

export async function isLead(): Promise<boolean> {
  const client = getRayfinClient();
  const session = client.auth.getSession();
  if (!session.user) return false;
  const rows = await client.data.Membership
    .select(['storeRole'])
    .where({ user_id: { eq: session.user.id } })
    .execute();
  return rows[0]?.storeRole === 'lead';
}

The same query is one GraphQL call against /api/graphql on the app backend URL, so a script or notebook can read the issue log too.

Step 5: run it locally

npx rayfin login
npm run dev

npm run dev in this template provisions or reuses the backend in your Fabric workspace, applies the schema and starts Vite on http://localhost:5173. For a fully offline loop with email and password sign-in, run npx rayfin dev --provider docker instead. After any entity change, run npx rayfin up db apply. After any rayfin.yml change, restart the dev session.

Step 6: deploy

npx rayfin up --dry-run
npx rayfin up
npx rayfin up status

rayfin up creates or reuses the app item, syncs auth settings, applies the schema, builds and uploads dist and prints the hosted URL plus a portal link. Open the app from Fabric. Embedded sign-in expects to run inside the portal.

Check it worked

  • npx rayfin up status shows the item as deployed in the workspace you named.
  • In the portal the app item lists its SQL database. The query editor is read-only, which is enough: SELECT reporter_id, lead_id, kind FROM StoreIssue should show one row per logged issue.
  • Sign in as two store managers and one lead. Log one issue as each manager against ST-014. Each manager sees one row from issuesFor. The lead sees both.
  • A manager who calls create with someone else's reporter_id gets a permission error, not a row.

Where this breaks

  • Two roles, full stop. Only anonymous and authenticated exist and claims.role is always "Authenticated", so claims.role.eq('lead') never matches. That is why lead status lives in Membership and every rule keys on claims.sub. It also means Membership gates the UI, not the data. Anyone signed in can still create a Store, though only they can then change it. Promoting someone to lead is the one write I keep out of the browser entirely: the create policy pins new rows to manager and there is no update rule. Do the promotion server side through a Rayfin function. Test it before you rely on it. I have not run that path end to end.
  • Policies speak eq and ne only. The SDK's comparison operators are eq and ne (the method is .neq()), joined with .and() and .or(). No greater-than, no in, no joins. Anything richer goes into a copied field like lead_id or into a function. The update rule here cannot say "only the lead may set status to resolved", because a policy cannot compare the old value with the new one. A manager can resolve their own issue too. If only the lead should close issues, move that write into a function.
  • No secrets in the app. The static frontend is served from a public URL, so nothing secret belongs in src. On SDK 1.33.2 there was no way to deliver a secret to a deployed app at all. CLI 1.36.2 adds npx rayfin secret set, which stores values on the deployed item for server-side functions to read through ctx.Secrets. That is new and I have not tested it. Until you have, keep third-party keys, such as a carrier's tracking API key, in an Azure Function or Container App with Key Vault and a managed identity.
  • Password sign-in dies at deploy. Email and password works locally. Deployed apps accept Fabric SSO through Entra only, so every store manager needs an identity in your tenant and access to the item. Plan that before go-live, not on the day.
  • Unbounded text breaks GraphQL. @text() without max becomes NVARCHAR(MAX) on SQL, which can deploy cleanly and then fail with an internal server error when the GraphQL schema builds. Give every string a max.
  • Destructive schema changes. rayfin up blocks changes that would lose data. --force pushes them through and the issue log goes with them. Export first.

On the brewhouse floor

The same three entities run a blind tasting panel at a small brewery. Brewery A logs each packaged batch, tasters score it on aroma, flavour and true-to-style from 1 to 5 and name any off-flavour they notice. Each taster sees only their own score sheet, so nobody copies the person next to them, while the head brewer sees every sheet for their batches. It is the reporter and lead rule from this article with batches in place of stores.
