Real-time platform design: streaming, the lake and alerts together

A design guide for putting Eventstream, Eventhouse, OneLake and Activator together so operators get seconds, analysts get history and nobody keeps two copies. Includes the latency each hop really adds and the settings that lock you in.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa Real-timeKQLLakehouseDirect Lake

Short answer

Use Eventstream to land events, an Eventhouse as the hot store, KQL update policies for silver, materialised views for gold, then turn on OneLake availability so Spark, the SQL endpoint and Direct Lake read the same data as Delta without a second copy. Real-Time Dashboards serve operators, Activator turns conditions into actions and Power BI serves everyone else. Send Eventstream straight to a lakehouse only for append-only history with a stable schema, because the lakehouse destination enforces the first record's schema. The design question is never "real-time or batch". It is how fresh each consumer actually needs the data. Then pay for exactly that.

The decision

Start from consumers, not from tools. Each one has a freshness need and a natural home.

ConsumerFreshness they needServe fromWhy
An alert that something is wrong nowSecondsActivator on Eventstream or on an Eventhouse queryActs before a person looks
Operations wall screenSeconds to a minuteReal-Time Dashboard on EventhouseKQL over billions of rows in seconds
Analyst exploring last weekMinutesEventhouse (KQL) or its OneLake copy via SQLSame data, their language
Monthly report, financeHoursDirect Lake on the OneLake copyNo refresh, no extra storage
Data science training setHours to a daySpark on the OneLake copyDelta, read in place

And the landing choice:

Landing patternGood forWatch
Eventstream to EventhouseAnything operational, changing schemas, high volumeKQL skills on the team
Eventstream to LakehouseAppend-only history, stable schemaFirst record sets the schema; not recommended for CDC-shaped feeds
Both, fanned outHot alerts plus a cheap long archiveTwo stores to govern; only do it when retention differs
Spark Structured StreamingTeams already fluent in SparkYou run the job, checkpoints and the small-file problem yourself

Settings that decide cost and freshness:

  • OneLake availability on an Eventhouse table creates a logical Delta copy at no extra storage cost. The write delay (TargetLatencyInMinutes) defaults to up to 3 hours, or until files of about 200 to 256 MB form. You can set it from 5 minutes to 3 hours. Shorter delays mean small files. The OneLake copy is read-only, so you cannot optimise it later.
  • While OneLake availability is on you cannot rename tables, change a column type, apply row level security to the table or delete, truncate or purge data. Turning it off soft-deletes the OneLake copy. Decide the schema before you switch it on.
  • Eventstream retention beyond one day is billed as OneLake storage.
  • Activator from a Real-Time Dashboard tile only works if the tile's KQL uses the dashboard's _startTime and _endTime parameters. A custom time range disables Set alert.

Reference design

Harbour Goods, the fictional retailer used across this site, runs cold-store warehouses. Each sensor sends sensor_readings (warehouse_id, sensor_id, reading_time, temperature_c, humidity_pct) every 30 seconds. Ops wants an alert when a cold room drifts. Finance wants monthly spoilage risk next to deliveries.

Three choices are deliberate. The alert reads from Eventstream, not from the OneLake copy, so it is not waiting on a 60-minute write delay. Bronze keeps 30 days because nobody debugs a parser older than that. Silver keeps 13 months so a year-on-year comparison always has its base month.

The latency budget, end to end:

HopTypical delayControlled by
Sensor to EventstreamSecondsSource and network
Eventstream to EventhouseSecondsIngestion batching policy
Bronze to silver to goldSeconds after ingestionUpdate policy, materialised view
Eventhouse to OneLake Delta5 minutes to 3 hoursTargetLatencyInMinutes
OneLake to Direct Lake reportSeconds after a commitAutomatic Direct Lake updates

Questions to ask the client

  1. Who acts on this data and how fast do they need to? Name a person and a minute count, not "real time".
  2. What is the action? An email nobody reads at 2am is not an action. Who picks up the phone?
  3. Does the source schema change? CDC feeds and evolving device payloads rule out the direct lakehouse destination.
  4. How long must raw events be kept? For whom? Retention per layer drives cost more than ingestion does.
  5. Will the OneLake copy need row level security? It cannot be applied on the Eventhouse table while availability is on, so secure it in the semantic model or with OneLake security instead.
  6. Is there an existing Kafka or Event Hubs estate? Eventstream connects to both, so do not rebuild the producer side.
  7. Who on the team writes KQL today? If nobody, plan the training before the go-live.

Review checklist

  • Every consumer has a freshness number and a serving layer from the first table.
  • Alerts read from the hottest layer that holds the signal, not from the OneLake copy.
  • Retention set per table, with a reason written next to each.
  • TargetLatencyInMinutes chosen against the slowest consumer that reads the Delta copy, not the fastest.
  • Schema settled before OneLake availability is switched on.
  • Activator rules have a named owner and a tested action.
  • Dashboard tiles that feed alerts use _startTime and _endTime.
  • Capacity Metrics checked after a week; Eventhouse always-on compute is the usual surprise.

Anti-patterns

  • Real time everywhere. Five-minute OneLake latency on a table read once a month buys small files and nothing else.
  • Alerting off the lake. An alert built on a Direct Lake report inherits the slowest hop. The cold room has warmed for an hour before anyone hears.
  • Two copies of the same stream. Eventstream into both an Eventhouse and a lakehouse with the same retention is double storage with no benefit. OneLake availability already gives the Delta copy.
  • Lakehouse destination for CDC. The first record fixes the schema. The first new column breaks the feed.
  • Alerts with no owner. A rule that fires into a shared mailbox trains everyone to ignore it within a fortnight.

On the brewhouse floor

Fermentation is the brewery version of the cold room. Each fermenter at Brewery A reports temperature every minute. A lager that drifts two degrees warm for a few hours can pick up off-flavours the brewer will taste a fortnight later. The alert belongs on the stream: FV-03 above its set point for 20 minutes pages the shift brewer. The OneLake copy can lag by an hour, because the people reading it are comparing this month's fermentation curves with last year's, not saving tonight's batch.
