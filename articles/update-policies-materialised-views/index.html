Update policies and materialised views in an Eventhouse

Land raw cold-store readings as text, clean them on the way in with an update policy, then keep hourly aggregates ready in a materialised view. Every report and alert reads the same cleaned numbers and nobody rewrites the filter.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa KQLReal-time

Short answer

Ingest raw readings into a landing table, then put an update policy on a clean table. The policy runs a stored function on every batch that lands, casts the text to proper types, drops readings no freezer can produce and writes the result to the clean table. On top of the clean table, a materialised view holds one row per cold store per hour with the count, average, maximum and humidity. The view is always up to date when you query it, because Kusto combines what it has already aggregated with anything that arrived since. Put the reshaping in the update policy and keep only the aggregation in the view.

What you will build

This extends the Harbour Goods cold-store stream from Catch a failing freezer. That walkthrough queried raw readings directly, which is fine until a probe misbehaves. Here the readings arrive exactly as the devices send them, every field as text. Three of them are bad:

  • Two readings from WH-02 at 02:15 and 02:30 say -127.0 °C. That is not a freezer having a very good night. It is the value a common digital temperature probe reports when its cable comes loose.
  • One reading from WH-04 at 04:00 has no temperature at all.

The pieces:

  • sensor_raw: a landing table, all columns string.
  • CleanSensorReadings(): a stored function that types and filters the rows.
  • sensor_clean: the typed table, fed by an update policy.
  • ColdStoreHourly: a materialised view with hourly aggregates per cold store.

Sample data: update-policies-materialised-views.csv, 96 synthetic readings every 15 minutes from four cold stores between 00:00 and 05:45 UTC on 1 October 2026. WH-03 has a door left on its latch from 03:00, so its temperature and humidity climb for the last three hours.

Before you start

  • A workspace on a Fabric capacity or a trial, with an Eventhouse. Reuse coldchain_rti from the earlier walkthrough or create one with New item > Eventhouse.
  • Database Admin on the KQL database. Creating a materialised view needs at least Database Admin. The creator becomes the view's admin.
  • The sample CSV downloaded to your machine.

Create everything before you ingest. An update policy only fires on data that lands after it exists, so rows ingested first never reach the clean table.

Step 1: create the landing and clean tables

Open the KQL database and its queryset (the button may read Query with code or Explore your data), then run each command on its own:

.create table sensor_raw (reading_time: string, warehouse_id: string, sensor_id: string, temperature_c: string, humidity_pct: string)
.create table sensor_clean (reading_time: datetime, warehouse_id: string, sensor_id: string, temperature_c: real, humidity_pct: real)

Landing everything as string is deliberate. If the landing table were typed, a device that sends "N/A" would fail ingestion or quietly become null and you would never see the original value again. As text, the raw table keeps exactly what arrived.

Step 2: write the cleaning function

.create-or-alter function with (folder = "UpdatePolicies", docstring = "Types raw cold-store readings and drops impossible values")
CleanSensorReadings()
{
    sensor_raw
    | extend reading_time = todatetime(reading_time),
             temperature_c = todouble(temperature_c),
             humidity_pct = todouble(humidity_pct)
    | where isnotnull(reading_time)
        and isnotnull(temperature_c)
        and temperature_c between (-40.0 .. 40.0)
    | project reading_time, warehouse_id, sensor_id, temperature_c, humidity_pct
}

Three rules matter here. The output columns must match sensor_clean in name, order and type, or the policy fails. The function refers to sensor_raw by its plain name, never database("...").sensor_raw. And the range is a sanity bound, not a business rule: -40 °C to 40 °C covers every real reading a frozen or chilled store can produce while rejecting the probe's -127.

Test it before wiring it up. It returns nothing yet, which proves it parses.

CleanSensorReadings() | take 5

Step 3: attach the update policy

The policy lives on the target table and names the source:

.alter table sensor_clean policy update
@'[{"IsEnabled": true, "Source": "sensor_raw", "Query": "CleanSensorReadings()", "IsTransactional": true, "PropagateIngestionProperties": false}]'

IsTransactional: true means that if the function fails, the whole ingestion fails and nothing lands in either table. Microsoft recommends it for production so the clean table never silently misses a batch. With false, the raw table would take the data and the clean table would not. You would only find out from .show ingestion failures.

Check it took:

.show table sensor_clean policy update

Step 4: create the materialised view

.create materialized-view with (folder = "Gold", docString = "Hourly readings per cold store") ColdStoreHourly on table sensor_clean
{
    sensor_clean
    | summarize readings = count(),
                avg_temp_c = avg(temperature_c),
                max_temp_c = max(temperature_c),
                avg_humidity_pct = avg(humidity_pct)
      by warehouse_id, hour_start = bin(reading_time, 1h)
}

A view is one summarize over one source table. The summarize must be the last operator. A few things are not allowed. You will hit them the day you try to be clever:

  • No ago() or now() in the definition. Use a retention policy on the view to limit how far back it goes.
  • No ratio of two aggregates such as sum(a)/sum(b). Store both sums and divide at query time.
  • No round() around an aggregate. Round when you read.

The table is empty, so the view is created empty and is available immediately. If you add a view to a table that already holds data, use .create async materialized-view with (backfill=true) and watch progress with .show operations.

Step 5: ingest the readings

  1. In the KQL database select Get data > Local file.
  2. Choose the existing table sensor_raw, drop in the CSV and select Next.
  3. On Inspect the data pick CSV and keep First row is column header ticked. Every column maps to string. Select Finish.

In production you would point the Eventstream Eventhouse destination at sensor_raw instead. The policy and the view do not care how the rows arrive.

Step 6: query it

The view behaves like a table:

ColdStoreHourly
| where warehouse_id == "WH-03"
| project hour_start, readings, avg_temp_c = round(avg_temp_c, 2), max_temp_c, avg_humidity_pct = round(avg_humidity_pct, 2)
| order by hour_start asc

Querying ColdStoreHourly by name always returns current results, because Kusto adds any records not yet materialised at query time. When you only want the part already processed, which is faster on a large view, use materialized_view("ColdStoreHourly").

To share the hourly logic with dashboards and Activator, wrap it in a function so every consumer reads the same columns:

.create-or-alter function with (folder = "Gold") ColdStoreHourlyReport()
{
    ColdStoreHourly
    | project warehouse_id, hour_start, readings,
              avg_temp_c = round(avg_temp_c, 2),
              max_temp_c,
              avg_humidity_pct = round(avg_humidity_pct, 2)
}

Check it worked

All figures are computed from the sample file.

  • sensor_raw | count returns 96.
  • sensor_clean | count returns 93. The two -127.0 readings and the blank one are gone.
  • ColdStoreHourly | count returns 24: four cold stores times six hours.
  • WH-02 at 02:00 shows readings of 2 and an average of -20.15 °C. Without the filter, the raw average for that hour would be about -73.6 °C, a freezer apparently colder than anything the compressor can reach.
  • WH-04 at 04:00 shows 3 readings and an average of -20.77 °C.
  • WH-03 climbs hour by hour: an average of -18.35 °C at 03:00, -14.5 °C at 04:00 and -10.4 °C at 05:00, with a maximum of -8.9 °C and humidity averaging 88.28% in the last hour. Every other store stays between -20.9 °C and -19.73 °C on average.
  • .show materialized-view ColdStoreHourly shows IsEnabled and IsHealthy both true.

Where this breaks

  • Schema drift kills the policy. If someone adds a column to sensor_clean without updating the function, the output no longer matches and every transactional ingestion fails. Change the table and the function together, in one script.
  • Joins and streaming ingestion. Streaming ingestion is on by default for every table in an Eventhouse. An update policy whose function uses join needs streaming ingestion turned off on the source table (and on every upstream table in a chain). A lookup against a store dimension is a join.
  • The view gets disabled. A non-deterministic query (bag_unpack, pivot) or an incompatible change to sensor_clean makes Kusto disable the view automatically. It does not re-enable itself. Fix the cause, then run .enable materialized-view ColdStoreHourly.
  • Late data and .set-or-replace. A replace on the source table also replaces data in tables fed by its update policy. Use .set-or-append for corrections.
  • Shortcuts cannot host either. An accelerated or standard OneLake shortcut in an Eventhouse cannot carry an update policy or a materialised view. Land the data in a native table first.
  • The filter hides a broken probe. Dropping -127 keeps the averages honest, but a probe that reports -127 all day is a cable that needs fixing. Count the rejects: sensor_raw | count minus sensor_clean | count by sensor, on a dashboard tile, so somebody sees it.

On the brewhouse floor

A brewery logs fermenter temperatures the same way. Brewery A has twelve tanks with a probe in each glycol jacket reporting every minute, so FV-03 alone sends 1,440 readings a day. The head brewer wants hourly averages to see whether a lager is holding at 10 °C, not a minute-by-minute scribble. An update policy drops the -127 readings from loose probe cables, a materialised view keeps the hourly average per tank. The morning check reads one row per hour instead of sixty.
