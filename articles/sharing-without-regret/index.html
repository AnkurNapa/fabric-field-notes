Sharing without regret: items, apps and workspaces

Three ways to give someone a report in Fabric, what each one really grants and how to pick the least access that works. Includes the trap that catches most teams: row-level security does nothing for Admins, Members or Contributors.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 1 Ankur Napa GovernanceSecurityPower BI

Short answer

Workspace roles are for the people who build. Apps are for the people who read. Direct item sharing is for the odd one-off. Give builders Contributor or Member, give readers an app audience or the Viewer role and keep Admin to two or three named people. Then remember the rule that breaks most security designs: row-level security (RLS) on a semantic model only filters people who can read but not edit it. Admin, Member and Contributor all have edit rights on every semantic model in the workspace, so RLS does not apply to them at all.

What you will build

Harbour Goods, a fictional retailer, has a sales report over a small star schema: orders, products, stores and dates. Regional managers should see only their own region. You will:

  • Add a static RLS role so the North manager sees only North stores.
  • Set workspace roles for the build team.
  • Publish an app to the managers.
  • Share one report directly with a single person, without letting them reshare it.
  • Prove what each person can see.

Before you start

  • The model and report from A star schema that behaves, built on star-schema-that-behaves.csv (110 synthetic orders, prices in INR). Add one more measure: Orders = COUNTROWS ( orders ).
  • A Fabric workspace where you are Admin, for example Harbour Goods Sales.
  • Security groups, not individuals, for each audience. A group outlives the person who left in March.
  • Licences. Publishing an app needs a Pro licence and the Member role or higher. App readers need Pro or Premium Per User unless the workspace sits on an F64 or larger capacity, where a free licence is enough.

Step 1: define the RLS role in Desktop

  1. In Power BI Desktop, select Modeling > Manage roles.
  2. Select New and name the role North.
  3. Under Select tables choose stores. Under Filter data set region equals North. In the DAX editor that reads [region] = "North".
  4. Save, then select Modeling > View as, tick North and select OK.

The cards should drop to the North figures. The filter sits on the stores dimension and flows down the one-to-many relationship to orders, which is why the star schema shape matters here too. Select Stop viewing when you are done.

Step 2: publish and give the builders a workspace role

  1. Select Publish and choose your workspace.
  2. In the workspace select Manage access (on some layouts it sits under the ... menu), then Add people or groups.
  3. Add the build team group as Contributor. Add a second owner as Admin so you are not the single point of failure.

Contributor can create and edit items, run notebooks and read all data in the workspace. It cannot add people or share the workspace. That is the right default for builders. Member adds the ability to share and add other people. Hand it out sparingly.

Step 3: map the managers to the role

  1. In the workspace, hover over the semantic model, select ... > Security.
  2. Select the North role and add the North managers group. Select Save.
  3. Select ... next to the role, then Test as role. The report opens with a Now viewing as header showing the role in force.

Step 4: publish the app

  1. In the workspace select Create app.
  2. On Setup, name it Harbour Goods Sales and add a one-line description.
  3. On Content, select Add content and add the report.
  4. On Audience, add the North managers group to an audience. Under the audience's advanced settings, leave the options to share the semantic models and build content switched off.
  5. Select Publish app and copy the link.

App audiences get read access to the content in the app and to the semantic model behind it, without seeing anything else in the workspace. RLS still applies because they do not have edit rights.

Step 5: share one report, narrowly

For the finance analyst who needs the report once:

  1. Open the report and select Share.
  2. Choose Specific people and enter the name.
  3. Open the link settings and clear Reshare and Build. On some layouts the labels read as allowing recipients to share the report and to build content with its data.
  4. Send the link.

Reshare lets them pass access on up to the level they hold. Build lets them connect Excel or a new report straight to the model. Neither is needed to read a page.

The North figures cover two stores, ST-019 in Delhi and ST-021 in Jaipur.

The last row is the trap. Someone asks the North manager to "just help with a measure" and adds them to the workspace as Contributor. They are still in the North role. They now see every region, because Contributor carries edit rights on the semantic model and RLS is not enforced for anyone with edit rights. Nothing warns you. Remove the workspace role and the filter returns the next time they sign in.

Where this breaks

  • RLS on editors. As above. If someone must both edit and be filtered, give them a copy of the model in a separate workspace, not an exception in this one.
  • Hidden is not secured. Content hidden from an app's navigation can still be opened by anyone in the audience who has a direct link. Leave sensitive items out of the app instead of hiding them.
  • App access without RLS means all the data. App readers get read on the semantic model. Without an RLS role, a reader with Build permission can query every row, including tables the report never shows.
  • Delays. Workspace role changes take effect the next time the person signs in. Revoking an item permission can take up to two hours to bite for someone already signed in. Plan incident response around that.
  • Data outside the model. RLS on the semantic model does not stop a Contributor opening the lakehouse behind it. Data-plane security in OneLake and SQL is a separate layer for another article.
  • Service principals. They cannot be added to an RLS role, so an app that queries as a service principal sees everything.

On the brewhouse floor

A distillery stores maturing casks in three bonded warehouses, each with its own manager who signs off stock for the excise officer. Build one stock report, add an RLS role per warehouse on the warehouse dimension and publish an app with one audience per manager. Each manager then sees only the casks they are answerable for. The day the production lead asks to add a warehouse manager to the workspace "so they can fix a visual", check the role first: as Contributor, that manager sees every cask on site.
