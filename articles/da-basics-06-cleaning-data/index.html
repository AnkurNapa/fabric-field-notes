Data analysis basics, lesson 6 of 8

Cleaning data: blanks, duplicates and wrong types

Lesson 6 of Data analysis basics. Count what is wrong before you fix anything, decide what each bad row means, then save the rules as a view so every later query uses clean data. On Harbour Goods the quarter's revenue drops by 2,350 INR and September's top store changes.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa Lakehouse

Short answer

Cleaning data means finding the rows that would make an answer wrong and deciding, one by one, what to do with them. You do not edit the source. You write the rules into a view, a saved query that behaves like a table. Then you query the view instead. The order matters: count the problems first, decide what each one means, then filter. Deleting rows without understanding them is not cleaning. It is hiding.

Why it matters for your career

Every analyst spends a large part of the week on this. The habit shows in interviews too. Saying "I found a duplicate till line and a date that does not exist, here is what I did with them" earns more trust than a polished chart built on the raw table.

The idea

Harbour Goods has four kinds of problem in its 60 order lines. Each needs a decision, not only a filter.

ProblemRowLikely causeDecisionChange to revenue

Together they take the quarter from 156,269.85 INR down to 153,919.85 INR, exactly the 2,350 INR lesson 4 warned you about. The unknown store ST-099 from lesson 5 stays in. Its sale is real; only the store list is wrong, so you report it rather than drop it.

Now the wrong types. Every column has a data type: whole number, decimal, date or text. When Load to tables reads a CSV it guesses each type from the values. One value that is not a real date, such as 2026-09-31, can make it keep the whole order_date column as text. That is why lesson 1 told you not to worry about it. The fix is TRY_CAST, which converts a value and returns NULL instead of an error when it cannot. It works whether the column arrived as text or as a date.

Try it in Fabric

Open lh_harbour from lesson 1, switch the ribbon dropdown to SQL analytics endpoint and select New SQL query.

  1. Profile first. Count each problem before you touch anything:
SELECT
    COUNT(*)                                       AS all_rows,
    COUNT(*) - COUNT(DISTINCT order_id)            AS repeated_ids,
    SUM(CASE WHEN quantity IS NULL THEN 1 ELSE 0 END) AS blank_quantity,
    SUM(CASE WHEN quantity <= 0 THEN 1 ELSE 0 END)    AS zero_or_negative,
    SUM(CASE WHEN TRY_CAST(order_date AS date) IS NULL THEN 1 ELSE 0 END) AS impossible_dates
FROM dbo.orders;
  1. Save the rules as a view. The endpoint is read only for data but you can create views:
CREATE VIEW dbo.orders_clean AS
SELECT DISTINCT
    order_id,
    TRY_CAST(order_date AS date) AS order_date,
    store_id,
    product_id,
    quantity,
    unit_price,
    discount,
    CAST(quantity * unit_price * (1 - discount) AS decimal(12,2)) AS revenue_inr
FROM dbo.orders
WHERE quantity > 0
  AND TRY_CAST(order_date AS date) IS NOT NULL;

DISTINCT drops the repeated line. quantity > 0 removes both the negative row and the blank one, because a NULL is never greater than zero. The date test removes 2026-09-31.

  1. Select Refresh in the Explorer. orders_clean appears under Views.
  2. Check it: SELECT COUNT(*) AS order_lines, SUM(revenue_inr) AS revenue_inr FROM dbo.orders_clean;
  3. Rerun the September question from lesson 2 against the view:
SELECT store_id, COUNT(*) AS order_lines, SUM(revenue_inr) AS revenue_inr
FROM dbo.orders_clean
WHERE order_date >= '2026-09-01' AND order_date < '2026-10-01'
GROUP BY store_id
ORDER BY revenue_inr DESC;

Check it worked. Step 1 returns 60, 1, 1, 1 and 1. Step 4 returns 56 order lines and 153919.85. In step 5 ST-011 leads with 9345.00, ST-019 is second with 8039.25 and ST-014 falls from first to third with 6681.15. In lesson 2 ST-014 was top only because of an order dated a day that does not exist.

Common beginner mistakes

  • Cleaning before counting. If you do not know how many rows each rule removes, you cannot explain the new total. Profile first.
  • Treating every odd row as rubbish. The return in HG-40057 is real business. It belongs in a returns figure, not in sales.
  • Fixing the copy instead of the source. Tell the person who owns the till data. Otherwise the same rows come back next month.
  • Cleaning in every query. Put the rules in one view. Five reports with five slightly different filters will disagree.
  • Silently dropping rows. Write down what you removed and why, with the order ids. Someone will ask.

On the brewhouse floor

Brewery A logs a gravity reading for each fermenter every morning. The log has the same four problems. A reading saved twice, a blank where the sample was spilt, a reading of 1012 with the decimal point missing and a date of 31 September. Count them first, then decide: keep one copy, ask about the blank, correct 1012 to 1.012 only if the brewer confirms it. A cleaning view keeps the fermentation chart honest without touching the original log.
