Notebooks for data science: predict delivery time with MLflow

Train a small linear regression that predicts how many hours a delivery takes, in a Fabric notebook, then log the run and register the model with MLflow so the next person can find it, compare it and use it.

Ankur Napa 11 Oct 2026, 7 min read

Short answer

A Fabric notebook already has pandas, scikit-learn and MLflow installed. Read a CSV from the attached lakehouse, train a model, wrap the training in mlflow.start_run() and log the parameters, metrics and model. Fabric stores the run in an Experiment item in your workspace. mlflow.register_model then turns the logged model into an ML model item with a version number. The model is the easy part. The parts that make it useful are a split that respects time, a baseline to beat and a run history someone else can read.

What you will build

Harbour Goods, a fictional retailer, ships orders to customers through three carriers. The delivery log records when each parcel left the warehouse and when it arrived. Operations wants a number to promise customers at checkout.

You will:

  • Load 104 delivery records, keep the 97 that were delivered and compute hours in transit.
  • Train a linear regression on distance, parcel count and carrier.
  • Test it on the last 20 deliveries, which the model never saw.
  • Log everything to an MLflow experiment and register the model as delivery_hours_lr.

Before you start

  • A workspace on a Fabric capacity or a Fabric trial, with Contributor or higher.
  • The sample file: notebooks-for-data-science.csv. Synthetic, 104 rows: delivery_id, order_id, dispatched_at, delivered_at, carrier, status, distance_km and parcels.
  • The Spark runtime. Runtime 2.0 became the default for new workspaces on 6 October 2026, while some Learn pages still say 1.3. Check yours in Workspace settings > Spark. The code below uses pandas and scikit-learn only, so it runs on either.

Step 1: lakehouse and file

  1. In your workspace select + New item > Lakehouse. Name it lh_harbour.
  2. Next to Files select ... > Upload > Upload files and upload the CSV.

Step 2: open a notebook on the lakehouse

From the lakehouse ribbon select Open notebook > New notebook. The lakehouse is attached as the default, which also mounts it at /lakehouse/default/ for plain Python file access. Rename the notebook nb_delivery_hours.

Step 3: load and shape the data

Paste into the first cell and run it.

import pandas as pd

df = pd.read_csv(
    "/lakehouse/default/Files/notebooks-for-data-science.csv",
    parse_dates=["dispatched_at", "delivered_at"],
)
print(df["status"].value_counts())

df = df[df["status"] == "Delivered"].copy()
df["hours"] = (df["delivered_at"] - df["dispatched_at"]).dt.total_seconds() / 3600
df = df.sort_values("dispatched_at").reset_index(drop=True)

print(len(df), round(df["hours"].mean(), 2))   # expect 97 and 20.73
print(df.groupby("carrier")["hours"].agg(["count", "mean"]).round(2))

Returned and in-transit parcels are dropped on purpose. A returned parcel's "delivered" time measures something else. An in-transit parcel has no answer yet. Including either teaches the model the wrong lesson.

Step 4: split by time, not at random

X = pd.get_dummies(df[["distance_km", "parcels", "carrier"]],
                   columns=["carrier"], drop_first=True, dtype=float)
y = df["hours"]

cut = int(len(df) * 0.8)            # 77 for training, 20 for testing
X_train, X_test = X.iloc[:cut], X.iloc[cut:]
y_train, y_test = y.iloc[:cut], y.iloc[cut:]
print(df.loc[cut, "dispatched_at"]) # first test delivery: 2026-09-03 07:26

A random split would mix September deliveries into training and August ones into testing. The model would then be graded on the past using knowledge of the future. Training on the oldest 80 per cent and testing on the newest 20 per cent mirrors how the model will actually be used. drop_first=True makes Carrier A the reference, so the model learns how much slower or faster B and C are.

Step 5: train and log with MLflow

import mlflow
import mlflow.sklearn
from sklearn.linear_model import LinearRegression
from sklearn.metrics import mean_absolute_error, r2_score

mlflow.autolog(disable=True)        # log explicitly, one clean run
mlflow.set_experiment("exp_delivery_hours")

with mlflow.start_run(run_name="linreg_distance_parcels_carrier") as run:
    model = LinearRegression().fit(X_train, y_train)
    pred = model.predict(X_test)

    baseline_mae = mean_absolute_error(y_test, [y_train.mean()] * len(y_test))
    mae = mean_absolute_error(y_test, pred)
    r2 = r2_score(y_test, pred)

    mlflow.log_params({"features": ",".join(X.columns), "train_rows": cut,
                       "split": "time ordered 80/20"})
    mlflow.log_metrics({"mae_hours": mae, "r2": r2, "baseline_mae_hours": baseline_mae})
    info = mlflow.sklearn.log_model(model, artifact_path="model",
                                    input_example=X_train.head(3))

print(round(model.intercept_, 2), dict(zip(X.columns, model.coef_.round(3))))
print(round(mae, 2), round(r2, 3), round(baseline_mae, 2))

Fabric turns on MLflow autologging by default in notebooks. That is handy for quick experiments, but here it would log a second, automatic set of values alongside yours. Turning it off for this notebook keeps one run with exactly the names you chose. set_experiment creates the Experiment item in your workspace the first time it runs.

The artifact_path argument is the MLflow 2 spelling. Fabric notebooks ship with MLflow 2 by default. If you upgrade to MLflow 3, name="model" is the new form and the old one still works.

Step 6: register the model

mv = mlflow.register_model(info.model_uri, "delivery_hours_lr")
print(mv.name, mv.version)

Refresh the workspace list. You now have two new items: exp_delivery_hours (Experiment) and delivery_hours_lr (ML model, version 1). Open the experiment to see the run, its parameters and metrics. Run the notebook again after a change and you get a second run to compare side by side.

Step 7: use it

loaded = mlflow.sklearn.load_model("models:/delivery_hours_lr/1")
new = pd.DataFrame([{"distance_km": 250, "parcels": 6,
                     "carrier_Carrier B": 1.0, "carrier_Carrier C": 0.0}])
print(round(loaded.predict(new)[0], 1))   # expect about 24.7

Check it worked

  • Status counts: 97 Delivered, 4 In transit, 3 Returned.
  • Mean hours in transit over the 97 deliveries: 20.73. By carrier: Carrier A 31 deliveries averaging 18.62 hours, Carrier B 39 at 23.04, Carrier C 27 at 19.80.
  • Intercept about 5.11. Coefficients about 0.051 hours per kilometre, 0.513 per parcel, +3.737 for Carrier B and -0.864 for Carrier C, both relative to Carrier A.
  • On the 20 test deliveries: mean absolute error 1.86 hours and R² 0.786.
  • Baseline, always predicting the training mean: mean absolute error 3.41 hours.
  • A 250 km, six-parcel delivery with Carrier B: about 24.7 hours.

The baseline matters more than the R². The model roughly halves the error of simply quoting the average. That is the claim you can take to operations. If your figures differ in the third decimal place, that is library versions. If they differ in the first, check the row count after filtering and that the data is sorted before the split.

Where this breaks

  • Leaking the answer. A column such as delivered_at or a status that is only known after arrival must never be a feature. Here the hours are built from it, which is fine for the target and fatal as an input.
  • Twenty test rows. One odd delivery moves the error by a few tenths of an hour. Treat the numbers as a direction, not a guarantee, until you have months of data.
  • New carriers. The dummies encode three carriers. A fourth carrier in production produces a column the model has never seen and the prediction fails. Check the input columns before scoring.
  • Autolog surprises. If you leave autologging on and also call log_model, the experiment fills with runs and models you did not ask for. Pick one approach per notebook.
  • Workspace moves. Experiments and models live in the workspace that created them. Logging from another workspace needs the cross-workspace setup in the MLflow docs.

On the brewhouse floor

A brewery wants to know, on brew day, where a beer will finish. Brewers measure how much sugar is in the liquid before fermentation (original gravity) and again when the yeast has finished (final gravity). The gap between the two decides the strength. Train the same kind of regression on past batches, with original gravity, mash temperature and yeast strain as inputs and final gravity as the target. Split by brew date, beat the "it usually finishes at" baseline and log each run with MLflow. The model gives a confident number on day one. The brewer still takes a sample when the tank goes quiet, because a sluggish yeast pitch never made it into the training data.
