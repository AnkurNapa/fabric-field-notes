Dev to prod without fear: Git integration and deployment pipelines

Connect a dev workspace to Azure DevOps or GitHub, commit and branch, then promote to test and prod with a deployment pipeline. Covers the deployment rule that stops a Direct Lake model in prod reading the dev lakehouse, variable libraries for stage values and the YAML route with a service principal.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa CI/CDGovernance

Short answer

Use one workspace per stage. Connect only the dev workspace to Git and commit from there, working on feature branches in branch workspaces. Promote dev to test to prod with a deployment pipeline, which copies item definitions but never data. Put anything that differs between stages in a variable library or a deployment rule, not in the items. The trap that bites everyone once: a Direct Lake semantic model does not rebind to the next stage's lakehouse on its own, so the prod model keeps reading dev until you fix it. A data source rule fixes it for Direct Lake on SQL. Direct Lake on OneLake does not support rebind rules, so deploy that one from Git with fabric-cicd instead.

What you will build

Three workspaces for the Harbour Goods sales KPI solution from Your first Direct Lake model:

  • ws-harbour-dev, connected to Git on main
  • ws-harbour-test and ws-harbour-prod, fed by a three stage deployment pipeline

Inside each: the lh_sales_gold lakehouse, the nb_build_gold notebook, the sm_sales_kpis model, the rpt_sales_kpis report and a vl_sales variable library.

Why bother for one sales report? I have watched a margin measure get "fixed" directly in a production model at eleven at night before a board pack. It was fixed. Nobody could say what it had been before, which mattered when last month's pack stopped matching. Git is not ceremony. It is the only rollback Fabric has.

Before you start

  • A Fabric capacity or trial for all three workspaces. Put prod on its own capacity if you can, so a heavy test run never throttles it.
  • Workspace Admin on all three. Only an Admin can connect a workspace to Git or create a deployment pipeline from it.
  • Tenant settings on (in OneLake catalog > Govern > Configurations > Tenant settings): Users can synchronize workspace items with their Git repositories, plus Users can synchronize workspace items with GitHub repositories if you use GitHub.
  • An Azure DevOps repo, or a GitHub repo and a fine-grained personal access token with Contents read and write.

Step 1: connect dev to Git

  1. Open ws-harbour-dev and select Workspace settings > Git integration.
  2. Pick Azure DevOps or GitHub.
    • Azure DevOps: select Connect to sign in as your Entra user, or Add account and choose OAuth2 or Service Principal for authentication.
    • GitHub: select Add account, give it a display name and paste the token.
  3. Choose the organisation, project and repository (or the GitHub repository URL), branch main and a folder such as fabric.
  4. Select Connect and sync. If the workspace has items and the branch is empty, the items are written to the branch.

Step 2: commit and branch

  1. Make a change, for example add a description to the Gross margin % measure.
  2. Select the Source control icon at the top of the workspace. The badge shows the number of uncommitted changes.
  3. On Changes, tick the items, write a message ("Describe margin measure") and select Commit.

For anything bigger than a description, branch out instead of committing straight to main:

  1. In Source control, open Branches and select Branch out to workspace.
  2. Name the branch feature/margin-target and a new workspace ws-harbour-margin-target. Tick Select items individually if the workspace is large.
  3. Work and commit in that workspace, raise a pull request into main in Azure DevOps or GitHub, merge it.
  4. Back in ws-harbour-dev, open Source control > Updates > Update all.

Update pulls the whole branch. There is no picking individual items on the way in.

Step 3: create the deployment pipeline

  1. From the Workspaces flyout select Deployment pipelines, then Create pipeline (or + New pipeline).
  2. Name it dp-sales-kpis and keep the three default stages, Development, Test and Production. You can have 2 to 10 stages, but the count is fixed once created.
  3. Assign ws-harbour-dev to Development. Leave Test and Production empty for now.
  4. Select the Test stage, choose Development as the source, tick all items and select Deploy. The pipeline creates the test workspace and copies the definitions. Rename it ws-harbour-test in its settings.

The test lakehouse is now empty. Pipelines move metadata only, so run nb_build_gold in test to load its tables.

Step 4: point the test model at the test lakehouse

Open the test model's lineage: it still reads lh_sales_gold in dev. Direct Lake models do not autobind to the target stage.

If the model is Direct Lake on SQL (created from the SQL analytics endpoint page):

  1. In the pipeline, select the Test stage, then Deployment rules.
  2. Select sm_sales_kpis > Data source rules > + Add rule.
  3. From: the dev SQL analytics endpoint. To: Other, then the test lakehouse's SQL connection string as the server and its SQL analytics endpoint ID as the database.
  4. Save, then deploy Development to Test again. Rules only apply on the next deployment.
  5. Repeat on the Production stage with the prod values.

If the model is Direct Lake on OneLake (the default when you create from the lakehouse), deployment rules cannot rebind it. Deploy it from Git with fabric-cicd and let parameter.yml swap the workspace and lakehouse IDs, as in step 6.

Step 5: a variable library for stage values

Notebooks and pipelines read stage values from a variable library. Semantic models do not.

  1. In ws-harbour-dev select + New item > Variable library, name it vl_sales.
  2. Add a String variable gold_lakehouse with default lh_sales_gold and an Integer variable days_to_load with default 14.
  3. Add value sets Test and Prod, setting days_to_load to 90 and 400.
  4. In the notebook, read the active values:
vl = notebookutils.variableLibrary.getLibrary("vl_sales")
days = vl.days_to_load # 14 in dev, 90 in test, 400 in prod
lakehouse = vl.gold_lakehouse
  1. Commit, deploy to test, then open vl_sales in ws-harbour-test, set the Test value set as active and save. A variable library deployed to an empty stage starts on Default.

Step 6: the code route with a service principal

For approvals, many targets or ID rewriting, deploy from Git with Microsoft's open source fabric-cicd library. The service principal needs workspace access and the tenant setting Service principals can call Fabric public APIs.

parameter.yml in the repo folder rewrites dev GUIDs at deploy time:

find_replace:
  - find_value: "11111111-1111-1111-1111-111111111111" # dev workspace ID
    replace_value:
      test: "$workspace.$id"
      prod: "$workspace.$id"
  - find_value: "22222222-2222-2222-2222-222222222222" # dev lh_sales_gold ID
    replace_value:
      test: "$items.Lakehouse.lh_sales_gold.$id"
      prod: "$items.Lakehouse.lh_sales_gold.$id"

Both GUIDs sit in the OneLake URL of a Direct Lake on OneLake model, so this does the rebind rules cannot. An Azure Pipelines definition that releases on a push to test or prod:

trigger:
  branches:
    include: [test, prod]
  paths:
    include: [fabric/**]

variables:
  - name: target_env
    value: ${{ replace(variables['Build.SourceBranch'], 'refs/heads/', '') }}
  - group: fabric_cicd_secrets # aztenantid, azclientid, azspnsecret

stages:
  - stage: Deploy
    jobs:
      - deployment: Fabric
        environment: $(target_env) # approval gate lives on the environment
        pool:
          vmImage: ubuntu-latest
        strategy:
          runOnce:
            deploy:
              steps:
                - checkout: self
                - task: UsePythonVersion@0
                  inputs:
                    versionSpec: "3.12"
                - script: pip install fabric-cicd azure-identity
                - script: python .deploy/deploy.py --env $(target_env)
                  env:
                    AZ_TENANT_ID: $(aztenantid)
                    AZ_CLIENT_ID: $(azclientid)
                    AZ_CLIENT_SECRET: $(azspnsecret)

deploy.py builds a FabricWorkspace with the target workspace ID, environment, repository_directory="fabric" and the item types in scope, then calls publish_all_items.

One limit to know before you choose a Git provider: a service principal can connect a workspace to Git only for Azure DevOps. Automated GitHub connection with a service principal is not supported. GitHub still works interactively in the portal.

Check it worked

  • ws-harbour-dev shows every item as Synced in Source control. The repo's fabric folder holds sm_sales_kpis.SemanticModel and rpt_sales_kpis.Report.
  • In the pipeline, select Compare between Development and Test. No differences after a fresh deployment.
  • Open the test report. The Net sales card should show the test lakehouse's figure. If test still shows exactly what dev shows, the model is still reading dev. Run nb_build_gold in test with 90 days and dev with 14 days and the two cards stop matching, which is the cheapest rebind test I know.

Where this breaks

  • No autobinding for Direct Lake. This is the one that ships dev data to a prod audience. Check lineage after every first deployment.
  • Rules have conditions. You must own the item to create a rule, rules cannot sit on the first stage and they take effect only at the next deployment. Data source rules only swap to a source of the same type.
  • Data never moves. Pipelines and Git carry definitions. Every stage loads its own tables. A deployment that changes a column type in a model can stop and ask to continue; continuing drops the target model's data until refresh.
  • Switching branch is destructive. Switch branch overwrites every item in the workspace and deletes items that are not in the new branch. You cannot switch with uncommitted changes, so commit first.
  • Service principal through a group. Community reports show Azure DevOps Git operations failing when the service principal gets workspace access only through an Entra group. Add it to the workspace directly.

On the brewhouse floor

Brewery A runs the same three workspaces for its production report. The measure that gets "fixed" late at night there is brewhouse yield: how many litres of finished beer came out of the litres brewed. When that number moves, the head brewer has to know whether the beer changed or the formula did. A commit history answers that in one click, which no spreadsheet copy named FINAL_v3 ever has.
