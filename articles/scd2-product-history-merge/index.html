Keep history in a dimension: SCD type 2 with MERGE

Build a product dimension that keeps every price change, recategorisation and discontinued line as history. Dedupe the daily extract with row_number, apply it with one Delta MERGE in PySpark, then do the same in a Fabric Warehouse with T-SQL MERGE. Margin stays consistent with cost and price at every step.

Ankur Napa 11 Oct 2026, 9 min read

Short answer

Keep one row per version of each product, with valid_from, valid_to and is_current. For each extract, first cut it to one row per product with row_number(), because MERGE fails when two source rows hit the same target row. Then run a single Delta MERGE that closes changed rows, inserts their new versions, inserts new products and closes products that vanished from a full snapshot. In a Fabric Warehouse, T-SQL MERGE is generally available and does the same job in one explicit transaction with a follow-up INSERT.

What you will build

A dim_product table for Harbour Goods, a retailer with 25 products over three extracts from its product master:

  • three products moved to a different category, then one moved back
  • two products repriced
  • one new product launched
  • two products discontinued, so they disappear from the extract
  • one extract sent twice and one row keyed with a price ten times too high, then corrected

That last one is the case I always design for. Somebody on the category team edits the price sheet, types 4990 for a ₹499 glass container, notices half an hour later and sends the row again. The extract now has two versions of the same product on the same day. A dimension that keeps the first one is wrong. A dimension that crashes on it is worse.

Every row carries a margin, calculated as list price minus unit cost, over list price. A product costing ₹240 and selling at ₹449 runs at 46.5%. Last quarter's margin report has to use last quarter's price, so a dimension that overwrites a price change rewrites history on paper.

Before you start

  • A workspace on a Fabric capacity or trial, Contributor or higher.
  • Spark runtime 1.3 or 2.0. Both ship a Delta version with whenNotMatchedBySource. Runtime 2.0 became the default on 2026-10-06, though some Learn pages still say 1.3, so check Workspace settings > Spark.
  • The sample: scd2-product-history-merge.csv. 96 synthetic rows across batch dates 2026-09-01, 2026-09-15 and 2026-10-01.

Step 1: land the extract as bronze

  1. In the workspace select + New item > Lakehouse, name it lh_retail.
  2. In the explorer select ... next to Files > Upload > Upload files and upload the CSV.
  3. From the ribbon select Open notebook > New notebook. Run:
from pyspark.sql import Window, functions as F
from delta.tables import DeltaTable

bronze = (spark.read.option("header", True).csv("Files/scd2-product-history-merge.csv")
          .select(F.to_date("batch_date").alias("batch_date"),
                  F.to_timestamp("extracted_at").alias("extracted_at"),
                  "product_id", "name", F.to_date("launched").alias("launched"),
                  "category",
                  F.col("unit_cost").cast("decimal(10,2)").alias("unit_cost"),
                  F.col("list_price").cast("decimal(10,2)").alias("list_price")))
bronze.write.mode("overwrite").format("delta").saveAsTable("bronze_product_snapshot")

I drop the extract's own margin_pct column on purpose. The dimension recalculates it from cost and price, so a typo in one field cannot leave the three numbers disagreeing.

Step 2: create the dimension

spark.sql("""
CREATE TABLE IF NOT EXISTS dim_product (
  product_id STRING, name STRING, launched DATE, category STRING,
  unit_cost DECIMAL(10,2), list_price DECIMAL(10,2), margin_pct DECIMAL(5,1),
  row_hash STRING,
  valid_from DATE, valid_to DATE, is_current BOOLEAN, end_reason STRING
) USING DELTA""")

Step 3: dedupe and merge one batch

TRACKED = ["category", "unit_cost", "list_price"]

def apply_batch(batch_date):
    dim = DeltaTable.forName(spark, "dim_product")
    latest = spark.table("dim_product").agg(F.max("valid_from")).first()[0]
    if latest is not None and str(latest) >= batch_date:
        print(f"skip {batch_date}: already applied") # makes reruns safe
        return

    # 1 one row per product: the latest extract wins
    w = Window.partitionBy("product_id").orderBy(F.col("extracted_at").desc())
    src = (spark.table("bronze_product_snapshot")
           .where(F.col("batch_date") == batch_date)
           .withColumn("rn", F.row_number().over(w)).where("rn = 1").drop("rn")
           .withColumn("margin_pct", F.round((F.col("list_price") - F.col("unit_cost"))
                       / F.col("list_price") * 100, 1).cast("decimal(5,1)"))
           .withColumn("row_hash", F.sha2(F.concat_ws("|", *[F.coalesce(F.col(c).cast("string"),
                       F.lit("~")) for c in TRACKED]), 256)))

    # 2 changed products need two actions: close the old row, insert a new one.
    # A copy with a NULL merge key can never match, so it lands in WHEN NOT MATCHED.
    current = spark.table("dim_product").where("is_current").select("product_id", F.col("row_hash").alias("old_hash"))
    changed = (src.join(current, "product_id")
               .where("row_hash <> old_hash").drop("old_hash")
               .withColumn("merge_key", F.lit(None).cast("string")))
    staged = src.withColumn("merge_key", F.col("product_id")).unionByName(changed)

    (dim.alias("t")
        .merge(staged.alias("s"), "t.product_id = s.merge_key AND t.is_current = true")
        .whenMatchedUpdate(condition="t.row_hash <> s.row_hash",
            set={"is_current": "false", "valid_to": "s.batch_date", "end_reason": "'changed'"})
        .whenNotMatchedInsert(values={
            "product_id": "s.product_id", "name": "s.name", "launched": "s.launched",
            "category": "s.category", "unit_cost": "s.unit_cost", "list_price": "s.list_price",
            "margin_pct": "s.margin_pct", "row_hash": "s.row_hash",
            "valid_from": "s.batch_date", "valid_to": "CAST(NULL AS DATE)",
            "is_current": "true", "end_reason": "CAST(NULL AS STRING)"})
        # 3 deletes: a current product missing from a FULL snapshot was discontinued
        .whenNotMatchedBySourceUpdate(condition="t.is_current = true",
            set={"is_current": "false", "valid_to": f"DATE'{batch_date}'",
                 "end_reason": "'discontinued'"})
        .execute())

for b in ["2026-09-01", "2026-09-15", "2026-10-01"]:
    apply_batch(b)

Three details carry the whole pattern:

  • row_number() over extracted_at descending picks the corrected ₹499 row over the 4990 typo. dropDuplicates(["product_id"]) would keep whichever row Spark met first, which is not a rule you can explain to an auditor.
  • The hash compares only tracked attributes. name and launched are treated as fixed, so they are not in it. coalesce stops a null from silently dropping out of concat_ws.
  • It is one MERGE, so one Delta commit. The two-step version (update, then append) is easier to read but leaves a window where a product has no current row if the second step fails.

Step 4: the same thing in a Warehouse

If your gold layer lives in a Fabric Warehouse, T-SQL MERGE is generally available there. Fabric's MERGE has no OUTPUT clause, so the new versions of changed products go in with an INSERT inside the same transaction. Create a warehouse wh_retail in the same workspace, then in a new SQL query:

CREATE TABLE dbo.dim_product (
  product_id varchar(10) NOT NULL, name varchar(60) NOT NULL, launched date NOT NULL,
  category varchar(20) NOT NULL,
  unit_cost decimal(10,2) NOT NULL, list_price decimal(10,2) NOT NULL, margin_pct decimal(5,1) NOT NULL,
  valid_from date NOT NULL, valid_to date NULL, is_current bit NOT NULL, end_reason varchar(12) NULL
);

Then, once per batch:

DECLARE @batch date = '2026-09-15';

BEGIN TRANSACTION;

WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY product_id ORDER BY extracted_at DESC) AS rn
  FROM lh_retail.dbo.bronze_product_snapshot
  WHERE batch_date = @batch
), src AS (
  SELECT product_id, name, launched, category, unit_cost, list_price,
         CAST(ROUND((list_price - unit_cost) / list_price * 100, 1) AS decimal(5,1)) AS margin_pct
  FROM ranked WHERE rn = 1
)
MERGE dbo.dim_product AS t
USING src AS s
  ON t.product_id = s.product_id AND t.is_current = 1
WHEN MATCHED AND (t.category <> s.category OR t.unit_cost <> s.unit_cost
               OR t.list_price <> s.list_price)
  THEN UPDATE SET is_current = 0, valid_to = @batch, end_reason = 'changed'
WHEN NOT MATCHED BY TARGET
  THEN INSERT (product_id, name, launched, category, unit_cost, list_price, margin_pct,
               valid_from, valid_to, is_current, end_reason)
       VALUES (s.product_id, s.name, s.launched, s.category, s.unit_cost, s.list_price,
               s.margin_pct, @batch, NULL, 1, NULL)
WHEN NOT MATCHED BY SOURCE AND t.is_current = 1
  THEN UPDATE SET is_current = 0, valid_to = @batch, end_reason = 'discontinued';

INSERT INTO dbo.dim_product (product_id, name, launched, category, unit_cost, list_price,
                             margin_pct, valid_from, valid_to, is_current, end_reason)
SELECT b.product_id, b.name, b.launched, b.category, b.unit_cost, b.list_price,
       CAST(ROUND((b.list_price - b.unit_cost) / b.list_price * 100, 1) AS decimal(5,1)),
       @batch, NULL, 1, NULL
FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY product_id ORDER BY extracted_at DESC) AS rn
  FROM lh_retail.dbo.bronze_product_snapshot WHERE batch_date = @batch
) AS b
JOIN dbo.dim_product AS c
  ON c.product_id = b.product_id AND c.valid_to = @batch AND c.end_reason = 'changed'
WHERE b.rn = 1;

COMMIT TRANSACTION;

The semicolon after MERGE is required in Fabric. The three-part name reads the lakehouse table through its SQL analytics endpoint, which works because both items sit in the same workspace.

Check it worked

Run this in the notebook after all three batches:

spark.sql("""
SELECT count(*) AS rows, sum(CAST(is_current AS INT)) AS current_products,
       sum(CASE WHEN is_current THEN list_price END) AS current_list_total,
       sum(CASE WHEN end_reason = 'discontinued' THEN 1 END) AS discontinued
FROM dim_product""").show()

Expected: 31 rows, 23 current products, ₹14,987.00 of list price across the current rows, 2 discontinued. P-0005 should have three versions (Kitchen, Home, Kitchen again). P-0014 should have two, at ₹449 and ₹499. Neither should say 4990. Run apply_batch("2026-10-01") again: it prints skip and the counts do not move.

Where this breaks

  • Duplicates in the batch. Skip the dedupe and Delta MERGE fails with a multiple source rows error, or worse in a hand-rolled version, inserts both rows. Dedupe the source batch to one row per key every time.
  • Deletes on an incremental feed. whenNotMatchedBySource only means "discontinued" when the extract is a full snapshot. Point it at a changes-only feed and it closes every product that did not change that day. Watermark loads cannot see deletes at all. For changes-only sources you need CDC or an explicit delete flag. Copy job offers SCD type 2 as a write method on CDC sources if plain history is all you need.
  • Warehouse write conflicts. Fabric Warehouse uses snapshot isolation with table-level conflict detection. Two jobs merging into dim_product at once fail with error 24556 or 24706, even when the MERGE only inserts. Run one writer per table and add a retry with backoff.
  • Backfilling out of order. The guard in apply_batch refuses a batch older than the newest valid_from. Remove it to backfill and you will close rows with a valid_to earlier than their valid_from. Backfills need a rebuild from bronze, not a merge.
  • Hashing floats. If prices arrive as double, 499.0 can hash differently from 499.00 after a round trip and every product "changes" every day. Cast to a fixed decimal before hashing, as the bronze step does.

Next on the roadmap

This is SCD type 2 with MERGE (eng-2-3) with the delete half of Incremental loads and deletes (eng-2-2). Next is orchestration and errors (eng-2-4): put apply_batch in a pipeline with a retry policy and an alert when a batch is skipped twice in a row.

On the brewhouse floor

A whisky distillery keeps the same kind of history for its casks. Each cask moves between warehouses, gets measured again for volume and strength and is eventually emptied. The duty owed is worked out from litres of pure alcohol: bulk litres times strength. The cask ledger is a type 2 dimension keyed on cask number, with warehouse, volume and strength as the tracked columns and an emptied cask closed by the same not-matched-by-source branch. The 4990 price typo has a twin there too: a rack position keyed as R9-99 instead of R5-19 on the warehouse tablet. row_number() picks the correction the same way.
