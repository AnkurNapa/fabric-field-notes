Day-one tenant hardening: settings that matter before anyone builds

Six weeks into a Fabric pilot, 29 tenant settings were open to the whole organisation and four reports were public on the web. Pull every setting into a notebook, count what is open, scope it to named security groups and prove the count went down.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa GovernanceSecurity

Short answer

Tenant settings decide who can create, share, export and switch on AI before any workspace role comes into play. Most of them start life open to everyone. Nobody notices until a report turns up on a public URL. On day one, list every setting with Semantic Link, count the ones enabled for the entire organisation, then scope each one to a named security group or switch it off on purpose. Keep the Fabric administrator role to two to four people. Remember the one thing tenant settings are not: security. Turning off an export button does not stop someone with Read on a semantic model from querying it.

The symptom

Harbour Goods, the fictional retailer used across this site, started a Fabric pilot without touching the admin portal. Six weeks later a review found:

  • Anyone could create a workspace. Sixty-one had appeared, eleven of them called some version of "test".
  • Four reports were live through Publish to web, one of them showing store-level margins.
  • Copilot was available to every user, on a capacity in Central India, with nobody having read the data residency settings.
  • Guests invited for one supplier project could browse content far beyond it.

Nothing had leaked that anyone knew of. That is not the same as nothing having leaked.

Measure it

1. Every tenant setting, in one table. A Fabric administrator opens a notebook and runs:

import sempy.fabric.admin as fadmin

ts = fadmin.list_tenant_settings()
print(len(ts))

def open_to_all(row):
    groups = row["Enabled Security Groups"]
    return bool(row["Enabled"]) and (groups is None or len(groups) == 0)

open_df = ts[ts.apply(open_to_all, axis=1)]
print(len(open_df))
display(open_df[["Tenant Setting Group", "Title"]].sort_values("Tenant Setting Group"))

list_tenant_settings wraps the Fabric REST API Tenants - List Tenant Settings and returns each setting's title, group, whether it is enabled and which security groups it is scoped to. Save the output as a Delta table with today's date. You will want the before picture later.

2. The settings worth reviewing. The sample day-one-tenant-hardening.csv holds the 43 settings the Harbour Goods review covered, their state before and after plus one line on why. At the start, 29 of the 43 were enabled for the entire organisation and the other 14 were off.

3. Public reports. In OneLake catalog > Govern (or Admin portal where Govern has not reached your region), open Embed codes. Four active codes. Note who created each one.

4. Workspace sprawl. Under Govern > Workspaces, sort by creation date and count what appeared since the pilot began. Sixty-one.

Fix it

Create the security groups in Microsoft Entra first. Scoping a setting to a group that does not exist yet means scoping it to nobody. Harbour Goods used nine: sg-fabric-workspace-creators, sg-fabric-builders, sg-fabric-automation, sg-fabric-ai-pilot, sg-fabric-approved-guests, sg-fabric-guest-inviters, sg-fabric-data-sharing, sg-fabric-platform and sg-fabric-governance-readers.

Then go to OneLake catalog > Govern > Configurations > Tenant settings. Changes take up to 15 minutes to reach everyone; the Copilot and data agent settings can take up to an hour.

Step 1: who can create

  • Create workspaces: specific security groups, sg-fabric-workspace-creators. Workspace requests now go through a short form, which is also where the workspace gets its domain.
  • Users can create Fabric items: sg-fabric-builders. This blocks Fabric items such as lakehouses and notebooks, not Power BI items. Capacity admins can override it per capacity, which is useful for a training capacity.
  • Users can try Microsoft Fabric paid features: off, so nobody starts a trial capacity outside the plan.

Step 2: who can share outside

  • Publish to web: disabled. Learn is blunt about this one: published reports need no authentication to view. With the setting disabled for the whole organisation, existing embed codes stop rendering too.
  • Guest users can access Microsoft Fabric: sg-fabric-approved-guests. Users can invite guest users to collaborate through item sharing and permissions: sg-fabric-guest-inviters. Guest users can browse and access Fabric content: off, so guests see only what is shared with them.
  • External data sharing and Users can accept external data shares: sg-fabric-data-sharing. A read-only link to a lakehouse is still data leaving the tenant.
  • Allow shareable links to grant access to everyone in your organization: off. Links should name people or groups.

Step 3: who can automate

  • Service principals can call Fabric public APIs and Service principals can create workspaces, connections, and deployment pipelines: sg-fabric-automation, which holds only your deployment identities.
  • Service principals can access read-only admin APIs: sg-fabric-governance-readers, for the inventory job that reruns the notebook above every week.
  • Block ResourceKey Authentication: on.

Step 4: who can use AI

  • Users can use Copilot and other features powered by Azure OpenAI: sg-fabric-ai-pilot. Copilot runs as the user and sees exactly what they can see, so fix over-sharing before widening it.
  • The two Data sent to Azure OpenAI can be processed outside and can be stored outside your capacity's geographic region settings are required for Copilot and data agents at all on a capacity in India. Azure OpenAI for Fabric runs in the US and the EU Data Boundary. Scope them to the pilot group and get a written sign-off from whoever owns data residency first. Data agent chat history is stored for up to 28 days.

Step 5: labels before content

Turn on Allow users to apply sensitivity labels for content, Apply sensitivity labels from data sources to their data in Power BI and Automatically apply sensitivity labels to downstream content. Labels applied on day one cost nothing. Labels applied to 400 existing items cost a project.

Step 6: keep some things open, on purpose

Six settings stayed enabled for everyone, each with a reason written in the CSV: semantic model reuse across workspaces, Export to Excel, Export to .csv, DirectQuery to Power BI semantic models, the XMLA and Analyze in Excel setting and usage metrics for creators. Blocking Excel export does not stop anyone; it moves the export to screenshots and makes the label on the exported file impossible to apply.

Prove it

Rerun the notebook from step 1 the next day and compare with the saved snapshot.

BeforeAfter
Reviewed settings enabled for the entire organisation29 of 4316 of 43
Of those, open on purpose with a written reason06
Of those, protections and labelling switches that belong everywhere010
Settings scoped to a named security group019
Settings switched off14, never reviewed8, by decision
Active Publish to web embed codes40
People who can create a workspaceEveryoneMembers of one group

The headline is not 29 to 16. It is that every one of the 43 now has an owner and a reason. Thirty-seven settings changed state; the six that did not were re-confirmed rather than left alone.

Where this breaks

  • Tenant settings are not security. Switching off export does not remove Read on a semantic model. Workspace roles, item permissions, row level security and OneLake security do the actual protecting.
  • Delegation to capacity admins. Settings such as Users can create Fabric items and the Copilot switch can be overridden at capacity level. Check capacity settings too, or a capacity admin can quietly undo step 1.
  • New settings arrive switched on. Microsoft adds tenant settings most months, often preview features. A banner at the top of the page lists new and changed ones. Rerun the notebook weekly and diff it against last week's snapshot.
  • Template apps still create workspaces. Installing a template app creates a workspace even when Create workspaces is restricted.
  • Too many Fabric administrators. The role can undo every line in this article. Two to four named people, with Privileged Identity Management if you have it.

On the brewhouse floor

A winery's riskiest Fabric moment is harvest. Winery A brings in a grower liaison and a contract lab for eight weeks, both as guests, both needing one report on grape intake and sugar readings by block. With the default settings they could browse everything else the winery had shared internally, including grower payment rates. Scoping guest access to an approved group and turning off guest browsing means each contractor sees their one report and nothing else. When harvest ends, removing two people from one group closes it.
