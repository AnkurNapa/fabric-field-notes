User data functions: one set of business rules, called from everywhere

Write a Python user data function that validates and repairs store issue reports, test it in the portal, publish it, then call it from a notebook and land clean and rejected rows in Delta. With the limits that decide when a function is the right tool and when Spark is.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa LakehouseSpark

Short answer

A user data functions item hosts Python functions on serverless compute inside Fabric. You write them once and call them from notebooks, pipelines, Activator rules, Power BI translytical task flows or any application through a REST endpoint. They suit small, shared business rules: validation, lookups, write-back and calls to other APIs. They do not suit bulk data movement. A request is capped at 4 MB, a run at 240 seconds and a call through the public endpoint at 100 seconds. When the same rule must give the same answer in a notebook, a pipeline and a report button, a function is the place to keep it. When you need to touch a million rows, use Spark.

What you will build

Harbour Goods stores report delivery problems through a form: wrong item, damaged, missing or late. The form came from a low-code tool and it validates nothing. Store codes arrive as ST-014, st-14 and ST14. Severity is meant to be 1 to 5 and someone has typed 9. The same complaint gets submitted twice because the confirmation screen is slow.

Today three people clean this three ways: a notebook for the weekly report, a pipeline step for the carrier claims file and a person with a spreadsheet. You will build:

  • A user data functions item udf_store_issues with one function, validate_store_issues, that takes a batch of submissions and returns each one with a status (accepted, repaired or rejected) and its reasons.
  • A notebook that sends the 48 sample submissions to it and writes store_issues_clean and store_issues_rejected Delta tables.

Before you start

  • A workspace on a Fabric capacity in a region where user data functions are available.
  • A lakehouse; the lh_sales_gold lakehouse from earlier walkthroughs is fine.
  • The sample: user-data-functions.csv. 48 synthetic submissions with columns submission_id, store_id, order_id, issue_type, severity and note. Upload it to the lakehouse Files area. The last twelve rows are the messy ones.

Step 1: create the item

  1. In the workspace select + New item, search for User data functions and select it.
  2. Name it udf_store_issues and select Create.
  3. Select New function. A sample hello_fabric function opens in the editor.
  4. Check you are in Develop mode (mode selector, top right).

Step 2: write the function

Replace everything in the editor with this:

import datetime
import fabric.functions as fn
import logging
import re

udf = fn.UserDataFunctions()

VALID_ISSUES = {"wrong_item", "damaged", "missing", "late"}
STORE_RE = re.compile(r"^ST-?(\d{1,3})$")
ORDER_RE = re.compile(r"^HG-\d{5}$")


def _check(row: dict, seen: set) -> dict:
    reasons, repaired = [], False

    raw_store = str(row.get("store_id", "")).strip().upper()
    match = STORE_RE.match(raw_store)
    store = f"ST-{int(match.group(1)):03d}" if match else raw_store
    if not match:
        reasons.append("bad store_id")
    elif store != row.get("store_id"):
        repaired = True

    order = str(row.get("order_id", "")).strip()
    if not ORDER_RE.match(order):
        reasons.append("bad order_id")

    issue = str(row.get("issue_type", "")).strip().lower()
    if issue not in VALID_ISSUES:
        reasons.append("unknown issue_type")

    try:
        severity = int(row.get("severity"))
    except (TypeError, ValueError):
        severity = None
    if severity is None or not 1 <= severity <= 5:
        reasons.append("severity out of range")

    key = (store, order, issue)
    if not reasons and key in seen:
        reasons.append("duplicate")
    if not reasons:
        seen.add(key)

    status = "rejected" if reasons else ("repaired" if repaired else "accepted")
    return {"submission_id": row.get("submission_id"), "store_id": store,
            "order_id": order, "issue_type": issue, "severity": severity,
            "status": status, "reasons": ", ".join(reasons)}


@udf.function()
def validate_store_issues(rows: list) -> list:
    seen = set()
    results = [_check(row, seen) for row in rows]
    logging.info("Checked %d submissions", len(results))
    return results

Four choices are deliberate.

  • One call per batch, not per row. Each invocation has overhead. Sending 48 rows in one request is one call; sending them one at a time is 48.
  • Repair what is unambiguous, reject the rest. st-14 and ST14 can only mean ST-014. ST-0141 could be a typo for ST-014 or ST-141, so it is rejected for a human to look at.
  • Duplicates are judged after repair. ST14 plus order HG-40106 plus wrong_item is the same complaint as an earlier ST-014 row. Only the repaired value shows it.
  • Parameter names are camelCase. The programming model requires it. rows is safe; row_list would fail to publish.

The import fabric.functions as fn line and udf = fn.UserDataFunctions() must stay. Without them the functions do not run.

Step 3: test, then publish

  1. Still in Develop mode, use the test capability on validate_store_issues with this input:
[
  {"submission_id": "T-1", "store_id": "st-14", "order_id": "HG-40160", "issue_type": "damaged", "severity": "2"},
  {"submission_id": "T-2", "store_id": "ST-014", "order_id": "HG-40160", "issue_type": "damaged", "severity": "2"}
]

T-1 should come back repaired and T-2 rejected with reason duplicate.

  1. Select Publish. It can take a few minutes. After it completes, the circle icon next to the function in the Functions explorer disappears.

Test runs on Python 3.12 and published functions run on Python 3.11. This code works on both. A library that only installs on 3.12 will pass your test and fail in production, so check versions in Library management before you add one.

Step 4: call it from a notebook

Open a notebook attached to your lakehouse and run:

from pyspark.sql import functions as F

rows = [r.asDict() for r in
        spark.read.option("header", True).csv("Files/user-data-functions.csv").collect()]

fns = notebookutils.udf.getFunctions("udf_store_issues")
results = fns.validate_store_issues(rows=rows)

df = spark.createDataFrame(results)
df.filter(F.col("status") != "rejected").write.mode("overwrite") \
  .format("delta").saveAsTable("store_issues_clean")
df.filter(F.col("status") == "rejected").write.mode("overwrite") \
  .format("delta").saveAsTable("store_issues_rejected")

df.groupBy("status").count().show()

Call getFunctions once and reuse the object; Learn recommends caching it rather than calling it in a loop. Exceptions raised inside the function propagate to the notebook, so a broken publish shows up as a failed cell, not as silently empty tables. If you would rather not type the call, Generate invocation code > Client code on the item's Home tab writes it for you.

Reading the CSV with headers only keeps every value a string, which is what a form sends. The function casts severity itself.

Check it worked

Figures computed in Python by running the same function over the 48-row sample:

StatusRows
accepted36
repaired1
rejected11

So store_issues_clean holds 37 rows and store_issues_rejected holds 11. The rejections break down as three duplicates (SUB-038, SUB-047, SUB-048), three severities out of range (SUB-040 at 0, SUB-041 at 6, SUB-042 at 9), two unknown issue types (SUB-043 broken, SUB-044 lost), two bad order IDs (SUB-045, SUB-046) and one bad store code (SUB-039, ST-0141). The one repair is SUB-037, st-14 to ST-014.

In the clean table, ST-019 Delhi has the most issues with 10. Ten of the 37 are severity 4 or 5.

Where this breaks

  • Duplicates only within a batch. The function is stateless, so it catches repeats inside one call. To catch a complaint sent yesterday and again today, add a Fabric data connection under Manage connections and check the clean table. Learn says lakehouse SQL analytics endpoints are read only from a function, which is fine for a lookup.
  • Only the owner edits. Only the owner of the item can modify and publish code. On a team, transfer ownership deliberately or keep the code in Git with the VS Code extension.
  • Two-minute publish cooldown. After a publish you wait at least two minutes before the next one. That includes Git and deployment pipeline publishes.
  • No service principal on managed connections. Connections managed by the item cannot use a service principal, managed identity or workspace identity.
  • Public endpoint timeout. Called from an external app, a function gets 100 seconds, not 240. Validation like this takes milliseconds; an external API call inside it might not.
  • It is not Spark. For a nightly file of two million rows, put the same rules in a PySpark function and keep the user data function for interactive callers: a report button, an Activator rule or the form itself.

On the brewhouse floor

A distillery's duty and inventory figures all rest on one sum: litres of pure alcohol equal bulk litres times ABV. A 200 litre cask gauged at 63.5 per cent holds 127 LPA. That sum, plus the rounding rule the excise office expects, lives in the gauging spreadsheet, the warehouse notebook and the tax report, each written by a different person in a different year. Put it in one user data function and call it from all three. When a warehouse keeper keys 635 instead of 63.5, the function rejects it before 1,270 LPA lands in the duty return for a cask that only holds 200 litres.
