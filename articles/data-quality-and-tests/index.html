Data quality and tests: checks that run every time

Eighty order rows hide two duplicates, three missing stores, a 31st of September and a 150 per cent discount. Measure the damage, put row rules in a materialised lake view, put set rules in a gate that fails the pipeline and test the gate itself.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa LakehouseSpark

Short answer

Split checks into two kinds. Row rules ask whether one row makes sense: is the date real, is the quantity positive, does the product exist. Put those in a materialised lake view as CONSTRAINT ... CHECK ... ON MISMATCH DROP, so bad rows never reach silver and Fabric counts what it dropped. Set rules ask whether the batch makes sense: are order IDs unique, did we drop more than we can accept, did anything arrive at all. Those cannot be judged one row at a time, so write them as a small notebook gate that raises an error and fails the pipeline. Then test the gate with rows you built to break it, because a check that has never failed has never been proven to work.

The symptom

Harbour Goods' September sales report said net sales of 322,736.80 rupees. Finance's number was lower. Then on 6 October, when Runtime 2.0 became the default for new workspaces, the same load notebook started failing outright with a cast error. Nothing in the code had changed.

Both problems came from the same file. Runtime 1.3 quietly turned a price of N/A into null and carried on. Spark 4 runs in ANSI mode, so the same cast now raises an error. The failure is the more honest of the two outcomes. Check which runtime you are on in Workspace settings > Data Engineering/Science > Spark settings, because some Learn pages still say 1.3 is the default.

Measure it

You need a lakehouse with Lakehouse schemas enabled and two files: data-quality-and-tests.csv (80 September orders) and harbour-goods-products.csv (nine products). Upload both under Files.

Land them as bronze with every column as text, so the load itself can never fail:

spark.sql("CREATE SCHEMA IF NOT EXISTS bronze")

(spark.read.option("header", True).csv("Files/data-quality-and-tests.csv")
      .write.mode("overwrite").format("delta").saveAsTable("bronze.orders_raw"))
(spark.read.option("header", True).csv("Files/harbour-goods-products.csv")
      .write.mode("overwrite").format("delta").saveAsTable("bronze.products"))

Then profile it. One query, one row per rule, so the numbers can sit in a ticket:

WITH o AS (SELECT DISTINCT * FROM bronze.orders_raw)
SELECT
  (SELECT COUNT(*) FROM bronze.orders_raw)                                         AS rows_in,
  COUNT(*)                                                                         AS distinct_rows,
  SUM(CASE WHEN o.store_id IS NULL THEN 1 ELSE 0 END)                              AS missing_store,
  SUM(CASE WHEN try_to_date(o.order_date) IS NULL THEN 1 ELSE 0 END)               AS bad_date,
  SUM(CASE WHEN try_cast(o.quantity AS INT) <= 0 THEN 1 ELSE 0 END)                AS non_positive_qty,
  SUM(CASE WHEN try_cast(o.unit_price AS DECIMAL(10,2)) IS NULL THEN 1 ELSE 0 END) AS bad_price,
  SUM(CASE WHEN try_cast(o.discount AS DECIMAL(4,2)) >= 1 THEN 1 ELSE 0 END)       AS discount_too_big,
  SUM(CASE WHEN p.product_id IS NULL THEN 1 ELSE 0 END)                            AS unknown_product
FROM o
LEFT JOIN bronze.products p ON o.product_id = p.product_id

You should get 80 rows in and 78 distinct, so two exact duplicates (HG-50015 and HG-50035, each loaded twice). Then three orders with no store, one dated 2026-09-31, two with a quantity of zero or minus two, one priced N/A, one with a discount of 1.50 and one for product P-199, which does not exist. That is nine bad rows, each failing exactly one rule.

The report's 322,736.80 included both duplicates (17,715.75 between them) and 14,547.30 from the bad rows, including a negative order and a discount that paid the customer to take a towel. The defensible September figure is 290,473.75.

Fix it

1. Row rules in a materialised lake view. In the lakehouse select Materialized lake views, then New > New notebook > Create with Spark SQL, or run this in any notebook attached to the lakehouse:

CREATE SCHEMA IF NOT EXISTS silver;

CREATE MATERIALIZED LAKE VIEW IF NOT EXISTS silver.orders (
  CONSTRAINT store_present  CHECK (store_id IS NOT NULL) ON MISMATCH DROP,
  CONSTRAINT valid_date     CHECK (order_date IS NOT NULL) ON MISMATCH DROP,
  CONSTRAINT positive_qty   CHECK (quantity IS NOT NULL AND quantity > 0) ON MISMATCH DROP,
  CONSTRAINT price_present  CHECK (unit_price IS NOT NULL AND unit_price > 0) ON MISMATCH DROP,
  CONSTRAINT discount_range CHECK (discount IS NOT NULL AND discount >= 0 AND discount < 1) ON MISMATCH DROP,
  CONSTRAINT known_product  CHECK (product_name IS NOT NULL) ON MISMATCH DROP
) AS
SELECT DISTINCT
  o.order_id,
  try_to_date(o.order_date)                     AS order_date,
  o.store_id,
  o.product_id,
  p.name                                        AS product_name,
  try_cast(o.quantity AS INT)                   AS quantity,
  try_cast(o.unit_price AS DECIMAL(10,2))       AS unit_price,
  try_cast(o.discount AS DECIMAL(4,2))          AS discount
FROM bronze.orders_raw o
LEFT JOIN bronze.products p ON o.product_id = p.product_id;

Four details carry the weight. try_cast and try_to_date return null instead of failing under ANSI mode, so a bad value becomes a dropped row rather than a dead job. Every rule spells out IS NOT NULL AND, so a null cannot slip through as "unknown". The product check is a left join plus a rule, because an inner join would drop P-199 silently with no count. DISTINCT removes exact duplicates before the rules run.

DROP keeps the refresh going and records the count; FAIL, the default when you write no action, stops the refresh at the first violation. If one view has both, FAIL wins. Use FAIL for rules where one bad row means the whole file is wrong.

Schedule the view from Materialized lake views > Manage > Manage schedules. Dropped counts show in the lineage view. The built-in data quality report shows violations over the last week.

2. Set rules in a gate. Add a notebook after the refresh. Keep the logic in a function so it can be tested:

def gate_problems(bronze, silver, max_drop_share=0.15):
    problems = []
    distinct_in = bronze.distinct().count()
    rows_out = silver.count()
    if rows_out == 0:
        problems.append("silver is empty")
    dup_ids = silver.groupBy("order_id").count().filter("count > 1").count()
    if dup_ids:
        problems.append(f"{dup_ids} order_id values appear more than once")
    dropped = distinct_in - rows_out
    if distinct_in and dropped / distinct_in > max_drop_share:
        problems.append(f"dropped {dropped} of {distinct_in} rows")
    return problems

problems = gate_problems(spark.table("bronze.orders_raw"), spark.table("silver.orders"))
if problems:
    raise ValueError("Quality gate failed: " + "; ".join(problems))

A raised error fails the notebook activity, so the pipeline stops before gold and the refresh. The 15 per cent line is a business decision, not a technical one. Agree it with whoever owns the report.

3. Test the gate. Put this in a separate test notebook and run it in a test workspace from your CI through the Fabric REST API. Plain asserts are enough:

b = spark.createDataFrame([("HG-1",), ("HG-2",), ("HG-3",)], ["order_id"])

dupes = spark.createDataFrame([("HG-1",), ("HG-1",), ("HG-2",)], ["order_id"])
assert any("more than once" in p for p in gate_problems(b, dupes))

empty = spark.createDataFrame([], "order_id string")
assert "silver is empty" in gate_problems(b, empty)

clean = spark.createDataFrame([("HG-1",), ("HG-2",), ("HG-3",)], ["order_id"])
assert gate_problems(b, clean) == []
print("gate tests passed")

Check silver directly: SELECT COUNT(*), SUM(quantity * unit_price * (1 - discount)) FROM silver.orders returns 69 and 290,473.75, with dates from 1 to 30 September. Then break it on purpose: append HG-50001 again with a different quantity, trigger a refresh from the lineage view (the button may read Run or Refresh) and run the gate. DISTINCT cannot merge two different rows, so the gate reports one order_id more than once and the pipeline stops.

Where this breaks

  • Runtime support. Learn's materialised lake view quickstart lists a schema-enabled lakehouse and Runtime 1.3 as prerequisites. Confirm the view works on your Runtime 2.0 workspace before you depend on it, or attach a 1.3 environment to the notebook that creates it.
  • Dropped rows vanish. DROP keeps counts, not the rows. If someone must fix them, write the failing rows to a quarantine table in the gate notebook with the same conditions inverted.
  • Missing stores may be real orders. Three online orders with no store are still revenue. Dropping them is a choice; mapping them to an online store code may be the better one. Ask before you decide.
  • The data quality report has limits. It uses DirectQuery and is capped at one million returned rows per query.
  • A small test capacity hides problems. Concurrency and throttling only show up at production volume. Scale the test capacity up for load tests.

On the brewhouse floor

A brew log has the same two kinds of check. Row rules: final gravity must be lower than original gravity and the alcohol worked out from them must make sense. A brew at 1.050 down to 1.010 gives (1.050 - 1.010) x 131.25, which is 5.25 per cent ABV, while a log that shows the beer finishing above where it started is a typo or a stuck fermentation, never a recipe. Set rules: every brew number appears once and every fermenter that was filled this week has a log. The first kind catches a bad entry. The second catches the brew nobody wrote down.
