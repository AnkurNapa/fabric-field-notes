Data engineering basics, lesson 6 of 8

Data quality basics

Lesson 6 of Data engineering basics. Turn vague worries about bad data into five named checks, run them with one SQL query on the Harbour Goods bronze table and find the five rows that would quietly wreck a revenue report.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa Lakehouse

Short answer

Data quality means the data is fit for the job someone will use it for. You cannot check "quality" in general, but you can check specific rules: no duplicates, no missing values in required columns, values in a sensible range, dates that exist, codes that match a known list. Write each rule as a query that counts the rows breaking it. Zero is a pass. Anything else needs a decision: fix, quarantine or accept.

Why it matters for your career

The fastest way to lose trust as a data engineer is a report that is confidently wrong. The fastest way to earn it is to say "three rows failed the date check this morning, here they are" before anyone else notices.

The idea

Most quality problems fall into a few families. Each has a plain name and a simple test:

Check familyQuestion it asksHarbour Goods rule
UniquenessIs each thing recorded once?Each order_id appears once
CompletenessAre required values present?quantity is never blank
ValidityIs the value possible?quantity is above zero; order_date is a real date
ConsistencyDoes it match related data?store_id is one of the six known stores
TimelinessDid it arrive when expected?Yesterday's file landed before 06:00

The bronze table from lesson 5 has one deliberate problem in each of the first four families. None of them stops a load. All of them change the revenue number. That is why quality checks are a separate step: a pipeline that succeeds can still deliver wrong data.

A check needs three parts: the rule, a count of rows that break it and a threshold, the number of failures you will tolerate before stopping the pipeline. Lesson 7 uses a threshold to decide whether the daily run carries on.

Try it in Fabric

Open lh_harbour, switch to the SQL analytics endpoint, select New SQL query and run this quality report against bronze_orders:

WITH known_stores AS (
    SELECT store_id
    FROM (VALUES ('ST-003'), ('ST-007'), ('ST-011'),
                 ('ST-014'), ('ST-019'), ('ST-022')) AS s(store_id)
)
SELECT 'uniqueness: repeated order lines' AS check_name,
       COUNT(*) - COUNT(DISTINCT order_id) AS failing_rows
FROM dbo.bronze_orders
UNION ALL
SELECT 'completeness: missing quantity',
       COUNT(*)
FROM dbo.bronze_orders
WHERE NULLIF(TRIM(quantity), '') IS NULL
UNION ALL
SELECT 'validity: quantity zero or below',
       COUNT(*)
FROM dbo.bronze_orders
WHERE NULLIF(TRIM(quantity), '') IS NOT NULL
  AND TRY_CAST(quantity AS int) <= 0
UNION ALL
SELECT 'validity: impossible order date',
       COUNT(*)
FROM dbo.bronze_orders
WHERE TRY_CAST(order_date AS date) IS NULL
UNION ALL
SELECT 'consistency: unknown store',
       COUNT(*)
FROM dbo.bronze_orders
WHERE store_id NOT IN (SELECT store_id FROM known_stores);

Expected: five checks with 1 failing row each, out of 60 order lines. The known stores are typed into the query to keep this lesson self-contained; in a real build they would come from a stores table.

The completeness check uses NULLIF(TRIM(quantity), '') because a blank value can arrive as an empty string or as NULL depending on how it was copied. The validity check skips blanks on purpose, otherwise SQL Server's habit of converting an empty string to 0 would count the same row twice.

Now look at the actual rows:

SELECT *
FROM dbo.bronze_orders
WHERE order_id IN ('HG-40017', 'HG-40056', 'HG-40057', 'HG-40058', 'HG-40059')
ORDER BY order_id;

You should see six lines: HG-40017 twice, a blank quantity on HG-40056, a quantity of -2 on HG-40057, store ST-099 on HG-40058 and the date 2026-09-31 on HG-40059. Each one has a different likely cause: a till resend, a half-saved order, a return keyed as a sale, a new store missing from the store list and a typing slip. That is the real value of naming checks. The name tells you who to call.

Common beginner mistakes

  • Deleting bad rows silently. Move them to a quarantine table with the reason instead. Lesson 8 does exactly that. Someone will ask where order HG-40058 went.
  • Checking only that the pipeline succeeded. Success is about the machinery, not the data.
  • Rules with no threshold. If one failure stops everything, people learn to switch the check off. Decide how many failures are acceptable.
  • Fixing data in the lakehouse that is wrong at the source. If the store list is missing ST-099, fix the store list. Patching orders hides the problem until next month.
  • Forgetting timeliness. A perfect file that arrives at 11:00 still breaks a 09:00 meeting.

On the brewhouse floor

Distillery A records each cask filling as bulk litres and strength. Duty is charged on litres of pure alcohol: bulk litres times ABV. A cask of 200 litres at 63.5% ABV holds 127 litres of pure alcohol. If someone keys the strength as 63.5 instead of 0.635 in a column that expects a fraction, the same cask shows 12,700 litres of pure alcohol and the duty report is out by a factor of a hundred. A validity rule as plain as "strength between 0 and 1" catches it before the excise return does.
