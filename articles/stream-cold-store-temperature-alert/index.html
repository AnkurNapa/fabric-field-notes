Catch a failing freezer with Eventstream, Eventhouse and Activator

Stream cold-store temperature and humidity through Eventstream into an Eventhouse, chart it in KQL, flag a freezer that has run warm for two hours and let Activator send the message before the morning shift opens the door.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 2 Ankur Napa KQLReal-time

Short answer

Send each reading to an Eventstream custom endpoint, route it straight into an Eventhouse table, then let a KQL query look at the last two hours per sensor. If the latest reading is above the limit and the two-hour average is above it too, that freezer is failing. A defrost cycle or a forklift going through the door is not. Hand the query to Activator, track each sensor as an object and alert when its warm flag becomes true. One message per failure, not one every few minutes.

What you will build

Four Harbour Goods cold stores, one day of synthetic readings every ten minutes, one of them in trouble. Each freezer should run at about -20 °C. Every six hours each one runs a short defrost cycle and climbs to around -14 °C for twenty minutes before pulling back down. In the early hours at WH-03 a door is left on its latch after a late delivery. The store climbs from -20 °C towards -8 °C and stays there, because the compressor cannot beat an open door.

The detail that tells you it is a door and not a compressor: humidity. A failing compressor lets the temperature rise while the air stays as dry as it was. An open door pulls in warm, wet air, so humidity jumps from about 62% to the high 80s within the hour, usually before the temperature has moved far. Put both in the alert and whoever picks it up knows to walk to the door first.

The pieces:

  • An Eventstream with a custom endpoint source.
  • An Eventhouse with a sensor_readings table, fed by direct ingestion.
  • Two KQL queries: a temperature chart and a warm check.
  • An Activator rule that emails or posts to Teams when a cold store becomes warm.

Sample data: stream-cold-store-temperature-alert.csv, 576 readings with reading_time, warehouse_id, sensor_id, temperature_c and humidity_pct. All of it is synthetic.

Before you start

  • A workspace on a Fabric capacity or a trial. Real-Time Intelligence items do not run on Pro alone.
  • Contributor or higher on the workspace to create the Eventstream, Eventhouse and Activator.
  • Python 3.10 or later with pip install azure-eventhub for the sender script.
  • No special tenant switch for SAS key sending. If you want Microsoft Entra authentication on the custom endpoint instead, an admin has to enable Service principals can use Fabric APIs in the admin portal and you need Member on the workspace.

Step 1: create the Eventhouse

  1. In the workspace select New item > Eventhouse, name it coldchain_rti and select Create. Fabric creates a KQL database with the same name.
  2. Leave the table for later. The Eventstream destination wizard creates it from the incoming data.

Step 2: create the Eventstream and custom endpoint

  1. New item > Eventstream, name it es_cold_stores, Create.
  2. On the get-started page select Use custom endpoint, give the source a name such as cold-store-sensors and select Add.
  3. Select Publish.
  4. In live view select the custom endpoint node. On the Details pane open the Event Hub tab, then SAS Key Authentication. Copy Connection string-primary key. It already carries the EntityPath, so the SDK needs nothing else.

Step 3: send the readings

This script replays the sample file and shifts every timestamp so the last reading lands at the current time. That way the two-hour window has something in it the moment you finish.

"""Replay synthetic cold-store readings into an Eventstream custom endpoint."""
import csv
import json
import os
import sys
from datetime import datetime, timezone

from azure.eventhub import EventData, EventHubProducerClient

CONN = os.environ["EVENTSTREAM_CONN"] # Connection string-primary key
path = sys.argv[1] if len(sys.argv) > 1 else "stream-cold-store-temperature-alert.csv"

with open(path, newline="") as f:
    rows = list(csv.DictReader(f))

def parse(ts: str) -> datetime:
    return datetime.fromisoformat(ts.replace("Z", "+00:00"))

shift = datetime.now(timezone.utc) - max(parse(r["reading_time"]) for r in rows)

producer = EventHubProducerClient.from_connection_string(CONN)
with producer:
    batch = producer.create_batch()
    for r in rows:
        event = EventData(json.dumps({
            "reading_time": (parse(r["reading_time"]) + shift).isoformat(),
            "warehouse_id": r["warehouse_id"],
            "sensor_id": r["sensor_id"],
            "temperature_c": float(r["temperature_c"]),
            "humidity_pct": float(r["humidity_pct"]),
        }))
        try:
            batch.add(event)
        except ValueError: # batch full: send it and start another
            producer.send_batch(batch)
            batch = producer.create_batch()
            batch.add(event)
    producer.send_batch(batch)

print(f"Sent {len(rows)} readings")

Run it with EVENTSTREAM_CONN="<connection string>" python send_readings.py. Keep the connection string out of the file and out of Git. It is a write key to your stream.

Step 4: route to the Eventhouse

  1. Back in the Eventstream, switch to edit mode and select Add destination > Eventhouse.
  2. Choose Direct ingestion, enter a destination name, pick the workspace and coldchain_rti, then Save. Connect the card to the stream if it is not connected already and Publish.
  3. In live view select Configure on the Eventhouse node. In Get data choose New table, call it sensor_readings, then Next.
  4. On Inspect the data pick JSON. Open Edit columns and check that reading_time is datetime and that temperature_c and humidity_pct are real. Then Finish and Close.
  5. Run the script again if your first run happened before the table existed.

Step 5: chart temperature per cold store

Open the KQL database, open its queryset and run:

sensor_readings
| where reading_time > ago(1d)
| summarize temperature_c = avg(temperature_c) by warehouse_id, bin(reading_time, 10m)
| project reading_time, warehouse_id, temperature_c
| render timechart

You should see four flat lines near -20 °C with short spikes every six hours, the defrost cycles. One line leaves the pack in the last few hours and does not come back. That is WH-03.

Step 6: detect a store that has run warm

let window = 2h;
let limit = -15.0; // °C, the warmest a frozen store should run
let current = sensor_readings
    | where reading_time > ago(1d)
    | summarize arg_max(reading_time, temperature_c, humidity_pct) by warehouse_id, sensor_id;
let trend = sensor_readings
    | where reading_time > ago(window)
    | make-series T = avg(temperature_c) default = real(null) on reading_time from ago(window) to now() step 10m by sensor_id
    | extend T = series_fill_linear(T)
    | extend (RSquare, Slope) = series_fit_line(T)
    | extend Avg2h = round(todouble(series_stats_dynamic(T).avg), 1)
    | project sensor_id, Avg2h, Rise2h = round(Slope * 12, 1); // slope is per 10 min bin
current
| join kind=inner trend on sensor_id
| extend IsWarm = temperature_c > limit and Avg2h > limit
| project warehouse_id, sensor_id, temperature_c, humidity_pct, Avg2h, Rise2h, IsWarm

The two conditions matter equally. The latest reading on its own catches every defrost cycle and every pallet that goes through the door. The two-hour average on its own keeps alerting after the door is shut and the store has pulled back down. Only a store that is warm now and has been warm for most of two hours is a failure. Rise2h is not part of the rule, on purpose: a store mid-defrost shows a steep rise too. It goes in the message so the reader can see which way the store is heading.

Step 7: hand it to Activator

  1. Run the warm query, then select Set alert on the ribbon.
  2. Name the rule, set the Monitor frequency to 15 minutes (or the nearest value the pane offers), pick Send email (or the Teams message action) as the action and under Save location create a new Activator called act_cold_stores. Select Create.
  3. That pane only offers On each event, which fires for every row on every run. Fix it in Activator: in the Rules pane select ... > View in Activator, delete the rule you just made, select the query source and choose New object (Activator sometimes creates an object for query sources on its own; if so, use that one). Name it ColdStore with sensor_id as the Unique Identifier.
  4. On the ColdStore object add a rule on IsWarm with the Logical change condition Becomes true. Add the action again: email the warehouse shift lead, or post a Teams message, with @warehouse_id, @temperature_c and @humidity_pct in the body.
  5. Start the rule.

Now each store alerts once when it tips into warm. It alerts again only if it recovers and then fails a second time.

Check it worked

  • The Eventstream live view shows events flowing into the custom endpoint and out to the Eventhouse node.
  • sensor_readings | count returns 576 after one replay.
  • The warm query returns four rows with IsWarm true only for WH-03, at about -8.4 °C and 85% humidity, with a two-hour average near -9 °C and a rise of about 2.5 °C.
  • WH-02 is the interesting false. Its last reading is -14.4 °C, mid-defrost, which is above the limit. Its two-hour average is near -19 °C, so it stays quiet. A plain "temperature above -15 °C" alert on raw readings would have fired 12 times across the day on the three healthy stores.
  • Within one monitor cycle the alert arrives. The rule history in Activator shows a single activation for WH-03.

Where this breaks

  • Activator copies the query. It takes a copy when you create the rule and runs that against the Eventhouse directly. Editing the queryset afterwards changes nothing. To change the logic, delete the rule and recreate it from the updated query.
  • The timestamp is the run time. Activator does not use a timestamp column from a KQL query; each run is stamped when it ran. Write the query to return current state per sensor, as above, not a history.
  • Polling keeps the Eventhouse awake. A query every one or five minutes effectively holds the Eventhouse in an always-on state, which costs capacity units around the clock. Frozen stock takes hours to warm through, so 15 minutes is a fair trade. Go faster only if the cost is agreed.
  • Defrost looks like a failure. Drop the two-hour average and you will page someone four times a day per freezer. That is how alerts get muted. If your defrost cycles run longer than the window, widen the window.
  • Events before routing. Data that arrives while the destination is still starting may never reach it. If the table looks short after the first run, replay the file.
  • The sensor is not the stock. A probe by the door reads air, not product. A pallet in the middle of the store can still be frozen while the probe says -8 °C. The alert gets someone to the store. It does not replace a product probe.

Next on the roadmap

Move the warm logic into the Eventhouse with an update policy or a materialised view so every consumer reads the same flag (rti-2-1), then tune cache and retention once the history grows (rti-3-1). The full path is on the roadmap.

On the brewhouse floor

A brewery uses the same pattern to catch a stuck fermentation. Each fermenter, say FV-03, reports sugar level (gravity) and temperature every hour. The gravity should fall steadily for several days as yeast eats the sugar. The query fits a line through the last 12 hours and flags a tank whose gravity has stopped falling while plenty of sugar is still left, often because a cooling valve stuck open and chilled the yeast to sleep. The same Activator object and "becomes true" rule send one message per stuck tank instead of one every run.
