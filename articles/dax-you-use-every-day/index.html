DAX you use every day: CALCULATE, filters and time intelligence

Five measures on a small retail model that cover most of what a report needs: a filtered total, a share of total, year to date, last year and growth. Each one comes with the number it should return, plus the year-on-year trap that makes a good quarter look like a collapse.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 1 Ankur Napa Power BI

Short answer

Most everyday DAX is one base measure plus CALCULATE with a different filter. CALCULATE evaluates an expression after changing the filter context: a filter argument on a column replaces whatever filter was already on that column, REMOVEFILTERS clears filters and KEEPFILTERS intersects instead of replacing. Time intelligence functions such as TOTALYTD and SAMEPERIODLASTYEAR are filters too. They only behave on a marked, contiguous date table. Learn those three ideas and you can read almost any measure a colleague writes.

What you will build

Five measures on the Harbour Goods sales model, a fictional retailer with eight stores and nine products:

  1. Outdoor sales: a fixed filter with CALCULATE.
  2. Share of all regions: a percentage of total with REMOVEFILTERS.
  3. Sales YTD: year to date with TOTALYTD.
  4. Sales PY: the same period last year, done honestly.
  5. Sales YoY %: growth on top of the last one.

Each sits on one base measure, Net sales, so a change to how sales are calculated happens in one place.

Before you start

  • The model from A star schema that behaves: orders, products, stores and a marked Date table covering 2025 and 2026, with single-direction many-to-one relationships. If you are starting here, that article takes about twenty minutes and uses the same file.
  • The sample: star-schema-that-behaves.csv, 110 synthetic order lines from January 2025 to September 2026, prices in INR.
  • Power BI Desktop, or the same model opened for editing in a Fabric workspace.

Confirm the base measure exists and returns 995,654.70 on a card:

Net sales =
SUMX ( orders, orders[quantity] * orders[unit_price] * ( 1 - orders[discount] ) )

Step 1: a filtered total

Select the orders table, then New measure:

Outdoor sales =
CALCULATE ( [Net sales], products[category] = "Outdoor" )

Put it on a card: 452,275.80. Now put it in a table next to products[category]. Every row says 452,275.80, Kitchen and Home included. That surprises everyone once. The filter argument products[category] = "Outdoor" replaces the category filter coming from the row, so each row computes Outdoor.

If you want the measure to respect the visual and only show a value on the Outdoor row, wrap the filter in KEEPFILTERS:

Outdoor sales (kept) =
CALCULATE ( [Net sales], KEEPFILTERS ( products[category] = "Outdoor" ) )

Now Kitchen and Home are blank and Outdoor reads 452,275.80. Neither is wrong. Decide which question the measure answers and name it accordingly.

Step 2: share of total

Share of all regions =
DIVIDE ( [Net sales], CALCULATE ( [Net sales], REMOVEFILTERS ( stores ) ) )

The denominator clears every filter on the stores table, so it is always the all-region total for whatever dates and products are selected. DIVIDE returns blank instead of an error when the denominator is zero. Format the measure as Percentage with one decimal place.

Put it next to stores[region]. If you use ALL ( stores ) instead, you get the same result here. REMOVEFILTERS reads as what it does when it sits inside CALCULATE.

Step 3: year to date

Sales YTD =
TOTALYTD ( [Net sales], 'Date'[Date] )

Put it in a matrix with Date[Month] on rows and Net sales beside it. Each month adds to the running total and the total resets on 1 January. From October 2026 the running total stops moving because there are no orders yet, so the last value repeats for October, November and December. That is correct behaviour, not a bug, but it confuses readers. Hide future months with a filter on the visual if it matters.

Step 4: last year, honestly

The obvious measure is:

Sales PY (naive) =
CALCULATE ( [Net sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )

On a monthly row it is fine. On the 2026 year row it is not. The year 2026 in the date table runs to 31 December, so SAMEPERIODLASTYEAR returns all of 2025. You compare nine months of 2026 against twelve months of 2025 and growth looks like a collapse.

Cap last year at the date of the latest order, moved back one year:

Sales PY =
VAR LastOrder =
    CALCULATE ( MAX ( orders[order_date] ), REMOVEFILTERS () )
RETURN
    CALCULATE (
        [Net sales],
        SAMEPERIODLASTYEAR ( 'Date'[Date] ),
        'Date'[Date] <= EDATE ( LastOrder, -12 )
    )

Two filter arguments in one CALCULATE are combined with AND, so the result is last year's dates up to the same day of the year as the latest order. The latest order in the sample is 27 September 2026, so the cap is 27 September 2025.

Step 5: growth

Sales YoY % =
DIVIDE ( [Net sales] - [Sales PY], [Sales PY] )

Format as a percentage. For any 2025 row it is blank, because there is no 2024 in the data and DIVIDE swallows the empty denominator.

The two growth figures are the point of this page. Same data, same year, one says sales fell by almost a third and the other says they fell by about a ninth. The first number reaches a board pack more often than anyone admits.

If Sales YTD returns the same value as Net sales on every month, the matrix rows probably come from a date hierarchy on orders[order_date] rather than from the Date table. If it returns blank, the Date table does not cover the order dates.

Where this breaks

  • Patchy or unmarked date table. Time intelligence assumes one row per day across whole years. A date table built from the order dates has gaps and returns odd numbers without an error. Marking matters most when the relationship uses an integer date key such as 20260927: unmarked, the time intelligence filters do not clear the month filter and every result looks like a single month.
  • Fiscal years. TOTALYTD takes a year-end argument, for example TOTALYTD ( [Net sales], 'Date'[Date], "3/31" ) for an April to March year. Week-based retail calendars need a different pattern altogether.
  • Filters on the wrong table. CALCULATE ( [Net sales], orders[store_id] = "ST-014" ) works, but filtering the fact column bypasses the dimension and confuses anyone reading the model. Filter dimension columns.
  • Measures inside iterators over the fact. SUMX ( orders, [Net sales] ) triggers a context transition for every row. It works on 110 rows. It crawls on 110 million.
  • Calendar-based time intelligence. The newer calendar feature, in preview, changes how filters on the date table are cleared. Do not mix it with classic functions on the same table until you have read the SQLBI write-up.

On the brewhouse floor

A winery's cellar door and online shop sell all year, but the owner always asks one question in October: are we ahead of last year? Build the same five measures on a sales table of bottles sold by wine and channel. Sales PY with the cap matters even more here, because a harvest-season month can swing the year either way and a naive comparison against a full twelve months will look like disaster every autumn. Add a filtered measure for one label, the reserve wine perhaps, plus a share-of-channel measure. The owner then has the whole conversation on one page.
