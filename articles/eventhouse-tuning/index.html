Eventhouse tuning: cache, retention and the five-minute lag

A cold-store alert arrives minutes after the reading and the Eventhouse keeps ten years of sensor data hot. Measure ingestion lag with ingestion_time(), shorten the batching window, set cache and retention to the way the data is actually queried and prove both with numbers.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa KQLReal-timeCapacity

Short answer

Two policies decide most of an Eventhouse's behaviour and both ship with defaults built for nobody in particular. The ingestion batching policy holds small batches for up to five minutes before it commits them, which is why a quiet table can show readings minutes late. Shorten the time limit to 30 seconds on the tables that feed alerts and measure the difference with ingestion_time(). The caching policy decides how much data sits on fast local disk. A new KQL database keeps 3,650 days hot. Cache drives compute size, so set the hot window to what dashboards actually read, often seven to thirty days. Set retention separately to what the business must keep. Old data stays queryable, just slower.

The symptom

Harbour Goods streams readings from four cold-store warehouses into sensor_readings, as built in stream cold-store temperatures to an alert. Two complaints arrived in the same week. The shift lead at WH-03 said the warm-store alert lands several minutes after the probe reading it quotes. And the capacity owner noticed the Eventhouse had scaled up a size although query traffic had not changed.

Measure it

Ingestion lag. If the table has its IngestionTime policy on, every row carries a hidden ingestion timestamp. Check first; a null result means the policy is off and ingestion_time() returns nulls.

.show table sensor_readings policy ingestiontime

Turn it on with .alter table sensor_readings policy ingestiontime true if needed. It only stamps rows ingested afterwards. Then compare the sensor's own timestamp with the ingestion time:

sensor_readings
| where reading_time > ago(1d)
| extend lag_s = (ingestion_time() - reading_time) / 1s
| summarize readings = count(), p50 = percentile(lag_s, 50), p95 = percentile(lag_s, 95),
            max_lag = max(lag_s), over_2min = countif(lag_s > 120)

The result is an estimate, because the sensor's clock and the service clock are not synchronised. A gateway that is a minute fast shows up as a minute of negative lag.

To practise on known numbers, load eventhouse-tuning.csv into a new table called lag_sample with Get data > Local file. It holds 48 readings from a working day before the fix and 48 from the day after, one every ten minutes across the four stores, with the lag already worked out:

lag_sample
| summarize readings = count(), p50 = percentile(lag_s, 50), p95 = percentile(lag_s, 95),
            max_lag = max(lag_s), over_2min = countif(lag_s > 120) by phase

The before row reads a median of about 151 seconds, a 95th percentile of about 273, a maximum of 304 and 30 of 48 readings more than two minutes late. KQL's percentile is an estimate, so a second either way is normal. A maximum just over 300 seconds is the tell: that is the batching policy's five-minute default plus processing.

The batching policy.

.show table sensor_readings policy ingestionbatching
.show database <DatabaseName> policy ingestionbatching

A null table policy means the database policy applies. If that is null too, the defaults apply: five minutes, 500 items or 1 GB, whichever comes first. A table receiving a few readings a minute never reaches 500 items or 1 GB, so every batch waits for the clock. Learn does not say which ingestion path each Eventstream destination mode uses, so trust the lag query over the theory.

Hot cache.

.show diagnostics
| project HotDataDiskSpaceUsage

.show tables details
| project TableName, HotOriginalSize

.show table sensor_readings policy caching
.show table sensor_readings policy retention

HotDataDiskSpaceUsage is the percentage of hot cache in use. At about 95 per cent the Eventhouse scales compute up to the next size whatever the CPU says; it only scales back in below about 35 per cent with other conditions met. A new KQL database caches and retains for 3,650 days, so every reading ever ingested competes for cache.

Fix it

1. Shorten the batching window on the alert table only.

.alter-merge table sensor_readings policy ingestionbatching '{"MaximumBatchingTimeSpan":"00:00:30"}'

Use alter-merge, not alter. With alter, any property you leave out resets to its default; alter-merge changes only what you name. Learn lists 20 to 30 seconds as the low-latency setting and 10 seconds as the minimum. Go no lower than you need: on a low-ingress table a very short window creates many small extents, more background merge work and sometimes higher end-to-end latency, not lower.

2. Set cache to the read pattern. In the KQL database select Manage > Data policies to change the database defaults, or set the table directly:

.alter table sensor_readings policy caching hot = 30d

Thirty days covers the dashboards and the alert's lookback with room for a month-end review. The materialised view from update policies and materialised views is tiny by comparison, so keep its hourly aggregates hot for longer:

.alter materialized-view ColdStoreHourly policy caching hot = 400d

Cache is evaluated on each extent's ingestion time. Learn notes it can take up to an hour for the cache to reflect a new policy.

3. Set retention to the obligation, not the default.

.alter-merge table sensor_readings policy retention softdelete = 400d recoverability = enabled

Four hundred days keeps a full year plus a month so this October can be compared with last October. A shorter retention applies to existing data straight away, so anything older becomes eligible for deletion. If the database has OneLake availability on, retention removes the Delta copy too, so agree the number before you run it.

Prove it

Run the lag query for a working day after the change. On the sample, the after row reads:

MeasureBeforeAfter
Median lag151 s24 s
95th percentile lag273 s39 s
Maximum lag304 s41 s
Readings more than two minutes late30 of 480 of 48
Batching time limit5 min (default)30 s
Hot cache window3,650 days30 days
Share of a 400-day history kept hot100 per cent7.5 per cent

The last line is arithmetic: once 400 days have accumulated, 30 hot days is 7.5 per cent of the table. Watch HotDataDiskSpaceUsage fall over the following hour. To see what a dashboard experiences with hot data only, run a query with set query_datascope = "hotcache"; at the top. A query that needs older data returns less, which tells you the window is too short.

Where this breaks

  • Cold is slower, not gone. Queries beyond the hot window read from OneLake storage and run noticeably slower. If a team runs a yearly review, add a temporary hot window for that period rather than caching a year all year.
  • Low windows on many tables. Applying 30 seconds database-wide multiplies small extents across every table. Set it per table on the ones that feed alerts.
  • Clocks lie. Lag measured against a sensor's own clock includes the clock's error. Check one sensor against a known time before you blame the pipeline.
  • Schema changes on streaming paths. Eventhouse nodes cache the schema for streaming ingestion; changing a table while data streams in can cause failures. Check .show ingestion failures after any change.
  • Minimum capacity. If the Eventhouse has a minimum capacity or a Capacity Scheduler baseline, compute does not shrink with the cache during those windows. Read the consumption page before you promise savings.

On the brewhouse floor

A winery at harvest is the same Eventhouse with a calendar. Winery C streams temperatures from forty fermentation tanks for six weeks a year, then almost nothing. During ferment, a red running warm needs cooling within the hour, so the tank table gets a 30-second batching window and the alert lands while the tank can still be pulled back. The winemaker compares this vintage with last year's, so retention runs past 400 days, while the hot cache covers the current harvest and the aggregates by tank and hour stay hot for years because they are small.
