Delta maintenance: OPTIMIZE, VACUUM and V-Order by read pattern

A gold table that takes a small append every six minutes hits the Direct Lake file guardrail inside a week. Count the files, compact them, turn on V-Order only where Power BI reads and learn why VACUUM deletes nothing on the day you first run it.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 3 Ankur Napa LakehouseSparkDirect Lake

Short answer

Every Delta append writes at least one new Parquet file. A table fed in small batches ends up as thousands of tiny files, which slows Spark, the SQL analytics endpoint and Direct Lake alike and eventually trips Direct Lake's file guardrail. OPTIMIZE rewrites them into a few large files. VACUUM deletes the old files once they are older than the retention period, seven days by default, so it frees storage a week later, not today. V-Order is a write-time layout that helps Direct Lake and the SQL endpoint read faster and costs write time, so turn it on for gold tables that Power BI reads and leave it off for bronze and silver that only Spark reads. Let auto compaction handle the daily churn and schedule OPTIMIZE and VACUUM weekly.

The symptom

Harbour Goods moved its order feed to a near real-time load. A pipeline appends the latest orders to fact_orders_live every six minutes, 240 times a day. A Direct Lake report sits on top. For four days it was fine. On the fifth, the report started failing to refresh with a guardrail error. Nobody had changed the model.

Reproduce it in a notebook attached to a lakehouse. This writes 240 appends of 1,000 orders, one file each, which is one day of the feed. It takes several minutes because every append is a commit.

from pyspark.sql import functions as F

# Keep the demo honest: show the files that pile up when nothing compacts them.
spark.conf.set("spark.databricks.delta.autoCompact.enabled", "false")

for i in range(240):
    (spark.range(i * 1000, (i + 1) * 1000)
        .withColumn("order_id", F.format_string("HG-%07d", F.col("id")))
        .withColumn("store_id", F.element_at(
            F.array(*[F.lit(s) for s in ["ST-003", "ST-007", "ST-011", "ST-014", "ST-019", "ST-022"]]),
            (F.col("id") % 6 + 1).cast("int")))
        .withColumn("quantity", (F.col("id") % 4 + 1).cast("int"))
        .withColumn("net_amount", (F.col("quantity") * 899).cast("decimal(12,2)"))
        .drop("id")
        .coalesce(1)
        .write.mode("append").format("delta").saveAsTable("fact_orders_live"))

Measure it

Check the runtime first: Runtime 2.0 became the default for new workspaces on 6 October 2026, though some Learn pages still say 1.3. It is in Workspace settings > Data Engineering/Science > Spark settings > Environment. Runtime 2.0 turns deletion vectors on by default, which changes how deletes and updates leave files behind.

Then count:

DESCRIBE DETAIL fact_orders_live;   -- numFiles, sizeInBytes
DESCRIBE HISTORY fact_orders_live;  -- one row per commit, with operationMetrics
SELECT COUNT(*) FROM fact_orders_live;

Expect numFiles of 240, 240 commits in the history and 240,000 rows. Divide sizeInBytes by numFiles: each file is a few kilobytes. Microsoft's target is 128 MB to 1 GB per file.

Now do the arithmetic the report did not. On F2 to F32, Direct Lake allows 1,000 Parquet files per table. At 240 new files a day the table passes 960 on day four and 1,000 early on day five. Direct Lake on OneLake then errors; Direct Lake on SQL falls back to DirectQuery and quietly gets slower. Either way, the file count was predictable from the load schedule on day one.

Two settings decide what happens next, so read them before changing anything:

spark.conf.get("spark.sql.parquet.vorder.default")         # 'false' in new workspaces
spark.conf.get("spark.fabric.resourceProfile", "unset")    # 'writeHeavy' is the default
SHOW TBLPROPERTIES fact_orders_live;

New workspaces default to the writeHeavy resource profile, which has V-Order off. That is right for ingestion and wrong for a table whose only job is to feed Power BI.

Fix it

1. Decide the read pattern. Learn's figures are the guide. V-Order improves Direct Lake cold-cache queries by 40 to 60 per cent and SQL analytics endpoint reads by about 10 per cent. Spark gets no inherent read benefit. Writes run 15 to 33 per cent slower. fact_orders_live is read by Direct Lake, so V-Order goes on. The bronze table behind it, read once by Spark, keeps it off.

2. Set the table properties so future writes behave.

spark.conf.unset("spark.databricks.delta.autoCompact.enabled")   # drop the demo's session override
ALTER TABLE fact_orders_live SET TBLPROPERTIES (
  'delta.parquet.vorder.enabled' = 'true',
  'delta.autoOptimize.autoCompact' = 'true'
);

A session setting can override what the table says, which is why the demo's false has to go first.

Auto compaction checks the table after each write and runs a synchronous compaction once 50 files sit under the minimum size. Microsoft recommends it as the default for most ingestion workloads. If a write latency target is strict, run a scheduled OPTIMIZE on a separate pool instead, since auto compaction adds its work to the write.

3. Compact the backlog once.

OPTIMIZE fact_orders_live VORDER;

OPTIMIZE with VORDER forces V-Order on the rewritten files whatever the session says. Without the keyword it follows the table property, then the session setting. The command returns metrics: expect numFilesRemoved of 240 and numFilesAdded of 1, because 240,000 small rows fit comfortably in one file under the 1 GB target.

4. Run VACUUM and watch it do nothing.

VACUUM fact_orders_live DRY RUN;

It finds nothing to delete. The 240 old files are no longer referenced, but they are minutes old and the default retention is 168 hours. That is the safety net doing its job: time travel and concurrent readers still need them. Seven days from now the same command removes all 240. Do not shorten retention to make today's number look better; the portal and the API reject anything under seven days unless spark.databricks.delta.retentionDurationCheck.enabled is set to false. That switch exists for people who have thought hard about it.

5. Schedule it. In the lakehouse explorer, select ... on the table, then Maintenance, to run it by hand. For a schedule, add the Lakehouse Maintenance activity to a pipeline (the Learn maintenance page still labels it preview), set OPTIMIZE on with Apply V-order ticked and VACUUM on at seven days. Chain it after the weekly load. Runs show in the Monitoring hub as TableMaintenance entries.

Order matters with Direct Lake. A framed model points at a specific Delta version. If automatic updates are off and the model has not reframed for longer than the retention period, VACUUM can delete files it still reads and users get query errors. Refresh the model before VACUUM runs. OPTIMIZE also replaces files that Direct Lake has already loaded, so the first queries after it are cold. Run both off peak.

Where this breaks

  • Copy activity and Dataflow Gen2 tables. Tables written outside Spark do not pick up Spark session defaults such as auto compaction. Schedule their maintenance separately.
  • Partitioning by day on a small table. That multiplies files per load and compaction cannot fix a bad partition key. From Runtime 2.0, Microsoft recommends liquid clustering for read performance and keeps partitioning mainly for concurrent writers on separate partitions.
  • Deletes and updates. With deletion vectors on, a DELETE marks rows rather than rewriting files. OPTIMIZE purges a file's deletion vectors once more than 5 per cent of its rows are marked. Auto compaction only purges them when the small-file trigger also fires, so an update-heavy table still needs a scheduled OPTIMIZE.
  • V-Order everywhere. Turning V-Order on for bronze and silver slows every write for readers that do not benefit. Use the readHeavyForPBI resource profile only in the environment that writes gold.
  • VACUUM is permanent. It removes time travel beyond the retention window. Keep retention longer than your longest rollback or audit need.

On the brewhouse floor

A distillery's cask inventory behaves the same way. Distillery B scans every cask movement in the warehouse as it happens and appends a few rows at a time to a table the stock report reads. Within a week the table is thousands of tiny files and the monthly duty report crawls. Auto compaction on the table and a weekly OPTIMIZE keep it to a handful of files. Seven days of retention still lets the excise team look back at last Tuesday's position when the counts do not match the rack.
