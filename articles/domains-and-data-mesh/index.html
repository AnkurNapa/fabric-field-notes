Domains and data mesh: organising Fabric for many teams

How to lay out workspaces and domains once more than one team builds on Fabric. Domains organise, delegate and help people find data. They do not secure anything, which is the mistake most designs make first.

Ankur Napa 11 Oct 2026, 8 min read

Short answer

A Fabric domain is a label on a group of workspaces plus a place to hand a few tenant settings down to the business. It lets people filter the OneLake catalog by business area. It lets a domain admin set a default sensitivity label and run certification for that area. It does not change who can see or open anything. Microsoft Learn is blunt about this: domain assignment does not affect item visibility or access. Access still lives on workspace roles, item permissions and OneLake security.

So design in two layers. Workspaces carry the hard boundaries: who has which role, which Git branch, which deployment stage and which capacity. Domains sit on top and carry ownership and discovery. Learn's data mesh shape is one domain per business area plus a central domain for shared enterprise data, with consumers reading producer data rather than copying it.

Use domains when a central team has become the queue every request waits in. Skip them while one team builds everything. A mesh with no owners is sprawl with nicer labels.

The decision

OptionFits whenCosts youWatch
No domains, one central teamOne data team, a handful of workspacesNothing yetThe catalog gets noisy as workspaces multiply
Domains for discovery onlyMany teams consume, one team producesA naming convention and someone to assign workspacesEasy start; delegation goes unused
Domains with delegated settingsBusiness areas own their data and want to certify it themselvesA named domain admin and certifiers per areaDomain admins cannot delete the domain, rename it or add other domain admins
Full mesh with producer and consumer workspacesSeveral teams publish data products that others depend onContracts, shortcuts, endorsement rules and a Centre of Excellence to refereeA shortcut couples the consumer to every schema change the producer makes

The rule for when to create a new workspace is older than domains and still the right one: create a workspace when the security group, Git branch, deployment stage or capacity differs. If none of those differ, it is a folder, not a workspace.

Three roles run domains. A Fabric admin creates domains, names domain admins and can assign any workspace. A domain admin edits the description, names domain contributors, assigns workspaces and overrides the settings the Fabric admin has delegated. A domain contributor is a workspace admin who has been allowed to put their own workspace into the domain from workspace settings. Today two kinds of tenant setting can be delegated: the domain-level default sensitivity label and certification settings.

Reference design

Harbour Goods, the fictional retailer and distributor used across this site, has three business areas that build on Fabric: Sales, Supply chain and Finance. Products and stores are used by everyone.

What each layer owns:

LayerOwnsSet by
DomainCatalog filter, certifiers, default labelFabric admin creates it; domain admin runs it
SubdomainFiner grouping only. General settings only, no admins of its ownFabric admin or domain admin
WorkspaceRoles, Git connection, deployment stage, capacityWorkspace admin
ItemSharing, endorsement, OneLake security rolesItem owner

How a data product moves between domains:

  1. Sales builds gold orders in sales-orders-prod and promotes the lakehouse. A Sales certifier reviews it against the certification rules and certifies it.
  2. Finance does not copy it. A Finance engineer creates a OneLake shortcut to it from fin-margin-prod. Finance users need read access on the source, granted by the producer through item permissions or a OneLake security role. The domain grants nothing.
  3. Products and stores carry the Master data badge, applied by the few people the Fabric admin has authorised. Turn this on with the Endorse master data (preview) tenant setting. Learn still labels it preview.

Getting workspaces into domains is a one-time job and then a habit. Fabric and domain admins can assign by workspace name, by workspace admin or by capacity. All three apply to existing workspaces only. To catch new ones, make the domain the default domain for the people who create workspaces in that area: unassigned workspaces they admin and every new one they create land in the domain automatically. By default an admin assignment does not override an existing assignment. That needs the Allow tenant and domain admins to override workspace assignments (preview) tenant setting.

Questions to ask the client

  • When a number in this data set is wrong, whose phone rings? Ask for a name, not a team.
  • Do the business areas have people who can build, or only people who can ask? A mesh needs producers.
  • Which data does everyone use (products, customers, stores, calendar)? Who owns it today, if anyone?
  • Does each business area already have its own capacity or budget? If yes, assigning by capacity is quick and chargeback follows.
  • Is there a workspace naming convention? If not, write one before creating domains, because assignment by name depends on it.
  • Who will certify? How does an item lose its certification?
  • Do any areas need data kept in a different region? That drives capacities, which drives workspaces. See the network and residency guide.
  • Which settings do they actually want delegated? Today that is the default label and certification, nothing more.

Review checklist

  • Every production workspace sits in a domain. None are left unassigned.
  • Each domain has two named domain admins, so leave and resignations do not orphan it.
  • Workspace names encode domain, product and stage, for example sales-orders-prod.
  • Dev, test and prod are separate workspaces. Prod sits on a different capacity from dev.
  • Shared data is reached through shortcuts, not copies, unless the copy changes shape, quality or ownership.
  • Certification is switched on, delegated where the domain really reviews items and has a documentation URL.
  • The Master data badge is on a short list of items, each with an owner.
  • Access was reviewed at workspace and item level with domains ignored, because domains grant nothing.
  • Default domains are set for the people who create workspaces, so new work does not land unassigned.
  • Domain changes are visible in the audit log and someone reads it.

Anti-patterns

  • Domain as a security boundary. "Only Finance can see the Finance domain" is false. Every user in the tenant sees every domain in the catalog filter. What they can open depends on workspace roles and item permissions alone.
  • One giant workspace per domain. It puts dev and prod, two security groups and one Git branch into the same box. You lose every boundary a workspace exists to give you.
  • Domains copied from this year's org chart. Reorganisations then mean reassigning hundreds of workspaces. Learn lists functional, product, process, regional and mixed structures. Pick the one that changes least.
  • The product table in every domain. Three copies give you three answers to "how many active products". Publish it once in the enterprise domain and shortcut to it.
  • A mesh with nobody minding it. Domain admins who never open the admin portal, certification that never happens and no central team to settle disputes. Federated ownership still needs a referee.
  • Expecting subdomains to behave like domains. Subdomains have general settings only and inherit their parent's admins. Use them for grouping, not for delegation.

On the brewhouse floor

A drinks group with a brewery, a bottling plant and a distribution arm hits the same wall Harbour Goods did. Each site wants its own reports, yet everyone needs one product list. Give each site a domain, keep the product and pack-size master in a shared enterprise domain with the Master data badge and let the bottling team shortcut to it. The quality lab's results table is the one everyone argues about, so the lab certifies it in its own domain and nobody else gets to edit it. Nothing about the domains decides who sees the lab results. The workspace roles do.
