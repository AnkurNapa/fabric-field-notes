Fabric IQ and ontologies: when an ontology is worth the modelling cost

A design guide for deciding whether to build an ontology in Fabric IQ, what it adds over a good semantic model and how to scope the first one. Ontology and the IQ workload are in preview as of October 2026.

Ankur Napa 11 Oct 2026, 7 min read

Short answer

An ontology in Fabric IQ is a shared business vocabulary: entity types such as Customer, Order, Store and Shipment, their properties, the relationships between them, rules written in plain language and metrics carried over from Power BI DAX measures. It binds those definitions to live data in lakehouses, eventhouses, warehouses, SQL databases, mirrored databases and semantic models without copying the data. It is worth the modelling cost when several agents or teams must share one vocabulary across domains, especially in operational and real-time scenarios. It is overkill for a single-domain question and answer agent over one semantic model. As of October 2026 both the IQ workload and the ontology item are in preview. The old ontology experience retires on 31 January 2027. Plan for change.

The decision

What each layer is for, so the ontology is not asked to do a semantic model's job.

LayerWhat it holdsBest atNot for
Power BI semantic modelTables, relationships, DAX measuresTrusted KPIs, fast interactive reportsConcepts that span several models or live streams
Ontology (preview)Entity types, relationships, rules, metrics, bindings, namespacesOne vocabulary across domains for people, apps and agentsQuerying data itself; it serves definitions, consumers query the bound sources
Graph (preview)Materialised nodes and edgesMultihop paths, dependency chains, shortest pathsRoutine lookups and aggregations
Data agentQ&A over chosen sourcesA tailored analyst for one domainGoverning definitions others reuse
Operations agentRules and actions over live dataWatching real-time data and recommending actionAd hoc analysis

When it pays and when it does not:

SignalBuild an ontologyStay with a semantic model and a data agent
Domains involvedThree or more (sales, logistics, warehouse sensors)One
ConsumersSeveral agents and apps need the same meaningOne report family, one agent
Data shapeMix of eventhouse streams, lakehouse tables and modelsOne star schema
Questions"Which orders are at risk because of that cold room?""What were net sales last month?"
TeamSomeone can own a vocabulary as a productNobody has time to curate definitions

Facts that shape the design (preview, so check Learn before you commit):

  • You can generate an ontology from an existing semantic model. Tables, relationships, calculated columns and DAX measures come across; measures become metrics whose DAX stays owned by the source model.
  • Graph execution is opt-in. An ontology-derived graph does not load instance data unless you materialise it.
  • Versions are named and created manually. Restoring one replaces the current definition.
  • Import works from RDF, Turtle and OWL into an empty ontology. Export goes to RDF or Turtle.
  • Access respects the bound data: OneLake security and source row, object and column level security still apply.
  • The ontology agent follows Copilot regional processing. Outside the US and the EU Data Boundary it is disabled by default until an admin turns on the tenant setting Data sent to Azure OpenAI can be processed outside your capacity's geographic region, compliance boundary, or national cloud instance.
  • During preview the ontology agent reads semantic models for grounding but does not bind entities directly to them. A Fabric data agent pointed at an ontology does not use the semantic-model grounding the ontology carries; only the ontology agent does.
  • Old-experience ontologies need create a copy in the new experience. Rules and Activator alerts are recreated by hand and downstream agents and dashboards must be reconnected to the new item.

Reference design

Harbour Goods, the fictional retailer used across this site, already has a sales semantic model. It wants one agent that can answer questions crossing orders, deliveries and the cold-store sensors.

Namespace: commerce                 Namespace: logistics
  Store ----sells----> Product        Delivery ---fulfils---> Order
    |                     |              |
  places (via)         Order <----------+
                          |            Warehouse --has--> Sensor
                       metric: Net sales,          property: temperature_c
                       Gross margin % (from
                       sm_sales_kpis DAX)

Rule (plain language, logistics):
  "An order is at risk when its delivery is dispatched from a warehouse
   where any cold-room sensor read above 8 C in the four hours before
   dispatched_at."

Bindings:
  Store, Product, Order -> lakehouse tables stores, products, orders
  Delivery              -> lakehouse table deliveries
  Warehouse, Sensor     -> eventhouse table sensor_readings
  Metrics               -> DAX measures owned by sm_sales_kpis
Consumers:
  ontology agent (sales and service desk), operations agent (cold chain),
  Real-Time Dashboard with ontology as source,
  Copilot Studio agent via the Fabric IQ Ontology MCP (preview)

Start with the generated ontology from sm_sales_kpis, bind entities to the gold lakehouse tables underneath it, then add the logistics namespace by hand. Keep the first version to the entity types the first two consumers actually ask about. An ontology that models the whole company before anyone uses it is a glossary project with a Fabric licence.

Questions to ask the client

  1. Which questions do people ask today that need two or more systems to answer? If none, you do not need an ontology yet.
  2. Which semantic models are trusted enough to seed the ontology? Generating from a model nobody trusts imports its arguments too.
  3. Who owns each definition? "Active customer" needs one owner, not a committee.
  4. Which agents or apps will consume it in the next six months? Name them.
  5. Where is the capacity? Outside the US and EU, cross-geo processing for Copilot must be acceptable to the data protection team.
  6. How will you absorb preview changes? Someone must read release notes and the known issues list.
  7. Do relationship-path questions matter ("what is downstream of this warehouse")? Only then plan for graph materialisation and its cost.

Review checklist

  • At least two named consumers, each with five real questions the ontology must answer.
  • Every metric traces to a DAX measure in a named semantic model.
  • Each entity type has one owner and one binding of record.
  • Namespaces match the domains that own the definitions.
  • Security tested with a restricted user through an agent, not only in the portal.
  • A named version saved before every significant change.
  • Known issues for ontology checked on the Fabric known issues site.
  • Any old-experience ontology has a copy in the new experience well before 31 January 2027, with consumers rewired.

Anti-patterns

  • Ontology as a data warehouse. It stores definitions and bindings, not data. Fix data quality in the lakehouse, not in the vocabulary.
  • Redefining measures. Writing a new margin formula in a rule when the semantic model already has one. Two definitions of margin is the problem the ontology was meant to solve.
  • Boiling the ocean. Fifty entity types on day one, zero consumers on day ninety.
  • Production promises on preview. Fine for a pilot with a named owner. Not fine for a regulatory report.
  • Graph by default. Materialising a graph for questions a SQL join answers in milliseconds.

On the brewhouse floor

A distillery is a good case for an ontology because its questions cross systems by nature. A cask has a fill date, a spirit batch, a warehouse position and a strength reading at each regauge, all kept in different places. "Which casks filled from batch 14 sit in the warmest bay of Warehouse 2?" needs every one of them. Define Cask, Batch and Bay once, bind them to the production log, the warehouse map and the sensor feed. The same question then gets the same answer whether a blender asks the agent or a manager opens the dashboard.
