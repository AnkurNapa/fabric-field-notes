What real time means in Fabric

A report that refreshes every fifteen minutes is not real time and a stream nobody watches is not useful. This walkthrough separates streaming latency from a faster refresh schedule, lays out the freshness ladder from Import to Activator and tours the Real-Time hub.

Short answer

When someone asks for "real time" they usually mean one of two different things:

  1. Fresher reports. The sales dashboard should show this morning, not last night. That is a refresh problem. Direct Lake, more refresh slots or automatic page refresh solve it. The data still arrives in batches.
  2. Seconds from event to action. A sensor reading, a click or a payment should be visible and acted on within seconds of happening. That is a streaming problem. In Fabric it means Eventstream to bring events in, an Eventhouse to store and query them with KQL, a Real-Time Dashboard to watch them and Activator to do something when a condition is met.

Ask one question before you design anything: what will someone do differently if they see it in ten seconds rather than ten minutes? If the honest answer is nothing, you want fresher reports, not a stream.

The idea in one picture

The freshness ladder, slowest to fastest:

RungTypical lagHow it worksGood for
Import model, scheduled refreshHours to 30 minutesUp to 8 refreshes a day on Pro, 48 on a capacityDaily and weekly reporting
Direct LakeMinutes after the Delta table changesThe model reframes automatically when new data lands in OneLakeBatch loads that run many times a day
DirectQuery plus automatic page refreshAbout a minuteThe report page re-queries the source on an interval or on change detection; capacity admins set the minimumLive views over a source that can take the load
Eventstream, Eventhouse, Real-Time DashboardSecondsEvents are ingested continuously and indexed by arrival time; dashboard tiles update as new data is ingestedTelemetry, logs, IoT, operations rooms
ActivatorSeconds, with no one watchingA rule watches the stream or a query and sends a message or starts a Fabric jobAlerts and automatic responses

Only the bottom two rungs are streaming. The top three are batch, done more often.

Harbour Goods shows the difference. Its two cold-store warehouses send sensor_readings every ten seconds: warehouse, sensor, reading time, temperature in °C and humidity. The rule is that chilled stock stays between 2 and 8 °C. During a busy unloading slot a dock door gets propped open and the nearest sensor climbs from 4 °C to 9 °C in about fifteen minutes. A report that refreshed at 06:00 shows nothing wrong. A Real-Time Dashboard shows the line bending upwards. An Activator rule on "temperature above 8 °C for five minutes at the same sensor" sends a message to the shift lead before the stock is at risk. Only the last one changes what happens on the dock.

A ten-minute tour

You need a workspace on a Fabric capacity or a trial and Contributor rights. The sample costs a little capacity while it runs; stop or delete it afterwards.

  1. Open the Real-Time hub. Select Real-Time in the left navigation bar. Every tenant has one; you do not create it. The Streaming data page lists the streams and KQL tables you can see.
  2. Look at what is already flowing. Browse the Fabric events category. Workspace item events and OneLake events are streams too: Fabric tells you when a file lands or an item changes, which is often the cheapest real-time signal you have.
  3. Start a sample. Select Add data, find the samples (the category may read Samples or Try a sample scenario) and connect Bicycle rentals. Give the source and the eventstream a name, review and create. The wizard builds an eventstream for you.
  4. Watch the stream. Open the eventstream. Its live view shows events arriving every few seconds. This is the latency the bottom of the ladder buys you.
  5. Find the dashboard setting that matters. If the sample also created a Real-Time Dashboard, open it, switch to editing and select Manage > Refresh settings. Live refresh is on by default and updates tiles when new data is ingested. Compare that with a Power BI report's refresh schedule.
  6. Clean up. Pause or delete the sample eventstream so it stops ingesting.

What people get wrong

  • "Refresh every five minutes is real time." It is batch, done often. It costs a full refresh each time and still misses anything that happens and resolves between runs.
  • "Streaming means everything goes to the Eventhouse." Stream what someone acts on in seconds. Keep the order history, the finance tables and the month-end views in a lakehouse or warehouse. Eventhouse data can be exposed to OneLake as Delta, but that copy lags (up to three hours by default, configurable) so it is not how Power BI gets second-level freshness.
  • "A live dashboard is the goal." Nobody watches a dashboard at three in the morning. If the condition matters, an Activator rule should send the message and the dashboard is where you go after.
  • "Land the stream in a lakehouse and you are done." An Eventstream can write to a lakehouse, but that destination fixes the schema from the first record and suits append-only history. Changing feeds belong in an Eventhouse first.

On the brewhouse floor

At Distillery A the fermenting wash sits in large vessels for a few days and the yeast generates heat as it works. Cooling water keeps each vessel in range; if a cooling valve sticks, the temperature climbs within the hour and the yeast starts producing off flavours. A morning report shows the damage after it is done. A probe on each vessel streaming through Eventstream into an Eventhouse, with an Activator rule on "temperature above the limit for ten minutes", calls the operator while there is still time to open the valve. Same ladder, same answer: the bottom rung earns its cost only when someone acts on it.
