Fabric as an application backend: when apps should read Fabric

Fabric can serve applications, but only from the right store and only for the right users. A design guide to SQL database, Cosmos DB, API for GraphQL and Fabric Apps (preview). Plus the cases where the app belongs on Azure with Fabric reading a mirror of its data.

Short answer

Fabric is a good backend for internal applications that live close to analytical data. It is a poor home for a customer-facing system whose uptime, latency and sign-in you have promised to the public.

When an app does read Fabric, pick the store for the access pattern:

  • Point lookups and small writes go to SQL database in Fabric (up to 32 vCores and 4 TB) or Cosmos DB in Fabric for semi-structured data. Both are built for operational traffic and both land their data in OneLake for analytics automatically.
  • Analytical results shown in an app can come from a warehouse or lakehouse SQL analytics endpoint, but those engines are built for scans and usually answer in seconds, not milliseconds. Keep them off the hot path of a page load.
  • API for GraphQL puts one managed endpoint over any of these sources, with a 100-second timeout and a 64 MB response limit.
  • Fabric Apps (preview), built on the Rayfin SDK, gives you a SQL database, a GraphQL API, Microsoft Entra sign-in and static hosting from TypeScript models. It suits internal tools. It is not yet the place for anything customer-facing.

Every request an app makes consumes capacity units from the same capacity your reports use. Size for it or separate it.

Fabric Apps has its own ceilings, all from Learn's FAQ. Deployed apps sign in with Microsoft Entra single sign-on only. It manages its own database schema and cannot attach to an existing one. Every entity has a single UUID id key and many-to-many relationships need a join entity. There is no built-in multi-environment management or application lifecycle management. Tenant or workspace private links and outbound access protection are not supported yet. It is also not available in every region. None of that makes it bad. It makes it an internal tool platform for now.

Reference design

Harbour Goods has four application needs. Each lands somewhere different.

The reasoning, need by need:

  1. Order tracking for customers. Public sign-in, an uptime promise and unpredictable traffic. It stays on Azure PaaS. Fabric reads its database through mirroring for analytics, so no pipeline is written and the app never waits on Fabric.
  2. Damaged-delivery claims for staff. Entra users, a form, its own small table and a team that knows TypeScript. A Fabric App fits. It reads delivery status from the gold warehouse through a connector and writes claims to its own SQL database, which analytics can query straight away.
  3. Delivery ETA scores for dispatchers. Calculated in a notebook every 15 minutes and written to a SQL database in Fabric, not the warehouse, because the dispatch screen does a lookup per delivery. API for GraphQL fronts it with single sign-on, so each dispatcher sees what their own permissions allow.
  4. Store performance. That is a report, not an app. A Direct Lake model and a Power BI app do it with no code to maintain.

App traffic runs on its own capacity. Month-end reporting will not slow the dispatch screen. A runaway app query will not throttle the finance reports.

Questions to ask the client

  • Who are the users: staff with Entra accounts, partners or the public?
  • What latency does a page load need? What is the peak number of users at once?
  • Does the app write data? How much per hour at peak?
  • Is there an uptime or support commitment to anyone outside the company?
  • Does the tenant use private links or outbound access protection? If so, Fabric Apps is out for now.
  • Which region must the app and its data sit in? Is Fabric Apps available there?
  • How many environments do they need? Who deploys to production?
  • Who is on call when the app breaks at night? Does that team know Fabric?
  • What would the capacity cost be at peak traffic? Who pays it?

Review checklist

  • No page load waits on a warehouse or SQL analytics endpoint scan.
  • Operational reads and writes go to SQL database or Cosmos DB in Fabric, or to an Azure database outside Fabric.
  • Every table exposed through GraphQL has a primary key.
  • GraphQL clients page through results and never pull whole tables; bulk reads use SQL.
  • Single sign-on is used for GraphQL unless saved credentials were chosen on purpose, with the exposure written down.
  • No secrets, API keys or connection strings sit in front-end code or hosted assets.
  • App source code, including Fabric App projects, is in a repository, since Fabric Apps are not replicated in a regional disaster.
  • App traffic has its own capacity, or its CU use has been measured against the reporting peak.
  • The app, its capacity and its data sources are in one region.
  • Preview features in the design are listed, with a fallback if one changes.

Anti-patterns

  • The warehouse as an OLTP database. It will work in the demo with three users and fail on launch day with three hundred.
  • Pointing an app at a report or semantic model to fetch rows. Reports are for people. Give code a SQL endpoint, a database or a GraphQL API.
  • Customer-facing on preview. Fabric Apps is preview, Entra-only once deployed and not in every region. Public sign-in needs a different platform.
  • One capacity for everything. An app's steady traffic plus month-end reporting pushes the capacity into throttling. Both suffer.
  • Saved credentials by default. Every caller then sees whatever that one credential can see.
  • Editing the Fabric App's database by hand. The schema comes from the TypeScript models. Changes made directly in the SQL database can break the app on the next deploy.

On the brewhouse floor

Kegs go out to pubs full and are supposed to come back empty. A brewery that does not track them loses a surprising number every year. Brewery A's cellar team scans each keg out and back on a tablet. That is a good Fabric App: staff sign in with their work accounts, scans land in the app's own SQL database and a nightly notebook works out which pubs are sitting on kegs. The ordering portal the pubs use is a different matter. It faces customers, so it stays on Azure. Fabric reads its orders through a mirror.
