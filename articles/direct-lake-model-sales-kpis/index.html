Your first Direct Lake model: sales KPIs without a refresh

Turn three gold Delta tables into a Direct Lake on OneLake semantic model, add two relationships and three DAX measures, then build a report. Plus the one difference between Direct Lake on OneLake and on SQL that decides whether a broken table errors or quietly slows down.

Ankur Napa 11 Oct 2026, 9 min read

Short answer

Load your gold tables as Delta in a lakehouse, select New semantic model from the lakehouse ribbon and you have a Direct Lake on OneLake model. Add relationships and measures in the browser, then build a report on top. There is no import refresh to schedule: a Direct Lake "refresh" is framing, a metadata pass that points the model at the latest Delta files in seconds. The catch worth learning on day one is that Direct Lake on OneLake has no DirectQuery fallback. If a table breaks a rule, queries error. Direct Lake on SQL falls back to DirectQuery instead and gets slower without telling anyone. This walkthrough shows how to tell which one you built.

What you will build

A small sales KPI model over one quarter of orders for Harbour Goods, the fictional retailer used across this site:

  • fact_sales: one row per order, 66 orders from July to September 2026
  • dim_product: eight products with their category
  • dim_date: one row per day

Three measures on top: net sales, gross margin percentage and average order margin percentage. Then a one-page report.

The numbers matter more than they look. Every store manager knows a discount that looks generous on the shelf can eat the whole margin on a thin-margin product. A gross margin measure that says 35.8 per cent across a quarter is the model's view. Two orders in this data sit below zero, at minus 4.9 per cent, which is what a 35 per cent promotion on a Bluetooth speaker that only carries 32 per cent looks like. The model sees the average. The store sees those two orders.

Before you start

  • A workspace on a Fabric capacity (an F SKU or a Fabric trial). Direct Lake does not run on Pro, Premium Per User or My workspace.
  • Contributor or higher on the workspace.
  • The sample file: direct-lake-model-sales-kpis.csv. It is synthetic, 66 rows. net_amount is quantity times unit price times one minus the discount; cost_amount is quantity times unit cost. Both are in rupees.

Step 1: create the lakehouse and land the file

  1. In your workspace select + New item, then Lakehouse. Name it lh_sales_gold.
  2. In the lakehouse explorer, select the ... next to Files, then Upload > Upload files. Upload the CSV.

Step 2: build the gold tables in a notebook

Select Open notebook > New notebook from the lakehouse ribbon. The lakehouse is attached as the default. Paste this into one cell and run it.

from pyspark.sql import Window, functions as F

# New workspaces have V-Order off by default. Direct Lake reads V-Ordered files faster.
spark.conf.set("spark.sql.parquet.vorder.default", "true")

raw = (spark.read.option("header", True).option("inferSchema", True)
       .csv("Files/direct-lake-model-sales-kpis.csv"))

dim_product = (raw.select("product", "category").distinct()
               .withColumn("product_key", F.dense_rank().over(Window.orderBy("product")))
               .select("product_key", "product", "category"))

dim_date = (spark.sql("SELECT explode(sequence(DATE'2026-07-01', DATE'2026-09-30')) AS date")
            .withColumn("year", F.year("date"))
            .withColumn("month_no", F.month("date"))
            .withColumn("month", F.date_format("date", "yyyy-MM")))

fact_sales = (raw.join(dim_product.select("product", "product_key"), "product")
              .withColumn("order_date", F.to_date("order_date"))
              .select("order_id", "order_date", "product_key", "store_id", "quantity",
                      F.col("unit_price").cast("decimal(10,2)").alias("unit_price"),
                      F.col("discount").cast("decimal(4,2)").alias("discount"),
                      F.col("net_amount").cast("decimal(12,2)").alias("net_amount"),
                      F.col("cost_amount").cast("decimal(12,2)").alias("cost_amount")))

for name, df in [("dim_product", dim_product), ("dim_date", dim_date), ("fact_sales", fact_sales)]:
    df.write.mode("overwrite").option("overwriteSchema", "true").format("delta").saveAsTable(name)

print(spark.table("fact_sales").count()) # expect 66

Three choices here are deliberate. order_date and dim_date[date] are both date type, because Direct Lake relationships need matching column types. The product key is an integer built once in the dimension, because a string join on product names is how duplicates sneak onto the one side of a relationship. Money is cast to decimal, so the model sees fixed decimal numbers rather than floating point.

Step 3: create the Direct Lake on OneLake model

  1. Go back to the lakehouse. Select ... next to Tables, then Refresh so the three tables show.
  2. On the ribbon select New semantic model (some tenants label it New Power BI semantic model).
  3. Name it sm_sales_kpis, pick your workspace, tick fact_sales, dim_product and dim_date, then select Confirm.

Creating from the lakehouse, or from Create > OneLake catalog, gives you Direct Lake on OneLake. Direct Lake on SQL can only be created from the SQL analytics endpoint page (Reporting > New semantic model), where a dialog asks which type you want. Microsoft recommends OneLake for new models.

Step 4: relationships

The model opens in web modelling. If it opens read only, switch to Editing in the top right corner.

  1. Drag fact_sales[product_key] onto dim_product[product_key]. Set Many to one, cross filter Single.
  2. Drag fact_sales[order_date] onto dim_date[date]. Same settings.
  3. Select dim_date, then Mark as date table and choose the date column.

Web modelling does not validate cardinality for Direct Lake models. It trusts what you pick, so get the one side right in the Delta table, not in the dialog.

Step 5: three measures

Select fact_sales, then New measure, once per measure.

Net sales =
SUM ( fact_sales[net_amount] )
Gross margin % =
DIVIDE ( [Net sales] - SUM ( fact_sales[cost_amount] ), [Net sales] )
Average order margin % =
AVERAGEX (
    fact_sales,
    DIVIDE ( fact_sales[net_amount] - fact_sales[cost_amount], fact_sales[net_amount] )
)

Format the two percentage measures as Percentage with one decimal place. DIVIDE returns blank instead of an error when net sales are zero, which happens the day someone keys a free replacement as an order.

The two margin measures answer different questions and will not agree. Gross margin is a ratio of sums, so big orders weigh more. Average order margin treats every order the same. Put both on the page and label them. Otherwise someone will quote the higher one in a meeting.

Step 6: build the report

In web modelling, go to File > Create new report. Alternatively, from the workspace, open the ... menu on sm_sales_kpis and select Create report.

Add three cards for the measures, a clustered column chart of Net sales by dim_date[month] and a table of order_id, Average order margin % sorted ascending. Save it as rpt_sales_kpis. The two loss-making orders float to the top of that table, which is the point of the page.

How to tell OneLake from SQL

The two Direct Lake types look identical in a report. They behave very differently when something goes wrong.

Direct Lake on OneLakeDirect Lake on SQL
Table breaks a rule or a guardrailQuery or refresh errorsFalls back to DirectQuery, slower
SQL views as tablesNot allowedAllowed, always DirectQuery
SQL endpoint RLSNot appliedApplied, through fallback
Deployment rule to rebind sourceNot supportedSupported

To check which one you have, select Edit in Desktop from web modelling to live edit in Power BI Desktop, open TMDL view and drag the Expressions node onto the canvas. An AzureStorage.DataLake expression pointing at onelake.dfs.fabric.microsoft.com means OneLake. Sql.Database or OneLake.SqlAnalytics means SQL.

On a Direct Lake on SQL model, run this from Write DAX queries on the model's menu to see which tables are falling back and why:

EVALUATE TABLETRAITS()

A [DirectLakeFallbackInfo] value of None means Direct Lake. Anything else is a reason. On SQL models, set Direct Lake behavior to Direct Lake Only in the model properties while you develop, so fallback shows up as an error you can fix rather than a slow report you never notice.

Check it worked

The cards should read:

  • Net sales: 468,212.55
  • Gross margin %: 35.8%
  • Average order margin %: 37.6%

By month, net sales are 157,833.65 in July, 162,931.25 in August and 147,447.65 in September. The margin table should open with HG-40018 and HG-40052, both at minus 4.9%. If your numbers differ, check the CSV loaded all 66 rows before touching the DAX.

Now prove there is no refresh. Append one order in the notebook, two backpacks at full price:

spark.sql("""INSERT INTO fact_sales VALUES
  ('HG-40067', DATE'2026-09-30', 1, 'ST-014', 2, 1799.00, 0.00, 3598.00, 1960.00)""")

With Keep your Direct Lake data up to date on (the default), the Net sales card moves to 471,810.55 within a minute or two. No refresh schedule fired.

Where this breaks

  • Duplicate keys on the one side. If dim_product ever gets two rows with the same product_key, Direct Lake queries fail. The relationship dialog will not warn you. Test uniqueness in the notebook before you write the table.
  • Guardrails on small SKUs. An F2 to F32 allows 1,000 Parquet files and 300 million rows per table. A table that streams tiny appends all day will cross the file count long before the row count. On OneLake the refresh then fails and the model cannot be queried until you run OPTIMIZE. On SQL it falls back silently. One table over a guardrail stops Direct Lake for the whole model, not only that table.
  • SQL endpoint RLS that does nothing. RLS defined on the lakehouse SQL analytics endpoint is not applied by Direct Lake on OneLake. Queries succeed unfiltered. Put row level security in the semantic model instead.
  • Viewers who see errors. Direct Lake uses the viewer's own identity by default. Workspace Viewers have no OneLake read access, so give them ReadAll on the lakehouse, a OneLake security role or bind the model to a fixed identity cloud connection.
  • Half-loaded data on screen. Automatic updates reframe as soon as a Delta commit lands. If your pipeline loads facts before dimensions, users can see orphan rows for a few minutes. Turn automatic updates off in the model settings and trigger the refresh as the last step of the pipeline.

On the brewhouse floor

A brewery runs the same model with hectolitres instead of rupees. The fact table holds one row per brew at Brewery A: how much wort left the kettle and how much beer reached the keg. A yield measure is packaged volume over kettle volume, a ratio of sums exactly like gross margin. Across a quarter it might read 91 per cent while two batches sit near 81, which on the floor means a centrifuge having a bad week. Sort the batch table by yield and those two float to the top before the head brewer asks.
