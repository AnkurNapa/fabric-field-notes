Medallion done properly: orders to deliveries, bronze to gold

Build bronze, silver and gold for a retailer's orders and deliveries in one schema-enabled lakehouse, with materialised lake views as the contract between layers and an order chain bridge that answers when the customer actually got their goods.

Ankur Napa 11 Oct 2026, 11 min read

Short answer

Medallion is not three folders. It is three contracts. Bronze keeps what arrived, untouched. Silver promises types, keys and rules. It refuses data that breaks them. Gold promises a star schema at a declared grain that a report author cannot misuse. In Fabric the cleanest way to write the first two contracts is a materialised lake view with CONSTRAINT ... ON MISMATCH FAIL, because Fabric then owns the refresh order. The one thing SQL views cannot do well, walking a chain of replacement orders of unknown length, goes in a short PySpark notebook that writes a gold bridge table.

What you will build

A lakehouse lh_harbour with three schemas:

  • bronze.order_delivery_export: the nightly export as it arrived, loaded from CSV.
  • silver.order_delivery: a materialised lake view that types every column and fails the refresh on a broken rule.
  • gold: a star schema of dim_store, dim_product, fact_order and fact_delivery as materialised lake views, plus bridge_order_root built by a notebook.

The sample is one month of synthetic online orders for Harbour Goods, the fictional retailer used across this site: 60 orders placed between 2 August and 2 September 2026 from six stores, eight products and three carriers. Each row is one order with its delivery: the store and its city and region, the product with its category and unit cost, the quantity, price and discount, then the delivery id, carrier, dispatch time, delivery time and status. Download it here: medallion-order-to-delivery.csv.

Status is delivered, damaged or lost. When a parcel arrives damaged or never arrives, the store raises a replacement order at a price of zero and fills in replaces_order_id with the order it replaces. A replacement can go wrong too. In this month 52 customers placed orders, six of those needed at least one replacement and two needed two.

The question gold has to answer is the one a customer service lead gets from an angry customer: when did this person order and when did the goods actually reach them in one piece? In the store that answer lives on a damage claim form stapled to the delivery note. By the time someone asks, the form is in a box file and the parcel is long gone.

Before you start

  • A workspace on a Fabric capacity or trial with Contributor or higher. Users can create Fabric items must be on in the tenant.
  • Materialised lake views need a lakehouse with Lakehouse schemas enabled. Microsoft's quickstart lists Runtime 1.3 as the prerequisite; check the known issue below before you run scheduled refreshes on Runtime 2.0.
  • Materialised lake views are generally available. PySpark authoring for them is still in preview, which is one reason the chain walk here is an ordinary notebook.
  • Optional for production: a Fabric pipeline, so the view refresh and the notebook run in one order.

Steps

1. Create the lakehouse

  1. In the workspace select + New item > Lakehouse.
  2. Name it lh_harbour, keep Lakehouse schemas ticked, select Create.

2. Create the three schemas

Select Open notebook > New notebook, rename it nb_setup_harbour and run:

%%sql
CREATE SCHEMA IF NOT EXISTS bronze;
CREATE SCHEMA IF NOT EXISTS silver;
CREATE SCHEMA IF NOT EXISTS gold;

Schema names are letters, digits and underscores. Keep them lowercase: all-uppercase schema names are not supported for materialised lake views.

3. Land bronze

  1. Get data > Upload files, upload the CSV.
  2. In Files, ... > Load to tables > New table.
  3. Schema bronze, New table name order_delivery_export, Column header ticked, Load.

Then turn on change data feed so the views downstream can refresh incrementally:

%%sql
ALTER TABLE bronze.order_delivery_export SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

Bronze is never edited by hand. If an order was keyed wrong, the fix is a new corrected file, not an update.

4. Silver: the typed contract

In the same notebook, add a cell:

%%sql
CREATE OR REPLACE MATERIALIZED LAKE VIEW silver.order_delivery
(
    CONSTRAINT known_status    CHECK (status IN ('delivered', 'damaged', 'lost')) ON MISMATCH FAIL,
    CONSTRAINT has_keys        CHECK (order_id IS NOT NULL AND delivery_id IS NOT NULL) ON MISMATCH FAIL,
    CONSTRAINT positive_qty    CHECK (quantity > 0) ON MISMATCH FAIL,
    CONSTRAINT price_not_neg   CHECK (unit_price >= 0) ON MISMATCH FAIL,
    CONSTRAINT arrived_has_time CHECK (status = 'lost' OR delivered_at IS NOT NULL) ON MISMATCH FAIL
)
COMMENT "One row per order and its delivery, typed. Replacements carry replaces_order_id."
AS SELECT
    trim(cast(order_id AS STRING))                              AS order_id,
    try_cast(cast(order_date AS STRING) AS DATE)                AS order_date,
    trim(cast(store_id AS STRING))                              AS store_id,
    trim(cast(city AS STRING))                                  AS city,
    trim(cast(region AS STRING))                                AS region,
    trim(cast(product_id AS STRING))                            AS product_id,
    trim(cast(product_name AS STRING))                          AS product_name,
    trim(cast(category AS STRING))                              AS category,
    try_cast(unit_cost AS DECIMAL(10,2))                        AS unit_cost,
    try_cast(quantity AS INT)                                   AS quantity,
    try_cast(unit_price AS DECIMAL(10,2))                       AS unit_price,
    try_cast(discount AS DECIMAL(4,2))                          AS discount,
    nullif(trim(cast(replaces_order_id AS STRING)), '')         AS replaces_order_id,
    trim(cast(delivery_id AS STRING))                           AS delivery_id,
    trim(cast(carrier AS STRING))                               AS carrier,
    try_cast(cast(dispatched_at AS STRING) AS TIMESTAMP)        AS dispatched_at,
    try_cast(nullif(cast(delivered_at AS STRING), '') AS TIMESTAMP) AS delivered_at,
    lower(trim(cast(status AS STRING)))                         AS status
FROM bronze.order_delivery_export;

I use FAIL rather than DROP here on purpose. A delivery silently dropped from an order chain is a customer who vanishes from the complaints report and nobody notices until they phone again. A failed refresh is loud and the run history shows which constraint broke.

5. Gold: dimensions and facts

%%sql
CREATE OR REPLACE MATERIALIZED LAKE VIEW gold.dim_store AS
SELECT store_id, max(city) AS city, max(region) AS region
FROM silver.order_delivery
GROUP BY store_id;

CREATE OR REPLACE MATERIALIZED LAKE VIEW gold.dim_product AS
SELECT product_id, max(product_name) AS product_name,
       max(category) AS category, max(unit_cost) AS unit_cost
FROM silver.order_delivery
GROUP BY product_id;

CREATE OR REPLACE MATERIALIZED LAKE VIEW gold.fact_order AS
SELECT order_id, order_date, store_id, product_id, quantity, unit_price, discount,
       cast(round(quantity * unit_price * (1 - discount), 2) AS DECIMAL(12,2)) AS net_amount,
       replaces_order_id
FROM silver.order_delivery;

CREATE OR REPLACE MATERIALIZED LAKE VIEW gold.fact_delivery AS
SELECT delivery_id, order_id, carrier, dispatched_at, delivered_at, status
FROM silver.order_delivery;

The grain is written into each name: one row per order, one row per delivery. Note what fact_order does not tell you. It holds 60 rows, but only 52 customers ordered anything; the other eight rows are free replacements. A report author who counts rows in fact_order overstates orders by 15 per cent. The only honest route from a replacement back to the customer's order is the bridge.

6. Gold: the order chain bridge

Create a second notebook, nb_build_order_chain, attached to lh_harbour:

from pyspark.sql import functions as F

od = spark.read.table("silver.order_delivery")

# Each replacement points at the order it replaces
edges = (od.where("replaces_order_id IS NOT NULL")
           .select(F.col("order_id").alias("child"),
                   F.col("replaces_order_id").alias("parent")))

# Start every order at itself and walk back until no order has a parent
frontier = od.select("order_id",
                     F.col("order_id").alias("root_order_id"),
                     F.lit(1).alias("attempt_no"))

MAX_HOPS = 10   # the longest chain this month is 2 hops: two replacements
for _ in range(MAX_HOPS):
    step = (frontier.alias("f")
            .join(edges.alias("e"), F.col("f.root_order_id") == F.col("e.child"), "left")
            .select(F.col("f.order_id"),
                    F.coalesce(F.col("e.parent"), F.col("f.root_order_id")).alias("root_order_id"),
                    (F.col("f.attempt_no")
                     + F.when(F.col("e.parent").isNotNull(), 1).otherwise(0)).alias("attempt_no"),
                    F.col("e.parent").isNotNull().alias("moved")))
    if step.where("moved").limit(1).count() == 0:
        break
    frontier = step.drop("moved")
else:
    raise RuntimeError("Order chain deeper than MAX_HOPS. Look for a loop in replaces_order_id.")

(frontier.write.mode("overwrite")
         .option("overwriteSchema", "true")
         .saveAsTable("gold.bridge_order_root"))

bad = spark.sql("""
    SELECT b.order_id FROM gold.bridge_order_root b
    JOIN silver.order_delivery s ON s.order_id = b.root_order_id
    WHERE s.replaces_order_id IS NOT NULL
""")
assert bad.count() == 0, bad.collect()
print("bridge OK")

Why a notebook and not a view: the walk repeats until it reaches an order with no parent and the number of steps depends on the data. A view is one SELECT. When a courier has a bad week and a parcel needs a third replacement, the chain gets a hop longer and this loop does not care.

7. Refresh in the right order

  1. In lh_harbour select Materialized lake views > Manage to see the lineage Fabric derived from the definitions.
  2. For a production run, create a pipeline: a Refresh Materialized Lake View activity pointed at lh_harbour, then on success a Notebook activity running nb_build_order_chain.

That pipeline is the hand-off for roadmap step eng-2-2. With change data feed on bronze, optimal refresh can process only changed rows instead of rebuilding every view.

Check it worked

Run these in Spark SQL cells. The SQL analytics endpoint will give the same answer once its metadata sync catches up. First, sales by region, counting customers rather than rows:

%%sql
SELECT s.region,
       COUNT(DISTINCT b.root_order_id) AS customer_orders,
       COUNT(*)                        AS order_rows,
       SUM(o.net_amount)               AS net_sales
FROM gold.fact_order o
JOIN gold.bridge_order_root b ON b.order_id = o.order_id
JOIN gold.dim_store s         ON s.store_id = o.store_id
GROUP BY s.region
ORDER BY s.region;

Expected:

regioncustomer_ordersorder_rowsnet_sales
North151749248.25
South161854442.80
West2125107598.30

The total is 211,289.35 rupees. Replacements add rows but no money, which is exactly why the two counts differ.

Then the customer's view, order to door:

%%sql
WITH chain AS (
    SELECT b.root_order_id,
           MAX(b.attempt_no) AS attempts,
           MAX(CASE WHEN d.status = 'delivered' THEN d.delivered_at END) AS delivered_at
    FROM gold.bridge_order_root b
    JOIN gold.fact_delivery d ON d.order_id = b.order_id
    GROUP BY b.root_order_id
)
SELECT COUNT(*)                                        AS customer_orders,
       SUM(CASE WHEN c.attempts = 1 THEN 1 ELSE 0 END) AS right_first_time,
       COUNT(c.delivered_at)                           AS delivered_in_the_end,
       ROUND(AVG(datediff(to_date(c.delivered_at), o.order_date)), 2) AS avg_days_to_door
FROM chain c
JOIN gold.fact_order o ON o.order_id = c.root_order_id;

Expected: 52 customer orders, 46 right first time, 52 delivered in the end and an average of 3.48 days from order to door. For order HG-30041 the bridge should show three rows: HG-30041 at attempt 1, HG-30042 at attempt 2 and HG-30043 at attempt 3, all with root HG-30041. The first two parcels were lost; the third arrived on 6 September, 13 days after the customer ordered. If that chain is right, the walk is right.

Naming

  • Lakehouse lh_harbour. Lakehouse names start with a letter and allow letters, digits and underscores.
  • Schemas by layer: bronze, silver, gold. Tables lowercase with underscores; materialised lake view names are lowercased anyway.
  • Gold prefixes say what a table is: dim_, fact_, bridge_.
  • Notebooks by verb and object: nb_setup_harbour, nb_build_order_chain. Pipelines pl_harbour_nightly.

This walkthrough keeps all three layers in one lakehouse so it fits in an afternoon. That is prototype-grade. Workspace Admins, Members and Contributors bypass OneLake security, so schemas in one lakehouse give weak isolation. In production I split it into one workspace per layer, named <domain>-<layer>-<env> such as sales-silver-prod. The view definitions then use four-part names (workspace.lakehouse.schema.table).

Where this breaks

  • Runtime 2.0 and scheduled refresh. Fabric known issue 1985 reports daily materialised lake view refreshes failing on Runtime 2.0 with Spark_System_OneLakeSecurity_OperationFailed. Check the issue for the current workaround before you trust the schedule.
  • Session settings are ignored on schedule. spark.conf.set in your notebook has no effect on a scheduled view refresh. Set properties at the lakehouse or workspace level.
  • No DML on a view. You cannot UPDATE a row in silver.order_delivery to fix a mistyped carrier. Fix it in a new bronze file and let the refresh carry it through. That is a feature.
  • The pipeline activity refreshes everything. Refresh Materialized Lake View refreshes all views in the selected lakehouse and does not support a service principal or workspace identity yet.
  • Incremental needs change data feed. Without it on the source tables, optimal refresh can only choose between full and skip.
  • Direct Lake and views. Direct Lake on OneLake cannot read non-materialised SQL views. Keep gold as tables or materialised lake views.

Next on the roadmap

Gold here is overwritten every run, which is fine for orders but wrong for a store that moves to a new region after a reorganisation. Keeping that history is the next step, SCD type 2 with Delta MERGE: Keep history in a dimension. The rest of Level 2 is on the roadmap. If you skipped the basics, start with your first notebook.

On the brewhouse floor

A winery has the same chain problem, only longer. Grapes from a vineyard block become juice, the juice becomes wine in a tank, several tanks are blended and the blend is bottled. Each step is a row saying "this lot came from that lot", like a replacement pointing at the order it replaces. The same loop walks a bottling run back to the vineyard blocks it came from and works out each block's share by volume. When a buyer asks which vineyard is in bottle run BT-03 at Winery A, the answer comes from a table instead of a blend sheet that was clipped to a tank now long since emptied.
