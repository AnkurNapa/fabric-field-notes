Coexisting with Databricks and Snowflake: Fabric as one engine

A design guide for platforms where Databricks or Snowflake stays and Fabric joins. Mirroring versus Iceberg versus migration, who writes which table, where security has to be rebuilt and the patterns that quietly double the compute bill.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 4 Ankur Napa LakehouseDirect LakeGovernanceSecurity

Short answer

Fabric is designed to sit next to Databricks and Snowflake, not to replace them on day one. Keep the incumbent where the team is strong and the workload is stable. Add Fabric where Power BI, real-time or business self-service is the pain. The rule that keeps this sane is one writer per table: each table has exactly one engine that writes it and every other engine reads. For Azure Databricks, mirror the Unity Catalog into Fabric. Only metadata is mirrored and the data is read through shortcuts, so nothing is copied. For Snowflake, either mirror (Fabric replicates managed tables into OneLake as Delta) or have Snowflake write Iceberg tables into OneLake. Permissions never travel with the data in either case, so plan the security rebuild before anyone sees a report.

The limits that change designs:

  • A mirrored Databricks catalog does not show materialised views or streaming tables. It skips external tables that are not Delta. Tables are read-only in Fabric.
  • Snowflake mirroring takes managed and Iceberg tables. External, transient, temporary and dynamic tables are not supported. The cap is 1,000 tables per mirrored database. Mirror all data silently takes the first 1,000 sorted by schema then table name. One older section of the limitations page still says 500, so check the page on the day you design.
  • Snowflake can only reach OneLake over the public network for Iceberg. A workspace locked behind private link is out.

Reference design

Harbour Goods, the fictional retailer used across this site, has a Databricks team that builds orders and deliveries from store systems and a finance team on Snowflake that owns products costing. Leadership wants Power BI on Direct Lake and an alert when deliveries run late.

Who writes what:

The serving lakehouse holds shortcuts to the mirrored tables plus the few tables Fabric genuinely owns. Mirrored databases are read-only, so any calculated column or derived table is built in that lakehouse, never by asking the source team for one more column every week.

Questions to ask the client

  1. Which engine is the system of record for each subject area? If two teams both answer "us" for the same table, stop and settle that first.
  2. Is the Databricks workspace behind a private endpoint? Mirroring needs external data access on the metastore and the EXTERNAL USE SCHEMA privilege. It does not work if the workspace sits behind a private endpoint.
  3. Which Snowflake warehouse do the apps already keep warm? Point mirroring at that one so it does not wake a separate warehouse.
  4. How many Snowflake tables are in scope? Over 1,000 means more than one mirrored database or a narrower selection.
  5. What row level security, column masking or ABAC exists in Unity Catalog or Snowflake today? Every rule has to be rebuilt in Fabric. List them now.
  6. Who pays which bill? Snowflake credits rise when changes are read for mirroring. Finance should hear that from you, not from the invoice.
  7. Is there a plan to switch either platform off within three years? If yes, design the coexistence as a migration's first wave.

Review checklist

  • Every table in scope has exactly one writer, written down.
  • Silver data is not rebuilt in Fabric when Databricks already produces it.
  • OneLake security roles (or semantic model RLS) reproduce every source-side access rule, tested with a restricted user.
  • Mirrored table counts checked against the 1,000-table Snowflake limit, with an explicit table list rather than Mirror all data.
  • Snowflake resource monitors or budgets set for mirroring-related credits.
  • A reseed alert or weekly check on the Snowflake mirroring status page; a reseed re-reads the whole table.
  • Freshness expectation agreed with report owners, since mirrored Databricks changes take seconds to minutes to appear.
  • Known issue checked: dropping and recreating a Unity Catalog table with the same name breaks the mirror.

Anti-patterns

  • Two writers, one table. Databricks writes orders and a Fabric notebook "just fixes a few rows". The next Databricks overwrite undoes it and nobody knows which number was right.
  • Rebuilding silver twice. The same cleaning logic in Databricks and Fabric means two compute bills and, by the second month, two different answers.
  • Assuming permissions came along. Mirroring moves structure and data, not grants. A report built on a mirrored table with no security rebuilt is an open door.
  • Mirror everything. Mirroring a whole Snowflake database for six tables burns credits and Fabric capacity on reseeds nobody needed.
  • Calling it temporary. A coexistence nobody designed becomes the permanent architecture. Decide whether it is a destination or a waypoint. Then write that down.

On the brewhouse floor

A winery often has the same split without calling it architecture. The vineyard team logs harvest picks and sugar readings in one system, the cellar team tracks tank transfers and blends in another. Finance costs every bottle somewhere else. One writer per table applies there too: the cellar system owns which wine sits in tank T-12 and what went into it. The reporting layer only reads. The day someone corrects a blend percentage in the report's own copy, the traceability record for that bottling stops matching the cellar book.
