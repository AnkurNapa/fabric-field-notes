Data engineering basics, lesson 1 of 8

What a data engineer actually does

Lesson 1 of Data engineering basics. A data engineer gets data from where it is made to where people can trust it, on time, every time. You will set up the workspace and lakehouse the whole course uses.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Ankur Napa Lakehouse

Short answer

A data engineer builds and looks after the plumbing that moves data from the systems where it is created to the place where analysts, reports and AI can use it. The job is less about clever code and more about reliability: the right data, in the right shape, at the right time, with someone told when it goes wrong. In Microsoft Fabric that plumbing lives in one place, so you can learn the whole job in one tool.

Why it matters for your career

Almost every analytics team has more people wanting data than people who can deliver it. Data engineering is the role that unblocks everyone else, which is why it is one of the most hired data roles. If you can show a working pipeline from raw file to clean table, you can talk credibly in an interview.

The idea

Imagine Harbour Goods, a mid-size retailer and distributor with stores in six Indian cities. Every day its tills record orders: an order id, the date, the store, the product, the quantity, the price and any discount. Those records sit in the till system. The finance team wants revenue by region every morning. Nobody wants to sign in to the till system and copy rows into a spreadsheet by hand.

The data engineer's work sits between those two points. A few plain words you will meet all through this course:

  • Source: the system where data is created, such as the till system.
  • Ingest: copy data from the source into your own storage.
  • Transform: clean and reshape data so it is correct and easy to use.
  • Table: data arranged in rows and columns with a fixed set of column names.
  • Pipeline: a set of steps that runs in order, for example copy then clean.
  • Lakehouse: in Fabric, a storage item that holds both raw files and tables.

Here is a typical day of work, mapped to Harbour Goods:

TaskHarbour Goods exampleWhere it lives in Fabric
IngestCopy yesterday's orders file from the till exportPipeline or Copy job
StoreKeep the file as it arrived, then as a tableLakehouse, in OneLake
TransformRemove a duplicated order, fix a bad dateNotebook, Dataflow Gen2 or SQL
Check qualityCount rows, flag a quantity of -2SQL query or notebook
ScheduleRun all of this at 06:00 every dayPipeline schedule
Hand overGive finance a clean revenue tableLakehouse table read by Power BI

Everything in Fabric is stored in OneLake, a single data lake for your whole organisation. A data lake is large, cheap storage for files of any kind. Because every Fabric tool reads the same OneLake, you rarely copy data between tools. That one fact removes a lot of the plumbing data engineers used to build.

Try it in Fabric

You will create the workspace and lakehouse the rest of the course uses. You need a Fabric capacity or a free Fabric trial and permission to create items. A workspace is a folder in Fabric that holds your items and controls who can see them.

  1. Open the Fabric portal and select Workspaces > + New workspace.
  2. Name it harbour-dev.
  3. Expand Advanced and under the workspace type pick Fabric Trial or Fabric with your capacity. Then select Apply.
  4. In the new workspace select + New item, search for Lakehouse and select it.
  5. Name it lh_harbour. Lakehouse names may only use letters, digits and underscores. Leave Lakehouse schemas ticked and select Create.
  6. Look at the Explorer pane on the left. You will see two areas: Tables and Files. Files is where raw data lands. Tables holds data that every Fabric engine can query.
  7. Go back to the workspace. Next to lh_harbour you will see a SQL analytics endpoint with the same name. Fabric created it for you so you can query the tables with SQL later.

That is the whole setup. Lessons 2 to 8 fill this lakehouse step by step.

Common beginner mistakes

  • Thinking the job is mostly coding. Most failures are not code bugs. They are a file that arrived late, a column that changed name or a duplicate row nobody noticed.
  • Building on a Power BI Pro licence alone. Pro does not give you a capacity, so you cannot create a lakehouse. Use the free trial.
  • Naming things casually. New lakehouse 3 becomes a mystery in six months. Pick a pattern such as lh_ for lakehouses and stick to it.
  • Skipping the boring bits. Schedules, alerts and row counts feel optional until the morning a report shows yesterday's numbers.

On the brewhouse floor

In a small brewery the fermentation log often starts on a clipboard hanging on tank FV-03, gets typed into a spreadsheet on Friday and lives on one laptop. A data engineer at Brewery A would do the same job as at Harbour Goods: get those daily gravity and temperature readings into one lakehouse, check that nobody typed 1.012 as 1012, then hand the brewer a table that is always up to date. The tank does not care about the tools. It cares that the reading from Tuesday morning is not lost.
