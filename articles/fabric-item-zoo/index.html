The item zoo: lakehouse, warehouse, eventhouse and SQL database

Four Fabric items store data and all of them land it in OneLake. What separates them is who writes, in which language and how fresh the data has to be. A short guide plus a ten-minute tour to see each one with your own eyes.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 0 Ankur Napa LakehouseWarehouseKQL

Short answer

Fabric gives you four places to keep tables and newcomers lose a week deciding between them. The deciding question is not how big the data is. It is who writes it and how.

  • Lakehouse: Spark and Python people write it. Files and Delta tables side by side. The SQL analytics endpoint reads it with T-SQL but cannot write.
  • Warehouse: SQL people write it. Full T-SQL inserts, updates, deletes, MERGE and multi-table transactions.
  • Eventhouse: events write it, seconds after they happen. You query with KQL. Built for telemetry, logs and time series.
  • SQL database: an application writes it, one row at a time. The Azure SQL engine, made for OLTP work and write-back, not for scanning a year of history.

All four end up as Delta in OneLake, so a table written by one engine can be read by the others. The one exception is the eventhouse, where OneLake availability is something you switch on.

The idea in one picture

Take Harbour Goods, the fictional retailer and distributor used across this site. It has stores in a dozen Indian cities, two cold-store warehouses and four kinds of data. Each kind has a natural home:

LakehouseData engineers, notebooks, pipelinesPySpark, Spark SQL; T-SQL read onlyRaw orders exports, supplier price files, product imagesA form someone edits all day
WarehouseSQL developersT-SQL, full DMLGold star schema: orders facts with products and stores dimensions for margin by regionSensor readings every ten seconds

That last row is the one teams get wrong most often. Most distribution sites still run dispatch from a whiteboard by the loading dock: bay numbers down the side, carrier and slot written in marker, wiped and rewritten when a van runs late. That board is a transactional database. Small rows, many edits a day, two people changing it at once. Moved into Fabric, it belongs in a SQL database, not a lakehouse. The analytics on top of it (how many late dispatches per carrier last quarter) belong somewhere else. The automatic mirror to OneLake is how they get there.

A ten-minute tour

You need a workspace on a Fabric capacity or a trial. These items cost almost nothing while they sit idle; delete them afterwards if the capacity is shared.

  1. Open your workspace and select + New item. The dialog groups items by task. Look under the storage group (the label may read Store data) and find Lakehouse, Warehouse, Eventhouse and SQL database together. That grouping is the whole point of this article.
  2. Create a Lakehouse called lh_zoo. Back in the workspace list you now have two rows: the lakehouse and a SQL analytics endpoint with the same name. You did not ask for the second one. Every lakehouse gets one and it is read only.
  3. Open the lakehouse. Note the Files and Tables folders in the Explorer. Files takes anything; only Delta under Tables shows up to SQL.
  4. Create a Warehouse called wh_zoo. Select New SQL query and run CREATE TABLE dbo.t (id int); INSERT INTO dbo.t VALUES (1);. It works. Try the same INSERT against a lakehouse table through its SQL analytics endpoint later and it fails. That difference is the whole of the lakehouse or warehouse question in one line.
  5. Create an Eventhouse called eh_zoo. A KQL database with the same name appears inside it. Open the database and look for OneLake availability in the database details. It is off by default. Turn it on only when Spark or Power BI needs the data as Delta.
  6. Create a SQL database called sqldb_zoo. When it opens, look at the workspace list again: it also brings a SQL analytics endpoint, because Fabric mirrors the database into OneLake for you.
  7. Delete what you made, unless you plan to follow the roadmap straight on.

What people get wrong

  • "Warehouse is faster than lakehouse." Both read Delta in OneLake through the same SQL engine. The choice is about how you write, not raw speed. Microsoft's decision guide frames it as skill set and the need for multi-table transactions.
  • "The SQL endpoint means I can write SQL." You can create views and functions there. You cannot insert, update or delete lakehouse data through it. Teams that need T-SQL writes want a warehouse.
  • "Real time means eventhouse, so put everything there." Eventhouse earns its place when freshness is measured in seconds or the data is event-shaped. Batch history belongs in a lakehouse. When you do turn on OneLake availability, the Delta copy can lag (up to three hours by default, configurable) and some table operations such as rename and delete are blocked while it is on.
  • "SQL database is a small warehouse." It is an OLTP engine with indexes, foreign keys and auto-scaling compute. Point a big analytical scan at it and you are using the wrong tool. Cap its vCores on a shared capacity so a busy app does not starve your reports.
  • Item limits. A workspace holds at most 150 warehouses plus SQL analytics endpoints combined and SQL database has its own per-workspace cap (lower on a trial). If you plan one lakehouse per source system, count first.

On the brewhouse floor

Brewery A has the same four kinds of data. Brew logs and lab results land in a lakehouse, the cost per hectolitre model lives in a warehouse and fermenter temperature probes stream into an eventhouse every ten seconds. The tank booking board by the cellar door, with tank numbers like FV-03 and the beer pencilled against each, is the SQL database: small edits all day by people on the floor. Same zoo, same rule. Pick the home by who writes and how often.
