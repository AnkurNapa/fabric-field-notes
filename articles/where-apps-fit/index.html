Where apps fit: GraphQL, the SQL endpoint and Fabric Apps

Three ways code reaches Fabric data: the SQL connection string for tools and scripts, API for GraphQL for applications and Fabric Apps (preview) when you want Fabric to host the whole back end. What each is for and where each stops.

11 Oct 2026 Fabric as of October 2026 Checked against Microsoft Learn Level 0 Ankur Napa RayfinWarehouseSecurity

Short answer

Reports are for people. When code needs Fabric data, there are three doors.

The SQL connection string is the oldest. Every warehouse and lakehouse SQL analytics endpoint has one. Anything that speaks T-SQL over TDS with Microsoft Entra sign-in can use it: SSMS, VS Code, Python, a .NET service. API for GraphQL is a Fabric item that puts a managed GraphQL endpoint over a warehouse, lakehouse, SQL database or mirrored database and writes the schema for you. Fabric Apps (preview), built on the Rayfin SDK, goes further: you describe your data model in TypeScript and Fabric creates a SQL database, a GraphQL API, sign-in and static hosting for the front end.

The rule of thumb: scripts and tools use SQL, application reads and simple writes use GraphQL, a small internal app with its own data uses Fabric Apps. Never point an app at a report.

Take Harbour Goods, a fictional retailer. The finance team's Python script pulls last month's orders through the SQL connection string. A store app shows each store its open deliveries through API for GraphQL over the gold warehouse. The team that logs damaged-delivery claims wants a small form with its own table, so that becomes a Fabric App.

A ten-minute tour

  1. Copy a SQL connection string. In a workspace, find a lakehouse's SQL analytics endpoint or a warehouse, select ... and look for Copy SQL connection string (on some items it sits under Settings > SQL connection string). It looks like <id>.datawarehouse.fabric.microsoft.com. Paste it into SSMS as the server name and sign in with Microsoft Entra ID - Universal with MFA support.
  2. Create an API for GraphQL item. Select + New item and, under Develop data, pick API for GraphQL. Name it and select Create. The endpoint exists straight away, empty.
  3. Choose how callers sign in. Select the Select data source tile. You pick Single sign-on, where each caller needs access to the data, or Saved credentials, where one stored credential reads the data for everyone. You cannot mix the two in one API.
  4. Add a table and look at the schema. Pick a warehouse from the OneLake catalog, tick one table and select Load. The schema explorer now lists a query type for it. Write one query in the editor and select Run. Then select Copy endpoint to see the URL an app would call.
  5. Look at the Fabric Apps switch. In the admin portal's Tenant settings, find Fabric Apps (preview). It is off until a tenant admin enables it. If you are curious, npm create @microsoft/rayfin@latest my-app scaffolds a project on Node.js 20 or later. Do not deploy it yet. The Level 3 walkthrough covers that.

What people get wrong

  • Expecting to write through the lakehouse endpoint. It is read only. Write with Spark or use a warehouse or SQL database.
  • Forgetting primary keys. GraphQL needs a key on every object it exposes. A table without one gives you a thin, awkward API.
  • Pulling a whole table through GraphQL. Results come back 100 items a page by default, with a 100-second timeout and a 64 MB response limit. It is an app API, not an export tool. Use SQL for bulk reads.
  • Choosing saved credentials without thinking. Every caller then sees whatever that credential can see. Single sign-on keeps each user's own permissions.
  • Treating Fabric Apps as a finished platform. It is in preview and not in every region. Deployed apps sign in with Microsoft Entra only, the email and password sign-in stops working once you deploy, it manages its own database rather than attaching to yours and secrets must never sit in front-end code. Good for internal tools, not yet for anything customer-facing.
  • Splitting regions. Keep the app, the capacity and the data in one region. Cross-region calls add latency on every request.

On the brewhouse floor

A winery's cellar team logs every topping, racking and addition on a tablet. Winery A wants that log in Fabric without building a web server. A small Fabric App holds the cellar log in its own SQL database and gives the cellar hands a sign-in screen and a form. A nightly job reads the finished lots through the SQL connection string for the vintage report. The bottling line's screen reads tank status through API for GraphQL. One set of data, three doors, each used for what it is good at.
